目标：从 0 开始学习实现一个工业级的流量网关。

# 需求

## 一、功能需求：网关自身能力完善

网关需具备一套完整的流量处理能力，核心功能包括：

- **安全类**：鉴权（身份认证）、校验（参数/请求合法性）、加解密（客户端↔网关、网关↔后端 两段）
- **治理类**：限流、熔断、负载均衡、重试、超时控制
- **流量类**：路由匹配、协议转换、请求/响应改写（Header、Path、Body）
- **转发**：把请求可靠地送达后端并返回响应

架构上满足三点：

1. **filter chain 编排**：以上功能统一通过一条可编排的处理链组合，而非散落在各处硬编码；
2. **可扩展、可插拔**：新增一个功能 = 新增一个 Filter，不动既有代码；
3. **可二次开发**：提供稳定的接口，允许接入方实现自定义 Filter。

## 二、性能需求：高并发

- 单实例目标 **QPS 5w**；
- 负载能力可**横向提升**：通过增加实例、扩展为集群的方式线性扩容；
- 由此要求网关**无状态化**（配置/数据不落单机内存），以便任意实例可被调度。

## 三、可观测性需求：logs / trace / metrics

- 链路中**任意环节**（接入、过滤、路由、转发、后端）均可追踪；
- 三件套配套完整：
  - **logs**：结构化日志，能定位每次请求的处理明细；
  - **trace**：贯穿网关与后端的分布式链路，支持跨服务串联；
  - **metrics**：QPS、延迟、错误率、熔断/限流命中次数、后端健康度等指标；
- 可**暴露 API 接口**（如 `/metrics`）供外部采集与数据分析。

## 四、可靠性需求：错误处理与可用性

- 各类异常场景（后端超时、后端宕机、限流触发、校验失败、内部错误）下：
  1. 将**错误以合适的语义上抛给调用方**（明确的状态码与错误体，而非网关崩溃或挂死）；
  2. **不影响整体服务**：单点失败被隔离，避免雪崩、避免阻塞其他请求。

## 五、需求：超时与重试（整条链路）

- 超时控制贯穿**整条链路**的每个环节（接入、过滤、路由、转发、后端），每个环节都有独立的超时上限，防止单环节挂起拖垮整体；
- 关键超时项：连接建立超时、请求读超时、响应写超时、后端调用超时、整体处理超时（兜底）；
- 重试策略：仅对**幂等且可重试**的请求生效，定义重试次数与退避策略；超时/失败时在可用额度内重试，超出则上抛错误；
- 核心目标：**任何请求都不会无限挂起**，耗尽连接或阻塞其他请求。

## 六、需求：配置管理

- 路由规则、限流阈值、Filter 开关等配置需支持**热更新**，改配置不重启；
- 为可扩展、可插拔提供配置入口，让新增/调整能力不动代码；
- 初期（单机单实例）实现：先以**静态配置 + 重启生效**跑通，仅保留配置加载的抽象接口，便于后续平滑升级为热更新。

## 七、需求：生命周期管理（后置）

- 目标：优雅启停（平滑关闭，不打断在途请求）、连接池复用与回收；
- **当前阶段（单机单实例起步）不做**，待核心链路跑通、进入集群阶段再补齐。

# 链路构建

需要分层，梳理出通用流程，为接口设计提供依据。

## 总体分层：三阶段

一次请求在网关内经历三个大阶段，由网关的"角色边界"天然切分：

```
┌──────────────────┐   ┌───────────────────────┐   ┌────────────────────┐
│  接入层 Listener   │ → │  Filter Chain（业务层） │ → │  后端对接层 Upstream │
│  连接/协议/解析     │   │  鉴权/限流/熔断/路由...  │   │  负载均衡/协议转换/转发 │
└──────────────────┘   └───────────────────────┘   └────────────────────┘
     连接管理             一条业务处理链                后端通信
     与业务无关              核心可扩展点                独立于业务
```

### 1. 接入层（Listener）—— 管"连接"，不懂业务

| 职责 | 说明 |
|------|------|
| TCP 连接管理 | accept、连接生命周期、TLS 终止、连接复用 |
| 协议嗅探 | 连接建立后读取前几个字节，判断是 HTTP/1.1 / HTTP/2 等 |
| 协议解析 | 把 TCP 字节流解析成标准 HTTP 请求（七层语义） |

- **角色**：把"字节流"翻译成"业务可读的请求"。
- **与业务无关**：它不知道要鉴权、要转发给谁，只负责把连接和协议处理好。
- **客户端协议转换发生在这一层**（HTTP/1.1 ↔ HTTP/2 由接入层解析器决定）。

### 2. 业务层（Filter Chain）—— 管"业务处理"，纯逻辑

- **角色**：对已解析好的请求做业务决策（鉴权、限流、熔断、加解密、改写、路由）。
- **不碰 socket**：只读/改一个标准上下文对象（RequestContext），与连接、协议完全解耦。
- **核心可扩展点**：所有功能都表现为可插拔的 Filter。

Filter Chain 内部再切成 **4 个子阶段**，过滤器按执行时机归属不同阶段：

```
         ┌──────────────────────────────────────────────────────────┐
         │                      Filter Chain                         │
         │  ① 前置过滤   ② 路由   ③ 目标选定   ④ 后置过滤   ⑤ 转发标记 │
         └──────────────────────────────────────────────────────────┘
```

| 子阶段 | 过滤器示例 | 时机 |
|--------|-----------|------|
| ① 前置过滤 | 鉴权、限流、IP 黑名单、防攻击校验 | 请求一进来即判断，可拦截短路 |
| ② 路由 | 按 Host / Path / Method / Header 匹配目标服务与规则 | 决定"发给谁" |
| ③ 目标选定 | 熔断检查、加解密（加密发给后端）、请求改写、负载均衡选实例 | 路由之后、真正转发之前 |
| ④ 后置过滤 | 响应改写、响应加解密 | 转发拿到响应之后 |
| ⑤ 转发标记 | 标记"发起出站转发" | 衔接后端对接层 |

### 3. 后端对接层（Upstream）—— 管"怎么送到后端"

| 职责 | 说明 |
|------|------|
| 负载均衡 | 从服务的一组实例中选一个（轮询 / 最少连接 / 一致性哈希） |
| 出站连接 | 复用连接池、建立到实例的连接 |
| 协议适配 | 后端协议转换（HTTP ↔ gRPC 等），**发生在路由之后** |
| 发送与等待 | 发请求、等待响应，受读写超时约束 |
| 结果处理 | 成功即返回；失败 / 超时则触发重试、更新熔断器状态 |

- **角色**：把"已选定的请求"可靠送达后端并取回响应。
- **熔断器状态切换真正发生在这里**：Filter 只负责"检查熔断是否放行"，而"开→半开→关"的状态迁移，由转发结果的成败反馈驱动。

## 层与层之间的协作关系、通信模式

各层**各自持有自己的字段**，互不共享，层与层之间通过传参衔接：

```
接入层 ──▶ 入站数据 ──▶ 业务层 Filter Chain
业务层 ──▶ 出站数据 ──▶ 后端对接层
后端层 ──▶ 响应/反馈数据 ──▶ 业务层 / 接入层
```

### 协作约定

1. **单向流转**：请求沿 `接入层 → 业务层 → 后端层` 推进，响应反向回传；
2. **按层隔离**：各层字段归各层所有，不共享可变状态，层间仅以接口衔接，各自可替换；
3. **贯穿身份**：公共身份字段（`RequestContext`：traceId、来源、时间）随数据流转，用于串联链路与关联可观测数据；
4. **反向反馈**：后端层通过响应数据回传成败/熔断/重试状态，供 Filter 与可观测消费；
5. **超时贯穿**：每个环节独立/共享超时预算，任一步超时即中止并上抛错误。

# 数据模型

数据模型分两类：**运行时数据**（请求在链路中流动的载体）与**配置数据**（路由、限流等规则）。

## 一、运行时数据（按层组织）

```
| 数据 | 流向 | 内容 | 生命周期 |
|------|------|------|----------|
| 入站请求数据 | 接入层 → 业务层 | 解析后的请求、来源、TLS 状态 + 公共身份 | 请求进入即创建，随请求结束销毁 |
| 业务决策状态 | 业务层内 | 路由结果、限流/熔断命中、目标服务 | 随链路推进写入，完成后归档 |
| 出站指令数据 | 业务层 → 后端层 | 目标服务/实例、重写后请求、超时/重试预算 + 公共身份 | 转发阶段构造，发出后复用回传 |
| 响应/反馈数据 | 后端层 → 业务层/接入层 | 状态码、响应体、错误、成败反馈 + 公共身份 | 响应生成时创建，回传后销毁 |
```

> 字段不在此处穷举，仅定义各阶段数据的边界与流转关系，具体字段在接口设计阶段按需补充。

## 二、配置模型

配置与运行时数据分离，路由、限流、Filter 等规则以配置形式加载：

- **路由配置**：Host / Path / Method / Header 匹配规则 → 目标服务映射；
- **Filter 配置**：各过滤器开关与参数（限流阈值、熔断阈值、鉴权开关等）；
- **服务配置**：目标服务实例列表（当前阶段为**静态配置**，将来可切换为服务发现 Provider）；
- **超时/重试配置**：各环节超时上限、重试次数与退避策略。

配置加载抽象为统一接口，当前以**静态配置 + 重启生效**实现，为后续热更新保留升级空间。

## 实习经历

### 腾讯开源蓝鲸 DBM 数据库高可用系统（DBHA）：自建 gRPC 故障探测上报通道
**2026.04 至今** | **腾讯科技有限公司·后端开发**  
[https://github.com/TencentBlueKing/blueking-dbm](https://github.com/TencentBlueKing/blueking-dbm)

* **技术栈**：MySQL / Go / gRPC
* **背景**：已有外部的 GSE 云通道用于数据上报；需要搭建自有 gRPC 链路作为备选
* **目标**：选取最适合周期性数据上报场景的 gRPC 通信模式，完成链路开发
* **结果**：经过端到端测试与异常测试，功能完善且具备客户端负载均衡、故障可恢复等特性

**独立负责完整项目**，从调研、选型、设计、开发到测试，独立完成 gRPC 上报链路全流程。

* **gRPC 通信模式对比**：对 Unary / Client Streaming / Bidirectional Streaming 做系统性压测对比
  * Unary RPC 使用第三方压测工具 ghz，以错误率为极限判定依据，单机并发量可达 6-7 万，QPS 在 2w 出头
  * Client Streaming 和 Bidirectional Streaming 均搭建最简客户端与服务端，通过配置文件控制连接数与消息上报间隔
    * 以客户端内存资源耗尽为极限判定依据，客户端流最多可维持 1.5w 连接，双向流最多可维持 5.5w 连接
* **pprof 排查内存异常问题**：使用 pprof 排查 client streaming 模式下客户端内存占用异常的根因，结合 sizePool / cs.Buffer 等线索进行推断
* **技术选型决策**：基于压测数据（CPU/内存、RPS、P99延迟、错误率、并发量等）结合业务场景，确定 Unary RPC 为最终通信方案
* **实现多实例高可用**：调研后利用 gRPC 框架的 resolver + loadBalancer 机制，完成多 receiver 负载均衡、故障切换、探活重连
* **混沌测试**：验证 probe / receiver / db 链路上任意节点宕机后可自愈，后续能够继续正常工作
* **发现持久化异常并增加超时控制**：使用 iptables 注入网络故障发现持久化静默阻塞问题（该状态可达半个小时），通过 mysql dsn 参数增加读写超时，避免网络故障时无告警、无 fail fast 的卡死

## 个人项目

### 电商秒杀场景中订单库存的性能优化 + 一致性 + 高可用方案
**2025.11 - 2026.03** | **独立开发与设计**

* **技术栈**：Redis / RocketMQ / MySQL / Go / OpenTelemetry / Docker / K8s / gRPC
* **背景**：原版 demo 的下单链路存在数据库直连、缺乏容灾等性能与可靠性瓶颈。
* **目标**：聚焦 Place Order 的改造，实现高并发场景下的高性能、数据最终一致、端到端0数据丢失。
* **结果**：单机 QPS 达到 1.5w，P99 延迟为 6ms（cnb 云开发环境，Redis 1主+1从+1哨兵，主从各1核1G）

**用 Saga 的补偿思想保证业务一致性，用 Write-Behind 异步化保证高性能，用事件驱动实现削峰填谷与故障隔离。**

* **Write-Behind 写后策略**：扣减事件先落 Redis Stream，库存增量落库、订单创建、订单状态更新均异步处理，通过 Redis Stream 和 RocketMQ 的 ack 机制确保消息可靠消费
* **Lua 幂等 + 原子扣减 + 事件记录**：完成幂等检查 -> 库存校验 -> 扣减 -> 写去重标记 -> 同时写库存/订单双 Stream，全程原子无竞态，热路径零 DB 访问
* **Forwarder 可靠转发订单记录**：Redis Stream -> RocketMQ 通过 ack 机制确保有效转发，转发失败不 ack
* **Pending 消息补偿消费**：定时扫描 Redis Stream 消费情况，XCLAIM 夺取长时间未 ack 消息的处理权，重新落库/转发
* **(同步)事件驱动更新**：库存扣减成功触发支付 rpc，支付成功后触发 PENDING 订单状态更新事件，发送到 RocketMQ
* **“未支付”订单对账**：CleanupWorker 捞取长时间 PENDING订单，查询支付状态。支付失败自动取消并触发库存回滚，支付成功则更新状态并触发发货
* **“未发货”订单补偿**：ShippingRecoverWorker 定时扫描支付后长时间未发货订单，重试发货
* **降级策略与死信队列兜底**：
  * 通过批量转发到 MQ / 写 MySQL 提升性能，批量失败则降级为逐条处理。防重复的幂等设计见下条
  * Redis Stream 和 RocketMQ 中多次消费失败的消息/事件移动到死信队列，防止被毒丸消息堵塞
  * 定期将死信队列消息持久化到 DB，交由人工处理
* **下游 MySQL 幂等设计，防止重复扣库存 / 生成订单 / 回滚**：
  * 库存落库前查扣减日志过滤已处理消息，日志与库存更新同事务提交
  * 订单创建靠 order_id 主键唯一约束，捕获 1062 错误视为幂等成功
  * 订单状态更新用 `WHERE status < ?` 条件更新，防止状态回滚（如已发货被更新为未支付）

## 一、Go 语言基础

### 1. slice 和 array 有什么区别？slice 的底层数据结构是什么？（8-31 Q9/Q10，答"不知道"）

**区别**：

* array 是**定长**的，长度是类型的一部分（`[3]int` 和 `[4]int` 是不同类型）；slice 是**变长**的。
* array 是**值类型**，赋值/传参会**整体拷贝**；slice 是对底层数组的封装，赋值/传参只拷贝切片头。
* slice 可以 append 扩容，array 不行。

**slice 底层结构**（`runtime.SliceHeader`）：

```go
type SliceHeader struct {
    Data uintptr // 指向底层数组的指针
    Len  int     // 当前长度
    Cap  int     // 容量
}
```

* 多个 slice 可能**共享同一个底层数组**，修改互相可见。
* `append` 超过 cap 时触发扩容：分配新数组、拷贝旧数据，此后不再共享旧数组。
* 扩容规则（Go 1.18+）：cap < 256 时翻倍；更大时按约 1/4 平滑增长，再按内存规格对齐。

### 2. 向已关闭的 channel 写数据会怎样？关闭后还能读吗？可以重复关闭吗？（8-31 Q12-15，读取行为没答上来）

| 操作 | 结果 |
|---|---|
| 向已关闭的 channel **发送** | **panic**（send on closed channel） |
| **重复关闭**同一个 channel | **panic** |
| 关闭 **nil** channel | panic |
| 向 **nil** channel 收发 | 永久阻塞 |
| **读取已关闭**的 channel | **可以读**：先读完缓冲区剩余数据，之后永远返回元素零值，`v, ok := <-ch` 的 ok 为 **false** |

判断方式：

```go
v, ok := <-ch
if !ok {
    // channel 已关闭且缓冲区已空
}
```

记忆口诀：**"写关 panic，读关零值 ok=false，只该由发送方关闭，且只关一次"**。

### 3. 多个 defer 的执行顺序？defer 里怎么修改函数返回值？什么是闭包？（8-31 Q18-23，闭包传参答错被纠正）

**执行顺序**：defer 后进先出（**栈结构**），最后注册的最先执行。

**修改返回值**：需要**命名返回值 + 闭包捕获**。

```go
func Func1() (x int) { // 命名返回值
    x = 10
    defer func() { // 闭包捕获 x
        x = 20
    }()
    return // return 先把 x 赋给返回值，再执行 defer，最终返回 20
}
```

原面经代码返回 **10**：`return x` 时 x 的值已拷贝进匿名返回值，defer 改的只是局部变量 x，影响不到返回值。

**闭包**：函数 + 它所引用的外部（词法作用域）变量的组合。闭包捕获的是**变量本身（按引用）**，所以内层函数对外层变量的修改是生效的。

**关键纠正**：defer 修改返回值靠"命名返回值 + 闭包捕获该变量"，**不是把值作为入参传进去**——值传参拿到的是拷贝，改了无效。

### 4. g 在什么情况下会脱离当前 P？（8-31 Q7-8，场景答得含糊）

* **g 阻塞在系统调用上**（文件 IO、cgo 等运行时无法拦截的阻塞）：M 陷入内核，P 与 M 解绑（handoff），交给空闲 M 或新建 M 继续跑其他 g。
* **g 阻塞在 channel / 锁上**：g 被 gopark 挂起放入等待队列，P 继续执行别的 g；g 被唤醒后可能放进全局队列或其他 P 的本地队列（也就换了 P）。
* **网络 IO**：由 netpoller 托管，g 挂起但不占用 M；就绪后重新调度。
* **时间片用尽（约 10ms）/ 协作式抢占点**：g 让出，回到 P 本地队列尾部。

## 二、MySQL

### 5. 什么是聚簇索引？什么是非聚簇索引？（8-31 Q24-25，非聚簇答"不知道"，聚簇答偏）

**聚簇索引**（InnoDB 主键索引）：

* **叶子节点存整行数据**，表本身就是按主键组织的 B+树——"索引即数据"。
* 注意纠正之前的错误答案：非叶子节点存的是**键 + 子节点指针**，不是"指向叶子的指针"，所有数据都在叶子层。

**非聚簇索引 / 二级索引**（普通索引、唯一索引、联合索引）：

* 叶子节点存**索引列的值 + 主键值**（不是数据行地址）。
* 查询需要非索引列时，先在二级索引拿到主键，再回聚簇索引查整行——即**回表**。
* 所以主键要尽量短：二级索引每个叶子都带主键，主键越长二级索引越占空间。

**对比**：MyISAM 全是非聚簇索引，索引和数据文件分离，叶子存数据文件地址指针。

**覆盖索引**：查询的列全部包含在二级索引里，无需回表（`Extra: Using index`）。

### 6. B+树介绍一下（8-31 Q26，答"有但是忘了"）

* 非叶子节点只存**键 + 子节点指针**，不存数据 → 单个 16KB 页能放更多键 → 树非常矮（千万级数据约 3~4 层）→ 一次查询只需 3~4 次磁盘 IO。
* 所有数据都在叶子节点，且叶子间**双向链表**串联 → **范围查询、排序、分页**极高效（定位起点后顺链表扫）。
* 对比 B 树：B 树数据分散在所有节点，范围查询要中序回溯，且单页容纳键更少、树更高。
* 对比哈希索引：哈希不支持范围查询和排序。
* 对比二叉树/红黑树：层高太深，磁盘 IO 次数过多。

### 7. 数据库有哪几种隔离级别？（8-31 Q29，答"4 种，记不太清了"）

| 级别 | 问题 |
|---|---|
| 读未提交 RU | 脏读 |
| 读已提交 RC | 不可重复读（事务内两次读同一行结果不同） |
| **可重复读 RR（InnoDB 默认）** | 通过 MVCC + 间隙锁基本解决幻读 |
| 串行化 | 无并发问题，性能最差 |

**顺带补全 MVCC**（8-31 Q28 答了一半）：

* **undo log 版本链 + ReadView**：每行记录有 trx_id 和回滚指针，串成版本链。
* 读时生成 ReadView（活跃事务列表、min/max trx_id、creator_trx_id），沿版本链找对自己可见的版本。
* **RC：每次快照读都生成新的 ReadView**（所以能读到别的事务已提交的新数据）。
* **RR：只在第一次读时生成 ReadView 并复用**（所以可重复读）。

### 8. update 操作如何保证走索引、避免全表扫描？（8-31 Q30-33，连续 4 问没接住）

* update 的本质是：where 定位行 → 改数据 → 写 redo/undo。**where 条件命中索引是效率关键**。
* RR 隔离级别下，走不了索引的 update 会**锁全表记录**（行锁退化），比 select 全表扫描更严重。
* 实践流程：**先看表结构和索引**（`show create table`）→ where 用索引列、遵守最左前缀 → **`explain` 验证**。
* explain 重点看：`type`（ALL 即全表扫描，至少 range/ref）、`key` 是否为预期索引、`rows` 扫描行数、`Extra`。
* 索引失效的坑：对索引列做函数/运算、隐式类型转换（字符串列传数字）、前导模糊 `like '%xx'`、`or` 两侧有无索引列混杂。

**回答模板**："我不会盲目写 update，先看表上有哪些索引，让 where 条件命中它们，再用 explain 确认没有全表扫描。"

## 三、Redis

### 9. Redis 有哪些数据类型？（8-25 Q38-39，只答了 Stream，set 等"没用过"）

| 类型 | 特点 | 典型场景 |
|---|---|---|
| String | 最基础 KV | 缓存、计数器（incr）、分布式锁（setnx） |
| Hash | 字段级读写 | 对象存储，单字段更新（hset/hget） |
| List | 双端链表 | 简单队列、最新列表（lpush/lpop）——**没有 ack，消费即丢** |
| Set | 无序去重集合 | 共同关注（sinter 交集）、抽奖去重、标签（sunion/sdiff） |
| ZSet | 带 score 排序 | 排行榜、延迟队列 |
| **Stream** | 消费组 + ack + pending | 轻量 MQ（你项目的核心用法） |
| Bitmap / HyperLogLog / Geo | 位图 / 基数估算 / 地理位置 | 签到 / UV 估算 / 附近的人 |

顺带熟练自己项目的说法：Stream 相当于 Redis 内置的消息队列，**消费组消费 + ack 确认 + XCLAIM 夺取超时未 ack 消息补偿重试**，这是选它而不是 List 的原因。

### 10. Redis 持久化方式？AOF 重放慢怎么办？（8-31 Q42-47，混合持久化没答出来，面试官给了答案）

**RDB**：

* `bgsave` fork 子进程生成**全量二进制快照**。
* 优点：文件紧凑、恢复快。缺点：两次快照之间宕机丢数据多。

**AOF**：

* 追加写每条写命令，宕机后重放恢复。
* `appendfsync` 三档：**always**（不丢但慢）/ **everysec（最多丢 1 秒，生产常用）** / **no**（交给 OS）。
* 文件会膨胀 → **AOF 重写**（bgrewriteaof）：fork 子进程按当前数据状态生成等价的最小命令集。

**关键点（面试官想听的）**：AOF 重放慢的根治不是优化重放，而是**混合持久化**——

* Redis 4.0+ 开启 `aof-use-rdb-preamble`。
* 重写时先写 **RDB 格式的全量数据**，之后只追加**增量 AOF 命令**。
* 恢复时先快速加载 RDB，再重放一小段 AOF——**恢复快 + 丢数据少**。

**生产实践**：RDB 与 AOF 同时开启 + 主从 + 哨兵/集群。单实例恢复慢的问题靠主从切换兜底。

**挂回项目**："我项目里 Redis 是链路的数据源头所以开了 AOF everysec，能接受最多丢 1 秒，再用 Stream ack + XCLAIM 补偿 + 定时对账兜底，丢的也能补回来。"

### 12. 统计日志里关键字出现的次数？多文件怎么 grep？（8-25 Q34-37、8-31 Q49，两场都没答上）

```bash
grep -c '5xx' access.log        # 统计关键字出现次数（最直接的答案）
grep '5xx' access.log | wc -l   # 等价写法：管道 + wc 计数
grep '5xx' *.log                # 多文件：grep 直接接通配符，不需要 cat |
grep -r '5xx' /var/log/nginx/   # 递归搜整个目录
awk '/5xx/{n++} END{print n}' access.log   # awk 版计数
zgrep '5xx' app.log.gz          # 压缩日志直接搜
```

**关键观念**：**grep 本身就接受多个文件参数**，`cat file | grep` 是冗余写法（useless use of cat）——8-25 面试官就是在纠这个。

**历史中 5xx 出现多少次的完整回答**（8-25 Q34-37 连环追问的标准答案）：

```bash
grep '5xx' /var/log/app/*.log | wc -l
```

## 五、网络协议 / HTTP

### 13. HTTP 也能传 protobuf，为什么还要用 gRPC？（8-31 Q3-4，答"不知道"，面试官提示了双向流）

**传输层基于 HTTP/2**：

* 二进制分帧、**多路复用**（一个 TCP 连接上并发多个请求，解决 HTTP/1.1 的队头阻塞）
* 头部压缩 HPACK
* **双向流 / 全双工**——HTTP/1.1 是一问一答的半双工（面试官提示的就是这一点）

**序列化用 Protobuf**：

* 强 schema 契约 + 代码生成（client/server stub）
* 二进制编码体积小、编解码比 JSON 快

**框架能力**：

* 四种通信模式（unary / client-streaming / server-streaming / bidi）
* deadline 超时传递、取消、拦截器
* **客户端负载均衡（resolver + balancer，实习项目在用）**、健康检查

**反驳坑点**："HTTP 也能传 protobuf"——对，但裸 HTTP/1.1 传 protobuf 只是省了序列化体积，**得不到流式、多路复用和框架生态**。

**收尾**：对外开放 API、浏览器直连、调试友好场景仍然用 REST。

### 14. 客户端发起一个 gRPC 请求到收到响应的全流程？（补充）

以 Unary 为例，按顺序九步：

1. **调用 stub**：客户端调用 protoc 生成的 stub 方法（传 ctx + 请求 struct）。
2. **拦截器链**：先过客户端一元拦截器（metadata、auth、日志、tracing 注入）。
3. **序列化**：请求 struct → protobuf Marshal → 二进制 bytes。
4. **选连接（负载均衡）**：ClientConn 内部，**resolver** 把服务名解析成地址列表，**balancer** 从中选出一个 subconn（如 round_robin）。
5. **构造 HTTP/2 请求**：按 gRPC 规范 path = `/{package}.{Service}/{Method}`；HEADERS 帧（`:method: POST`、`content-type: application/grpc`、`te: trailers`、`grpc-timeout` 等）+ 消息体前 5 字节前缀（1 字节压缩标志 + 4 字节长度）+ DATA 帧。
6. **传输**：所有帧在同一条 HTTP/2 长连接上按 stream **多路复用**，头部经 HPACK 压缩。
7. **服务端接收**：Server 按 path 路由到对应 handler（server stub）→ 过服务端拦截器 → 反序列化 bytes → struct → 调用用户实现的业务方法。
8. **响应返回**：响应 struct 序列化 → DATA 帧发回，随后发送 **Trailers**（HEADERS 帧：`grpc-status` / `grpc-message`）标志调用结束。
9. **客户端收尾**：反序列化响应，grpc-status = 0 返回结果，否则返回 status.Error；deadline 超时 / ctx 取消则中断 stream。

**记忆主线**：stub → 拦截器 → 序列化 → resolver/balancer 选连接 → HTTP/2 帧多路复用 → 服务端路由 → 反序列化执行 → 响应 + Trailers 状态。

### 15. gRPC 框架自带（客户端）负载均衡的缺陷？（补充）

gRPC 原生是**客户端负载均衡**（resolver + balancer，实习项目在用的机制），缺陷：

1. **N×M 连接放大**：每个客户端都要与每个后端实例建长连接，两端实例数大了以后连接数爆炸，后端 fd/内存压力大。
2. **服务发现耦合**：客户端必须能访问注册中心/控制面——DNS 解析性能差且不实时；xDS 方案依赖 Envoy 控制面，且各语言生态成熟度不齐；自建 resolver 要自己处理推送实时性、全量/增量更新。
3. **只是"请求数均衡"，不是真正的"负载均衡"**：round_robin 只轮询请求数，不考虑后端实际负载和请求处理耗时差异，慢节点照样分到等量请求。
4. **故障放大 / 重连风暴**：后端抖动时所有客户端同时感知、同时重连重试，容易雪崩，缺少集中式收敛和保护。
5. **策略变更要升级客户端**：限流、熔断、灰度等治理逻辑分散在每个客户端进程里，不能像网关那样集中调整。
6. **安全边界弱**：后端地址列表对每个客户端可见，客户端可以绕过均衡直连任意后端。

**对比与收尾**：

* **服务端 L7 代理**（Envoy/Nginx 转发）：集中治理、客户端零成本，代价是多一跳延迟、代理自身要扩容。
* **L4 负载均衡 + gRPC 有经典坑**：HTTP/2 长连接多路复用，少量连接承载全部流量，连接级均衡会导致流量严重不均——这正是很多团队选 L7 代理或客户端 LB 的原因。
* **挂回实习**："我们选 resolver+balancer 是因为内网环境、receiver 实例数可控，客户端 LB 省掉代理一跳，配合探活重连和故障切换，维护成本可接受。"

### 16. gRPC 的 keep-alive 配置（补充，挂回实习的"探活重连"）

**作用**：基于 HTTP/2 的 PING 帧做**应用层探活**，解决两个问题——

* **半开连接检测**：对端进程崩溃、网络分区、NAT/防火墙把空闲连接悄悄掐掉后，客户端无感知，下一次 RPC 会一直挂到超时。keep-alive 主动 ping，**fail fast** 发现连接死了，触发重连。
* 为什么不用 TCP keepalive：OS 默认 2 小时才探测且探测的是 TCP 层，**检测不到应用层假死**，且中间设备行为不可控；HTTP/2 PING 是应用层、时间可控。

**客户端配置**（`keepalive.ClientParameters`）：

```go
kacp := keepalive.ClientParameters{
    Time:                10 * time.Second, // 连接空闲超过 Time 发一次 PING
    Timeout:             5 * time.Second,  // PING 后 Timeout 内没收到 ACK → 判定连接死亡，关闭重建
    PermitWithoutStream: true,             // 没有活跃 RPC 的空闲连接也发 PING（默认 false！
                                           // 不开的话空闲连接根本不探测，等于白配）
}
grpc.NewClient(addr, grpc.WithKeepaliveParams(kacp))
```

**服务端配置**（`keepalive.ServerParameters` + `EnforcementPolicy`）：

```go
ks := keepalive.ServerParameters{
    MaxConnectionIdle:     5 * time.Minute,  // 空闲超过该时长，服务端主动 GOAWAY 关连接
    MaxConnectionAge:      30 * time.Minute, // 连接最长寿命，到期强制重建
    MaxConnectionAgeGrace: 10 * time.Second, // 关闭前给在途请求的宽限期
    Time:                  30 * time.Second, // 服务端侧空闲探测 ping 周期
    Timeout:               10 * time.Second, // 服务端等 PING ACK 的超时
}
kep := keepalive.EnforcementPolicy{
    MinTime:             10 * time.Second, // 允许客户端的最小 ping 间隔
    PermitWithoutStream: true,
}
grpc.NewServer(grpc.KeepaliveParams(ks), grpc.KeepaliveEnforcementPolicy(kep))
```

**默认值**：客户端 Time 默认 infinity（**默认不发 ping，必须显式配置**）、Timeout 20s；服务端 Time 默认 2h、Timeout 20s；Enforcement MinTime 默认 5 分钟。

**经典坑（能说出这个就超过大多数人）**：

* **`too_many_pings`**：客户端 Time 配得比服务端 Enforcement 的 MinTime 还短，且无活跃 stream 时，服务端发 GOAWAY（ENHANCE_YOUR_CALM）踢连接 → 现象是"连接莫名其妙反复断"。**原则：服务端 MinTime ≤ 客户端 Time**。
* **PermitWithoutStream 忘了开**：探针场景是周期性上报，两次上报之间连接是空闲无 stream 的，不开这个参数 keepalive 完全不生效。
* **MaxConnectionAge 是负载再均衡的利器**：长连接一旦建成就一直跑在同一后端，后端扩容后老连接不会迁移；定期强制重建连接能让 balancer 重新分配。

**挂回实习**："probe 和 receiver 之间是长连接，探活重连就是靠 keepalive 快速发现半开连接 + gRPC 自带的 reconnect backoff 自动重连；另外混沌测试里 kill receiver 验证过客户端能在 keepalive 超时内感知并切换到其他 receiver 实例。"

### 17. GET/POST/HEAD 等方法的使用场景？POST 能删数据吗？（8-31 Q54-56，HEAD 说不准，POST 删数据方向答反）

* **GET**：读取数据，安全且幂等。
* **POST**：提交数据/触发处理，非幂等。
* **PUT**：全量替换，幂等；**PATCH**：部分更新。
* **DELETE**：删除，幂等。
* **HEAD**：与 GET 相同但**不返回 body**，用于**探测资源是否存在、获取元信息**（Content-Length、Last-Modified），不是"调试用"。
* **OPTIONS**：CORS 预检。

**POST 删数据**（8-31 Q56 答反的点）：

* **功能上完全可以**——handler 是自己实现的，服务端想怎么处理都行。
* **只是规范/语义上**不该这么用（POST 表示"非幂等的创建/提交"语义）。
* 面试时方向别答反：先说"功能上可以，规范上不推荐"。

### 18. merge 和 rebase 的区别？冲突了怎么解决？（8-31 Q59-61，区别只答"历史干净"，冲突流程没答上）

**区别**：

* **merge**：新建一个 merge commit，保留真实分支历史，历史呈网状。
* **rebase**：把本分支提交"摘下来"逐个重放到目标分支顶端，历史**线性干净**。
* 注意：rebase **改写了 commit**，已 push 的公共分支禁止 rebase（需 force push，危险）。
* **两者都会产生冲突**，冲突解决流程完全一样（8-31 Q60 自己也说混了）。

**冲突解决流程（背下来）**：

```bash
# 把 master 同步进自己的 feature 分支（本地）
git checkout feature
git fetch origin
git merge origin/master        # 或 git rebase origin/master

# 冲突时：手动编辑冲突文件，处理 <<<<<<< ======= >>>>>>> 标记
git add <resolved-files>
git commit                     # merge 场景
git rebase --continue          # rebase 场景；放弃则 git rebase --abort
```

**团队规范**：自己分支合入主干用 rebase/squash 保持历史干净；主干只允许 PR + merge；有冲突找相关同事一起确认业务逻辑归属。

# Redis

> 定位：Redis 后端高频面试题，按「问题 → 准确答案」组织。
> 标记：`[必会]` 必须脱口而出；`[高频]` 能说清结论和支撑点；`[加分]` 被追问时能答。

## [必会] 1. Redis 为什么快？是单线程还是多线程？

- **结论**：Redis 基于内存、IO 多路复用和高效数据结构，命令执行是单线程；6.0 起网络 IO 可多线程，但命令执行仍单线程。

- **关键点**
  1. 纯内存操作，避免磁盘 IO。
  2. IO 多路复用：单线程用 epoll 管理大量连接，不需要为每个连接阻塞等待。
  3. 单线程执行命令：无锁竞争、无上下文切换，命令天然原子。
  4. 高效数据结构：SDS、listpack、quicklist、跳表、渐进式 rehash。
  5. Redis 6.0：IO 线程负责网络读写，命令执行仍由主线程串行；默认关闭，用 `io-threads` 开启。
  6. Redis 7.0：`UNLINK`、lazy-free、AOF fsync 等部分任务交给后台线程。

- **常见追问**
  - **单线程为什么能扛高并发？** 瓶颈通常在网络和内存，不在 CPU；命令本身是 O(1)/O(logN) 的内存操作。
  - **单线程的缺点？** 一个慢命令（`KEYS`、大集合操作）会阻塞所有请求，需避免 O(N) 命令。
  - **6.0 多线程会破坏原子性吗？** 不会，IO 线程只负责收发，命令执行仍单线程。

## [必会] 2. Redis 有哪些数据类型？分别适合什么场景？

- **结论**：5 种基础类型是 String、List、Hash、Set、ZSet，另有 Bitmap、HyperLogLog、Geo、Stream。

- **关键点**
  1. String：缓存、计数器、分布式锁、Session；`INCR` 原子自增。
  2. List：消息队列（`LPUSH`/`BRPOP`）、时间线、栈/队列。
  3. Hash：对象存储、购物车；可单字段更新，省内存。
  4. Set：去重、标签、共同好友（`SINTER`）、抽奖（`SRANDMEMBER`）。
  5. ZSet：排行榜、延迟队列、带权重集合；跳表 + 字典。
  6. 扩展：Bitmap 签到；HyperLogLog 做 UV 基数统计；Geo 附近的人；Stream 支持消费组的消息队列。

- **对比**

  | 类型 | 底层 | 典型场景 |
  |---|---|---|
  | String | SDS | 缓存、计数、锁 |
  | List | quicklist | 队列、时间线 |
  | Hash | listpack / hashtable | 对象、购物车 |
  | Set | intset / listpack / hashtable | 去重、交并差 |
  | ZSet | listpack / skiplist + dict | 排行榜、延迟队列 |

- **常见追问**
  - **String 和 Hash 存对象怎么选？** 需要整体读写、频繁过期用 String；需要单字段更新、字段较多用 Hash。
  - **List 做消息队列有什么问题？** 无 ACK、无消费组、无持久化保证，可靠队列用 Stream 或专业 MQ。
  - **HyperLogLog 精确吗？** 不精确，标准误差约 0.81%，只适合 UV 估算。

## [必会] 3. 各数据类型的底层编码是什么？

- **结论**：Redis 按数据量和元素大小在紧凑编码与标准结构间切换；7.0 后用 listpack 取代 ziplist。

- **关键点**
  1. String：`int`（整数）、`embstr`（≤44 字节，一次分配）、`raw`（>44 字节）。
  2. List：`listpack`（小数据）、`quicklist`（listpack 组成的双向链表）。
  3. Hash：`listpack`（字段少且值小）、`hashtable`。
  4. Set：`intset`（全整数）、`listpack`（7.2+ 小集合）、`hashtable`。
  5. ZSet：`listpack`（小集合）、`skiplist + dict`（跳表保证有序，字典保证 O(1) 查分值）。
  6. 阈值可配：`*-max-listpack-entries`、`*-max-listpack-value`，默认 Hash/ZSet 为 128 项、单值 64 字节。

- **常见追问**
  - **为什么小数据用 listpack？** 连续内存、无指针开销、缓存友好，省内存。
  - **ZSet 为什么用跳表不用红黑树？** 实现简单、范围查询方便、插入和并发表现好。
  - **编码会来回转换吗？** 超过阈值后单向升级为 hashtable/skiplist，通常不回退，除非重建。

## [必会] 4. Redis 为什么用 SDS 而不是 C 字符串？

- **结论**：SDS 记录长度和容量，做到 O(1) 取长度、二进制安全、预分配和惰性释放，规避 C 字符串的缺陷。

- **关键点**
  1. 结构：`len`（已用长度）、`alloc`（容量）、`flags`（类型）、`buf[]`。
  2. O(1) 长度：C 字符串 `strlen` 是 O(N)。
  3. 二进制安全：按 `len` 判断结尾，可存 `\0`，适合图片、序列化数据。
  4. 防溢出：追加前检查容量并扩容，C 字符串 `strcat` 可能越界。
  5. 预分配：`len < 1MB` 翻倍；`len >= 1MB` 每次多分配 1MB。
  6. 惰性释放：缩短时不立即回收，保留空间复用。
  7. 兼容 C：末尾仍补 `\0`，可复用部分 C 字符串函数。

- **常见追问**
  - **embstr 和 raw 区别？** embstr 把 SDS 和 redisObject 一次分配、只读；修改时转为 raw。
  - **预分配会浪费内存吗？** 会略多占，但显著减少 realloc 次数。
  - **SDS 是二进制安全的，为什么还要末尾补 `\0`？** 方便直接复用 C 的字符串打印和部分函数。

## [必会] 5. Redis 过期键怎么删除？内存满了怎么淘汰？

- **结论**：过期键用惰性删除 + 定期删除；内存达到 `maxmemory` 后按 8 种淘汰策略淘汰。

- **关键点**
  1. 惰性删除：访问 key 时检查是否过期，过期则删除。
  2. 定期删除：每 100ms 随机抽查，过期比例超过 25% 则继续抽查，避免漏删。
  3. 淘汰触发：`used_memory > maxmemory`。
  4. 8 种策略：`noeviction`；`allkeys-lru/lfu/random`；`volatile-lru/lfu/random/ttl`。
  5. 近似 LRU：采样若干 key，淘汰最久未用的；LFU（4.0）按访问频率淘汰。
  6. 默认 `noeviction`：写命令返回 OOM 错误，读命令正常。

- **对比**

  | 策略 | 范围 | 说明 |
  |---|---|---|
  | noeviction | 不淘汰 | 写入报错 |
  | allkeys-lru / lfu | 所有 key | 按最近/最频繁使用淘汰 |
  | allkeys-random | 所有 key | 随机淘汰 |
  | volatile-lru / lfu / random / ttl | 仅设过期时间的 key | 按对应维度淘汰 |

- **常见追问**
  - **惰性删除能保证过期键立即释放吗？** 不能，未被访问的过期键会占用内存，靠定期删除兜底。
  - **LRU 是精确的吗？** 不是，采样近似；`maxmemory-samples` 越大越精确。
  - **LFU 适合什么场景？** 访问频率差异大、想保留长期热点的场景。

## [必会] 6. RDB、AOF、混合持久化的区别？生产怎么选？

- **结论**：RDB 是快照，恢复快但可能丢数据；AOF 记命令，丢数据少但文件大、恢复慢；混合持久化兼顾两者。

- **关键点**
  1. RDB：`BGSAVE` fork 子进程，利用 COW 生成二进制快照；体积小、恢复快；两次快照之间宕机会丢数据。
  2. AOF：追加写命令；`appendfsync` 决定刷盘；文件大，需要重写；恢复要重放命令。
  3. 混合（4.0）：AOF 重写时前半部分写 RDB、后半部分追加增量命令；重启先加载 RDB 再重放增量。
  4. 选择：能容忍分钟级丢失用 RDB；要求秒级可靠用 AOF `everysec`；生产常用混合。
  5. fork 代价：数据量大时 fork 和 COW 会带来内存与延迟抖动。

- **对比**

  | 维度 | RDB | AOF | 混合 |
  |---|---|---|---|
  | 数据安全 | 低 | 高 | 高 |
  | 恢复速度 | 快 | 慢 | 较快 |
  | 文件体积 | 小 | 大 | 中 |
  | 性能影响 | fork 抖动 | 持续写盘 | 重写时抖动 |

- **常见追问**
  - **COW 是什么？** fork 后父子进程共享内存页，写时复制，读多写少时开销小。
  - **RDB 会阻塞主线程吗？** `BGSAVE` 只在 fork 瞬间阻塞；`SAVE` 会全程阻塞。
  - **AOF 和 RDB 同时开启用哪个恢复？** 优先用 AOF，因为数据更全。

## [必会] 7. AOF 重写的原理？appendfsync 三种策略怎么选？

- **结论**：AOF 重写用 fork 子进程按当前数据生成最小命令集，主进程期间的新写入进重写缓冲，完成后合并替换。

- **关键点**
  1. 触发：`auto-aof-rewrite-percentage` + `auto-aof-rewrite-min-size`；或手动 `BGREWRITEAOF`。
  2. 流程：fork 子进程 → 子进程遍历内存写新 AOF → 主进程新命令写 AOF 缓冲 + 重写缓冲 → 子进程完成，主进程追加重写缓冲 → 原子替换旧文件。
  3. `appendfsync always`：每条命令 fsync，最安全、性能最差。
  4. `everysec`：每秒 fsync，最多丢 1 秒，默认推荐。
  5. `no`：交给 OS，性能最好，宕机丢数据最多。
  6. 写放大：重写缓冲过大时可能阻塞主线程，可用 `no-appendfsync-on-rewrite` 缓解。

- **常见追问**
  - **重写会阻塞吗？** fork 瞬间阻塞；子进程工作不阻塞；缓冲合并可能有抖动。
  - **为什么重写不直接复用旧 AOF？** 旧文件包含冗余命令和已删除数据，重写才是最小集合。
  - **重写失败怎么办？** 旧 AOF 保留可用，记录错误后重试。

## [必会] 8. 缓存穿透、击穿、雪崩的区别和解决方案？

- **结论**：穿透是查不存在的数据，击穿是热点 key 失效，雪崩是大量 key 同时失效或实例故障；三者都要在缓存层和 DB 层做保护。

- **对比**

  | 问题 | 特征 | 方案 |
  |---|---|---|
  | 穿透 | 大量查不存在的 key，绕过缓存打 DB | 布隆过滤器、缓存空值、参数校验 |
  | 击穿 | 单个热点 key 过期瞬间大量请求回源 | 互斥锁/单飞、逻辑过期、热点不过期 |
  | 雪崩 | 大量 key 同时过期或实例故障 | 过期时间随机、多级缓存、高可用、限流降级 |

- **关键点**
  1. 穿透：布隆过滤器拦截不存在的 key；缓存空值设短 TTL；接口层做参数合法性校验。
  2. 击穿：重建缓存加分布式锁，只放一个请求回源；或逻辑过期后台异步刷新；热点 key 不设过期。
  3. 雪崩：过期时间加随机抖动；哨兵/Cluster 保证高可用；本地缓存兜底；限流熔断保护 DB。

- **常见追问**
  - **布隆过滤器会误判吗？** 会误判存在（假阳性），不会漏判；标准实现不支持删除。
  - **逻辑过期怎么实现？** value 里带过期时间但不设 TTL，读到逻辑过期时异步刷新并先返回旧值。
  - **缓存空值会占内存吗？** 会，需设较短 TTL，并防止大量随机 key 攻击。

## [必会] 9. 如何保证缓存和数据库的一致性？

- **结论**：常用 Cache Aside：读 miss 回填，写先更新 DB 再删除缓存；只能做到最终一致，强一致需要加锁或分布式事务。

- **关键点**
  1. 读流程：缓存命中直接返回；miss 查 DB 后回填缓存。
  2. 写流程：先更新 DB，再删除缓存；删除而非更新，避免并发写覆盖。
  3. 并发问题：删除缓存后、读请求回填前，旧值可能被重新写回。
  4. 延迟双删：更新 DB 前删一次，更新后延迟几百 ms 再删一次。
  5. 最终一致：订阅 binlog（Canal）异步删缓存，解耦且可补偿。
  6. 强一致：缓存和 DB 加分布式锁/事务，代价高，通常不追求。

- **常见追问**
  - **先删缓存再更新 DB 有什么问题？** 删后读请求回填旧值，DB 更新后缓存仍是旧值，脏数据窗口更长。
  - **更新 DB 成功、删缓存失败怎么办？** 重试、消息队列补偿、binlog 订阅，最后靠 TTL 兜底。
  - **延迟双删能彻底解决吗？** 不能，只能降低概率；延迟时间取决于主从同步和业务耗时。

## [必会] 10. 如何用 Redis 实现分布式锁？有哪些坑？

- **结论**：用 `SET key value NX PX ttl` 原子加锁，value 存唯一标识，释放时用 Lua 校验再删；复杂场景用 Redisson。

- **关键点**
  1. 加锁：`SET lock uuid NX PX 30000`，NX 保证互斥，PX 防死锁。
  2. value 唯一：UUID + 线程 ID，标识锁持有者。
  3. 释放：Lua 先比较 value 再 `DEL`，保证「判断 + 删除」原子，避免误删他人锁。
  4. 续期：业务超过 TTL 会提前释放；Redisson 看门狗每 1/3 TTL 续期。
  5. 可重入：Redisson 用 Hash 记录锁计数。
  6. Redlock：多主节点多数派加锁；对时钟和网络要求高，存在争议，强一致场景建议 etcd/ZooKeeper。

- **示例**

  ```lua
  if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
  else
    return 0
  end
  ```

- **常见追问**
  - **为什么不能 `SETNX` 后再 `EXPIRE`？** 两条命令非原子，中间宕机会导致锁永不过期。
  - **主从切换会丢锁吗？** 会，主库加锁后未同步就故障转移，新主无锁；Redlock 或强一致组件规避。
  - **锁超时了业务还没跑完怎么办？** 看门狗续期；TTL 设足够长并保证操作幂等。

## [必会] 11. Redis 主从复制的原理？全量同步和增量同步？

- **结论**：从库用 `PSYNC` 请求同步；首次全量（RDB + 缓冲命令），断线重连按偏移量做增量；复制是异步的。

- **关键点**
  1. 建立连接：从库 `REPLICAOF`，发送 `PSYNC ? -1`。
  2. 全量：主库 `BGSAVE` 生成 RDB，期间写命令进 replication buffer；发送 RDB，从库加载；再发送缓冲命令。
  3. 增量：主库维护 repl_backlog 环形缓冲；从库带 `runid + offset` 重连，offset 在缓冲内则只发缺失部分。
  4. 心跳：主从定期 `PING` / `REPLCONF ACK`，维持连接并检测延迟。
  5. 异步复制：主库写完即返回，不等待从库确认，故障时可能丢未同步数据。

- **常见追问**
  - **全量同步期间主库阻塞吗？** `BGSAVE` 的 fork 瞬间阻塞；传输不阻塞主线程。
  - **repl_backlog 太小会怎样？** 从库 offset 不在缓冲内，退化为全量同步。
  - **复制风暴是什么？** 多从库同时全量同步压垮主库和网络；可用级联复制或错峰。

## [必会] 12. 哨兵（Sentinel）的原理？故障转移流程？

- **结论**：Sentinel 监控主从、判定主观/客观下线、选举 leader 执行故障转移，并把新主地址通知客户端。

- **关键点**
  1. 功能：监控、通知、自动故障转移、配置中心。
  2. 主观下线 SDOWN：单个 Sentinel 在 `down-after-milliseconds` 内收不到心跳。
  3. 客观下线 ODOWN：达到 `quorum` 个 Sentinel 同意。
  4. leader 选举：Sentinel 之间基于 Raft 类投票选出 leader 执行转移。
  5. 选新主：过滤不健康/延迟大的从库，按 `replica-priority`、复制偏移量、runid 排序。
  6. 转移：新主 `REPLICAOF NO ONE`，其他从库指向新主，旧主恢复后降为从库。
  7. 客户端：向 Sentinel 查询主库地址，订阅 `+switch-master` 事件。

- **常见追问**
  - **quorum 和 majority 区别？** quorum 是判定 ODOWN 的票数；执行转移还需 leader 获得多数票。
  - **Sentinel 至少部署几个？** 建议 3 个以上奇数，避免单点和脑裂。
  - **故障转移会丢数据吗？** 异步复制下可能丢未同步的写。

## [必会] 13. Redis Cluster 的原理？槽位和故障转移怎么工作？

- **结论**：Cluster 把数据分成 16384 个槽，按 `CRC16(key) % 16384` 分配；节点用 Gossip 通信，主节点故障后从节点选举接管槽位。

- **关键点**
  1. 槽位：16384 个，`CRC16(key) mod 16384`；客户端收到 `MOVED` 重定向。
  2. hash tag：`{user}:1` 只对 `{user}` 计算，让相关 key 落同一槽。
  3. 节点通信：Gossip 协议，集群总线端口 = 客户端端口 + 10000。
  4. 部署：最少 3 主 3 从，主从复制 + 故障转移。
  5. 故障转移：主观下线 → 客观下线（多数主节点）→ 从节点选举（Raft 类）→ 接管槽位。
  6. 限制：不支持跨槽多 key 操作（除非 hash tag）、不支持多数据库、批量操作需客户端拆分。

- **常见追问**
  - **为什么是 16384 个槽？** 心跳包携带槽位位图，16384 位约 2KB，兼顾分片粒度和通信开销。
  - **MOVED 和 ASK 区别？** MOVED 表示槽已永久迁移；ASK 表示槽正在迁移，临时重定向。
  - **扩容怎么迁移槽？** `CLUSTER SETSLOT` 配合 `MIGRATE` 逐个迁移 key。

## [必会] 14. 大 key 和热 key 有什么问题？怎么发现和解决？

- **结论**：大 key 导致网络阻塞、慢查询和内存不均；热 key 导致单节点 CPU 打满；都要先发现再拆分或分散。

- **关键点**
  1. 大 key：String 值过大（如 >10KB）或集合元素过多（如 >5000）。
  2. 大 key 危害：读写阻塞主线程、网络带宽打满、删除阻塞、集群内存倾斜。
  3. 大 key 发现：`redis-cli --bigkeys`、`SCAN` 抽样、`MEMORY USAGE`、离线 RDB 分析。
  4. 大 key 解决：拆分为多个小 key、压缩、`UNLINK` 异步删除、hash tag 分散、控制集合大小。
  5. 热 key：单个 key 的 QPS 远高于其他 key。
  6. 热 key 危害：单分片 CPU/带宽打满，拖累同节点其他请求。
  7. 热 key 发现：`redis-cli --hotkeys`（LFU）、`MONITOR` 抽样、代理/客户端统计、监控。
  8. 热 key 解决：本地缓存、读写分离、key 加随机后缀分散到多分片、限流降级。

- **常见追问**
  - **UNLINK 和 DEL 区别？** DEL 同步释放，大 key 会阻塞；UNLINK 后台线程异步释放。
  - **热 key 加随机后缀有什么代价？** 读要聚合多份、写要维护多份，适合只读热点。
  - **怎么从源头避免大 key？** 限制集合长度、拆分对象、定期清理、设阈值监控告警。

## [必会] 15. Redis 事务、Lua 脚本、Pipeline 有什么区别？

- **结论**：事务保证命令连续执行不被打断但不支持回滚；Lua 在服务端原子执行可写逻辑；Pipeline 只是批量发送减少 RTT，不保证原子。

- **对比**

  | 维度 | 事务 MULTI/EXEC | Lua 脚本 | Pipeline |
  |---|---|---|---|
  | 原子性 | 执行不被打断，出错不回滚 | 整体原子执行 | 无 |
  | 逻辑能力 | 仅命令入队 | 可判断、循环 | 无，仅批量 |
  | 网络开销 | 入队多次 + 一次 EXEC | 一次 EVAL | 一次批量发送 |
  | 典型场景 | 简单命令组合 | 锁释放、原子逻辑 | 批量读写 |

- **关键点**
  1. 事务：`MULTI` 入队，`EXEC` 执行；`DISCARD` 放弃；`WATCH` 乐观锁，key 被改则 `EXEC` 失败。
  2. 事务不回滚：运行期某条命令出错，其他命令仍执行；语法错误在入队阶段就报错。
  3. Lua：`EVAL` / `EVALSHA`，服务端原子执行；脚本要短，避免阻塞主线程。
  4. Pipeline：客户端缓冲多条命令一次发送、按序返回；不是事务，中间可能插入其他客户端命令。

- **常见追问**
  - **事务能保证原子性吗？** 只能保证命令连续执行不被打断，不能保证全部成功或全部失败。
  - **Lua 脚本太长有什么问题？** 阻塞 Redis 单线程；超时后 `SCRIPT KILL` 只能终止只读脚本。
  - **Pipeline 和事务能一起用吗？** 可以，事务命令也能走 Pipeline，但要注意错误处理。

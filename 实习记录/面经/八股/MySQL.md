# MySQL

> 定位：MySQL 后端高频面试题，按「问题 → 准确答案」组织。
> 标记：`[必会]` 必须脱口而出；`[高频]` 能说清结论和支撑点；`[加分]` 被追问时能答。

## [必会] 1. 为什么用 B+ 树做索引？

- **结论**：B+ 树矮胖、磁盘 IO 少，叶子链表适合范围查询和排序，是最适合磁盘存储的索引结构。

- **关键点**
  1. 非叶子节点只存键 + 子节点指针，不存数据；单页 16KB 能放更多键，树高通常 3~4 层。
  2. 千万级数据一次查询约 3~4 次磁盘 IO。
  3. 数据全在叶子节点，叶子之间双向链表串联，范围查询、排序、分页高效。
  4. 对比 B 树：数据分散在所有节点，范围查询要中序回溯；单页键更少、树更高。
  5. 对比哈希：只支持等值查询，不支持范围查询和排序。
  6. 对比红黑树/二叉树：层高太深，磁盘 IO 次数过多。

- **常见追问**
  - **为什么不是 B 树？** B+ 树非叶子不存数据，扇出更大、树更矮；叶子链表适合范围扫描。
  - **为什么 InnoDB 页默认 16KB？** 平衡单次 IO 数据量和空间利用率。
  - **聚簇索引叶子存什么？** 整行数据；二级索引叶子存索引列 + 主键。

## [必会] 2. 聚簇索引和非聚簇索引的区别？什么是回表？

- **结论**：聚簇索引叶子存整行数据；二级索引叶子存索引列 + 主键，查询非索引列需要回表。

- **关键点**
  1. InnoDB 主键索引即聚簇索引，表按主键组织成 B+ 树，索引即数据。
  2. 二级索引（普通/唯一/联合）叶子存索引列值 + 主键值。
  3. 回表：二级索引拿到主键，再回聚簇索引查整行。
  4. 主键应尽量短：二级索引每个叶子都携带主键，主键越长二级索引越大。
  5. MyISAM 全是非聚簇索引，索引和数据文件分离，叶子存数据文件地址指针。

- **常见追问**
  - **为什么推荐自增主键？** 顺序写入减少页分裂；主键短，二级索引更小。
  - **UUID 主键有什么问题？** 随机写入导致页分裂和碎片；占用空间大。
  - **没有主键时 InnoDB 怎么选聚簇索引？** 第一个非空唯一索引；否则生成 6 字节隐藏 row_id。

## [必会] 3. 什么是覆盖索引？如何避免回表？

- **结论**：查询需要的列全部包含在二级索引中，无需回表；`EXPLAIN` 的 `Extra` 显示 `Using index`。

- **关键点**
  1. 覆盖索引不是一种索引类型，而是查询与索引的匹配状态。
  2. 例：索引 `(a,b)`，`SELECT a,b FROM t WHERE a=?` 可覆盖；`SELECT a,b,c` 需要回表。
  3. 优点：减少回表的随机 IO，提升查询性能。
  4. `SELECT *` 基本无法覆盖；联合索引的列顺序影响覆盖能力。

- **常见追问**
  - **如何判断用了覆盖索引？** `EXPLAIN` 的 `Extra: Using index`。
  - **覆盖索引避免了哪些开销？** 回表随机 IO、聚簇索引查找。
  - **索引下推是什么？** ICP 在存储引擎层用索引条件下推过滤，减少回表；`Extra: Using index condition`。

## [必会] 4. 最左前缀原则是什么？联合索引 (a,b,c) 能命中哪些查询？

- **结论**：联合索引按 `a → b → c` 顺序匹配，查询必须从最左列开始，不能跳过中间列。

- **关键点**
  1. 能命中：`(a)`、`(a,b)`、`(a,b,c)`。
  2. 不能命中：单独 `(b)`、`(c)`、`(b,c)`，因为缺少最左列 `a`。
  3. 范围查询后的列不能继续用于索引定位，但可用于覆盖索引或 ICP 过滤。
  4. 索引列顺序：等值查询列靠前，范围查询列靠后；区分度高的列优先。

- **常见追问**
  - **(a,b,c) 查询 `a=? AND c=?` 能命中吗？** 只能用到 `a`，`c` 不能用于索引定位。
  - **为什么范围查询后面的列失效？** 范围扫描后，后续列在索引中不再全局有序。
  - **(a,b) 和 (b,a) 一样吗？** 不一样，最左前缀不同，适用查询不同。

## [必会] 5. 索引失效的常见场景？

- **结论**：对索引列做函数/运算、隐式类型转换、前导模糊、`OR` 混用无索引列、不满足最左前缀等会导致失效。

- **关键点**
  1. 索引列做函数/运算：`WHERE YEAR(created_at)=2024`、`WHERE id+1=10`。
  2. 隐式类型转换：字符串列传数字、数字列传字符串，转换后无法使用索引顺序。
  3. 前导模糊：`LIKE '%xx'` 失效；`LIKE 'xx%'` 可用。
  4. `OR` 两侧有无索引列混杂：一侧无索引时可能退化为全表扫描。
  5. 不满足最左前缀；范围查询后的列；区分度太低时优化器可能主动放弃索引。
  6. `!=`、`NOT IN`、`IS NOT NULL` 是否失效取决于数据分布和优化器成本。

- **常见追问**
  - **为什么函数会导致失效？** B+ 树按列原值排序，函数结果无序。
  - **隐式转换为什么失效？** 类型转换后无法利用索引的有序性。
  - **如何验证？** `EXPLAIN` 看 `type`、`key`、`rows`。

## [必会] 6. 事务的 ACID 是什么？隔离级别有哪些？

- **结论**：ACID = 原子性、一致性、隔离性、持久性；隔离级别从低到高为 RU、RC、RR、串行化。

- **关键点**
  1. 原子性：undo log 回滚。
  2. 持久性：redo log 刷盘。
  3. 隔离性：锁 + MVCC。
  4. 一致性：由应用逻辑和数据库约束共同保证。
  5. InnoDB 默认隔离级别为 RR。

- **隔离级别**

  | 级别 | 脏读 | 不可重复读 | 幻读 |
  |---|---|---|---|
  | 读未提交 RU | 可能 | 可能 | 可能 |
  | 读已提交 RC | 否 | 可能 | 可能 |
  | 可重复读 RR | 否 | 否 | InnoDB 基本解决 |
  | 串行化 | 否 | 否 | 否 |

- **常见追问**
  - **脏读/不可重复读/幻读的区别？** 脏读读到未提交数据；不可重复读同一行两次结果不同；幻读同一范围两次行数不同。
  - **RR 如何解决幻读？** 快照读用 MVCC；当前读用间隙锁/Next-Key Lock。
  - **为什么很多公司用 RC？** 减少间隙锁、降低死锁概率；RR 是 InnoDB 默认值。

## [必会] 7. MVCC 的实现原理？RC 和 RR 的区别？

- **结论**：MVCC 通过 undo log 版本链 + ReadView 实现快照读；RC 每次读生成新 ReadView，RR 第一次读生成并复用。

- **关键点**
  1. 隐藏字段：`DB_TRX_ID`（最后修改事务）、`DB_ROLL_PTR`（回滚指针）、`DB_ROW_ID`。
  2. undo log 版本链：通过回滚指针串起历史版本。
  3. ReadView：`m_ids`（活跃事务列表）、`min_trx_id`、`max_trx_id`、`creator_trx_id`。
  4. 可见性：`trx_id = creator_trx_id` 可见；`trx_id < min_trx_id` 可见；`trx_id >= max_trx_id` 不可见；在 `m_ids` 中不可见；否则可见。
  5. RC：每次快照读生成新 ReadView；RR：第一次快照读生成并复用。

- **常见追问**
  - **快照读和当前读的区别？** 快照读是普通 `SELECT`；当前读是 `SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`，读最新版本并加锁。
  - **MVCC 能解决幻读吗？** 快照读可以；当前读还需要间隙锁。
  - **长事务有什么问题？** undo log 堆积、版本链过长、影响 purge。

## [必会] 8. MySQL 有哪些锁？行锁、间隙锁、Next-Key Lock 的区别？

- **结论**：按粒度分表锁/行锁；InnoDB 行锁包括记录锁、间隙锁、Next-Key Lock；RR 下默认 Next-Key Lock。

- **关键点**
  1. 表锁：表级 S/X 锁、意向锁 IS/IX。
  2. 行锁：记录锁锁索引记录；间隙锁锁索引区间；Next-Key Lock = 记录锁 + 间隙锁。
  3. 插入意向锁：Insert Intention Lock，插入时对间隙加锁，与间隙锁冲突。
  4. 加锁对象是索引，不是行；where 不走索引会锁大量行甚至全表。
  5. RC 下一般只有记录锁；RR 下默认 Next-Key Lock，用于防幻读。

- **锁类型**

  | 锁 | 作用 |
  |---|---|
  | 记录锁 Record Lock | 锁住单条索引记录 |
  | 间隙锁 Gap Lock | 锁住索引区间，阻止插入 |
  | Next-Key Lock | 记录锁 + 间隙锁 |
  | 插入意向锁 | 插入前对间隙加锁，与间隙锁冲突 |

- **常见追问**
  - **间隙锁的作用？** 防止其他事务在区间插入，解决幻读。
  - **什么情况会锁全表？** where 不走索引；RR 下 update/delete 可能锁所有记录和间隙。
  - **意向锁的作用？** 表级锁与行锁共存，快速判断表中是否有行锁。

## [高频] 9. 什么是死锁？如何排查和避免？

- **结论**：两个或多个事务互相持有对方需要的锁并等待；InnoDB 会检测并回滚代价较小的事务。

- **关键点**
  1. 死锁条件：互斥、持有并等待、不可剥夺、循环等待。
  2. 常见场景：不同顺序更新多行；间隙锁与插入意向锁冲突；唯一键冲突加锁。
  3. 排查：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK`；`information_schema.innodb_trx` 看事务；`performance_schema.data_locks` 看锁。
  4. 避免：固定加锁顺序；缩短事务；减少锁范围；用乐观锁/重试；避免大事务。
  5. 处理：捕获死锁错误（1213），重试事务。

- **常见追问**
  - **InnoDB 怎么检测死锁？** 等待图/DFS 检测环路；也可由 `innodb_lock_wait_timeout` 超时兜底。
  - **死锁和锁等待的区别？** 死锁是循环等待；锁等待是单向等待。
  - **如何减少死锁？** 小事务、固定顺序、索引命中、避免间隙锁。

## [必会] 10. redo log、undo log、binlog 的区别？为什么需要两阶段提交？

- **结论**：redo 保证崩溃恢复，undo 保证回滚和 MVCC，binlog 保证主从复制和归档；两阶段提交保证 redo 与 binlog 一致。

- **日志对比**

  | 日志 | 归属 | 内容 | 作用 |
  |---|---|---|---|
  | redo log | InnoDB | 物理页修改 | 崩溃恢复、持久性 |
  | undo log | InnoDB | 旧版本/回滚信息 | 事务回滚、MVCC |
  | binlog | Server 层 | 逻辑 SQL/行变更 | 主从复制、归档 |

- **两阶段提交**
  1. Prepare：InnoDB 写 redo log，标记 prepare。
  2. 写 binlog。
  3. Commit：redo log 标记 commit。

- **为什么需要**
  - 保证 redo 和 binlog 状态一致；崩溃恢复时判断事务提交还是回滚，避免主从不一致。
  - redo prepare + binlog 完整 → commit；binlog 缺失 → rollback。

- **常见追问**
  - **为什么 binlog 不在引擎层？** binlog 是 Server 层全局日志，跨存储引擎共享。
  - **redo 和 binlog 的顺序？** 先 redo prepare，再 binlog，最后 redo commit。
  - **undo log 什么时候删除？** 事务提交后不一定立即删除；MVCC 需要保留旧版本，由 purge 线程清理。

## [高频] 11. 一条 SQL 的执行流程？update 多了哪些步骤？

- **结论**：连接器 → 解析器 → 优化器 → 执行器 → 存储引擎；update 还要写 undo/redo/binlog 并两阶段提交。

- **查询流程**
  1. 连接器：建连、鉴权、权限缓存。
  2. 解析器：词法/语法分析，生成 AST。
  3. 优化器：选择索引、join 顺序，生成执行计划。
  4. 执行器：调用存储引擎接口，逐行处理。
  5. 存储引擎：InnoDB 查 buffer pool，未命中再读磁盘。

- **update 流程**
  1. 写 undo log，记录旧版本。
  2. 修改 buffer pool 中的数据页。
  3. 写 redo log，标记 prepare。
  4. 写 binlog。
  5. redo log 标记 commit。

- **常见追问**
  - **查询缓存呢？** MySQL 8.0 已彻底废弃。
  - **执行器怎么判断权限？** 表级/字段级权限校验。
  - **update 比 select 多了什么？** undo/redo/binlog、两阶段提交、锁。

## [必会] 12. 如何优化慢查询？EXPLAIN 看哪些字段？

- **结论**：先定位慢 SQL，再看执行计划，最后从索引、SQL、表结构、架构四层优化。

- **关键点**
  1. 定位：慢查询日志 `slow_query_log`、`long_query_time`；`SHOW PROCESSLIST`；APM/监控。
  2. `EXPLAIN` 重点：`type`（ALL 最差，至少 range/ref）、`key`（是否命中索引）、`rows`（扫描行数）、`Extra`（Using filesort/temporary/index condition）。
  3. SQL 优化：避免 `SELECT *`、减少回表、拆分大 SQL、避免函数/隐式转换、深分页优化。
  4. 索引优化：联合索引、覆盖索引、最左前缀、区分度。
  5. 表结构：字段类型、冗余、垂直拆分。
  6. 架构：读写分离、分库分表、缓存。

- **常见追问**
  - **`type` 的常见值？** system/const/eq_ref/ref/range/index/ALL。
  - **`Using filesort` 一定慢吗？** 不一定，但尽量用索引排序。
  - **`count(*)`、`count(1)`、`count(字段)` 区别？** InnoDB 下 `count(*)` 和 `count(1)` 近似；`count(字段)` 不统计 NULL；优先 `count(*)`。

## [高频] 13. 深分页为什么慢？怎么优化？

- **结论**：`LIMIT offset, n` 需要扫描并丢弃 offset 行，offset 越大越慢；用游标、延迟关联或覆盖索引优化。

- **关键点**
  1. 原因：不能直接跳到 offset，必须逐行扫描/回表后丢弃。
  2. 游标分页：`WHERE id > last_id ORDER BY id LIMIT n`，适合连续翻页。
  3. 延迟关联：`SELECT * FROM t JOIN (SELECT id FROM t ORDER BY id LIMIT offset, n) x USING(id)`，先在索引上分页再回表。
  4. 覆盖索引：减少回表。
  5. 业务限制：限制最大页数，或改用搜索/游标。

- **常见追问**
  - **为什么延迟关联有效？** 子查询只查主键，走覆盖索引，减少回表。
  - **游标分页的缺点？** 不能跳页；需要稳定排序字段。
  - **`LIMIT 1000000, 10` 和 `LIMIT 10` 差别？** 前者扫描 1000010 行，后者只扫描 10 行。

## [高频] 14. 主从复制原理？读写分离有什么问题？

- **结论**：主库写 binlog，从库 IO 线程拉取写 relay log，SQL 线程重放；读写分离有延迟和一致性问题。

- **关键点**
  1. 主库：提交事务写 binlog。
  2. 从库 IO 线程：连接主库，拉取 binlog 写入 relay log。
  3. 从库 SQL 线程：重放 relay log。
  4. 复制模式：异步、半同步、组复制；半同步保证至少一个从库收到。
  5. 读写分离：写主库、读从库，提升读吞吐。

- **常见问题**
  - 主从延迟导致读到旧数据。
  - 解决方案：强制走主库、半同步、延迟监控、缓存。

- **常见追问**
  - **主从延迟的原因？** 大事务、从库性能差、网络、单线程重放（MySQL 5.7+ 支持并行复制）。
  - **如何解决延迟？** 并行复制、半同步、读写分离策略、缓存。
  - **主从切换会丢数据吗？** 异步复制可能丢；半同步/组复制降低风险。

## [高频] 15. 为什么要分库分表？分库分表后有哪些问题？

- **结论**：单表数据量过大或单库连接/写入达到瓶颈时拆分；拆分后带来事务、join、分页、ID、路由等问题。

- **关键点**
  1. 触发：单表千万级以上、磁盘/连接/QPS 瓶颈；先优化索引/缓存/读写分离，再考虑拆分。
  2. 垂直拆分：按业务或字段拆库拆表。
  3. 水平拆分：按分片键（user_id/order_id）取模、范围或 hash。
  4. 问题：分布式事务、跨库 join、跨库分页/排序、全局唯一 ID、路由、扩容迁移、聚合统计。
  5. 方案：分片中间件（ShardingSphere）、全局 ID（雪花/号段）、冗余字段、异步汇总、分布式事务（TCC/Saga/事务消息）。

- **常见追问**
  - **分片键怎么选？** 高基数、分布均匀、查询常用；避免热点。
  - **跨库分页怎么做？** 各分片取 `offset+n`，内存归并排序；或游标分页。
  - **扩容怎么迁移？** 成倍扩容、双写迁移、一致性哈希。

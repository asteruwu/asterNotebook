## slice 与 array

- **定义**
  - array：定长序列，长度是类型的一部分（`[3]int` 与 `[4]int` 是不同类型），值类型。
  - slice：变长视图，对底层数组的封装，赋值 / 传参只拷贝切片头。

- **底层结构**
  ```go
  type SliceHeader struct {
      Data uintptr // 指向底层数组
      Len  int     // 当前长度
      Cap  int     // 容量
  }
  ```

- **核心区别**

  | 维度 | array | slice |
  |---|---|---|
  | 长度 | 编译期固定，属于类型 | 动态，可 append 扩容 |
  | 赋值 / 传参 | 整体拷贝 | 只拷贝 SliceHeader |
  | 底层数据 | 自身即数据 | 指向底层数组 |
  | 扩容 | 不支持 | 超过 cap 时分配新数组并拷贝 |

- **共享与扩容**
  - 多个 slice 可共享同一底层数组，修改互相可见。
  - `append` 超过 cap：分配新数组、拷贝旧数据，此后与原数组解耦。
  - Go 1.18+ 扩容：cap < 256 时翻倍；更大时按约 1/4 平滑增长，再按内存规格对齐。

- **易错点**
  - 传 slice 修改元素会影响原数组；但 append 触发扩容后，新 slice 与原数组脱钩。
  - `len` 是当前元素数，`cap` 是从起始位置到底层数组末尾的容量。

## channel 的关闭与读写

- **操作矩阵**

  | 操作 | 结果 |
  |---|---|
  | 向已关闭 channel 发送 | panic: send on closed channel |
  | 重复关闭同一 channel | panic |
  | 关闭 nil channel | panic |
  | 向 nil channel 收发 | 永久阻塞 |
  | 读取已关闭 channel | 先读完缓冲区，之后返回零值；`v, ok := <-ch` 的 ok 为 false |

- **判断关闭**
  ```go
  v, ok := <-ch
  if !ok {
      // channel 已关闭且缓冲区已空
  }
  ```

- **结论**
  - 写关 panic，读关零值 + ok=false。
  - channel 应由发送方关闭，且只关一次。

## defer 与闭包

- **defer 执行顺序**
  - 后进先出（栈结构），最后注册的最先执行。

- **defer 修改返回值**
  - 条件：命名返回值 + 闭包捕获该返回值变量。
  ```go
  func Func1() (x int) {
      x = 10
      defer func() { x = 20 }()
      return // 返回 20
  }
  ```
  - 匿名返回值场景：`return x` 已把值拷贝到返回值槽，defer 修改局部变量不影响返回值。
  - 值传参无效：`defer func(v int) { ... }(x)` 拿到的是拷贝。

- **闭包**
  - 定义：函数 + 其引用的词法作用域变量。
  - 捕获的是变量本身（按引用），内部修改对外部生效。

- **易错点**
  - 修改返回值靠「命名返回值 + 闭包捕获」，不是把值作为参数传入。

## goroutine 与 P 的解绑

- **系统调用阻塞**
  - g 阻塞在文件 IO、cgo 等运行时无法拦截的调用：M 陷入内核，P 与 M 解绑（handoff），交给空闲 M 或新建 M 继续调度其他 g。

- **channel / 锁阻塞**
  - g 被 gopark 挂起放入等待队列，P 继续执行其他 g。
  - 唤醒后可能进入全局队列或其他 P 的本地队列。

- **网络 IO**
  - 由 netpoller 托管，g 挂起但不占用 M；就绪后重新调度。

- **时间片耗尽 / 抢占**
  - 时间片约 10ms；协作式抢占点让出，g 回到 P 本地队列尾部。

- **结论**
  - g 脱离 P 的本质：g 不再处于可运行状态，或 M 与 P 的绑定被解除。

## 聚簇索引与非聚簇索引

- **聚簇索引（InnoDB 主键索引）**
  - 叶子节点存整行数据，表按主键组织成 B+ 树，即「索引即数据」。
  - 非叶子节点只存键 + 子节点指针，所有数据在叶子层。

- **非聚簇索引 / 二级索引**
  - 叶子节点存索引列值 + 主键值，不存行地址。
  - 查询非索引列时，先查二级索引得到主键，再回聚簇索引取整行，即回表。
  - 主键应尽量短：二级索引每个叶子都携带主键。

- **对比 MyISAM**
  - 全部为非聚簇索引，索引与数据文件分离，叶子存数据文件地址指针。

- **覆盖索引**
  - 查询列全部包含在二级索引中，无需回表。
  - `EXPLAIN` 的 `Extra` 显示 `Using index`。

## B+ 树

- **结构**
  - 非叶子节点只存键 + 子节点指针，不存数据。
  - 所有数据在叶子节点，叶子之间用双向链表串联。

- **优势**
  - 单页（16KB）可容纳更多键，树矮：千万级数据约 3~4 层，一次查询约 3~4 次磁盘 IO。
  - 范围查询、排序、分页高效：定位起点后沿叶子链表扫描。

- **对比**

  | 结构 | 特点 |
  |---|---|
  | B 树 | 数据分散在所有节点，范围查询需中序回溯；单页键更少、树更高 |
  | 哈希索引 | 不支持范围查询和排序 |
  | 二叉树 / 红黑树 | 层高太深，磁盘 IO 次数多 |

## 事务隔离级别与 MVCC

- **隔离级别**

  | 级别 | 主要问题 |
  |---|---|
  | 读未提交 RU | 脏读 |
  | 读已提交 RC | 不可重复读 |
  | 可重复读 RR（InnoDB 默认） | 通过 MVCC + 间隙锁基本解决幻读 |
  | 串行化 | 无并发问题，性能最差 |

- **MVCC 组成**
  - undo log 版本链：每行记录含 trx_id 和回滚指针，串成版本链。
  - ReadView：活跃事务列表、min/max trx_id、creator_trx_id。
  - 读取时沿版本链找对当前事务可见的版本。

- **RC 与 RR 的差异**
  - RC：每次快照读都生成新的 ReadView。
  - RR：只在第一次读时生成 ReadView 并复用。

- **易错点**
  - RR 下 MVCC 解决快照读一致性；当前读仍需间隙锁 / Next-Key Lock 防幻读。

## update 走索引与避免全表扫描

- **执行本质**
  - where 定位行 → 修改数据 → 写 redo/undo；where 命中索引是效率关键。

- **锁风险**
  - RR 隔离级别下，走不了索引的 update 会锁全表记录（行锁退化），比 select 全表扫描更严重。

- **排查流程**
  1. `SHOW CREATE TABLE` 查看表结构与索引。
  2. where 使用索引列，遵守最左前缀。
  3. `EXPLAIN` 验证执行计划。

- **EXPLAIN 关注点**
  - `type`：ALL 为全表扫描，至少应达到 range/ref。
  - `key`：是否命中预期索引。
  - `rows`：预估扫描行数。
  - `Extra`：是否出现 Using filesort / Using temporary 等。

- **索引失效场景**
  - 对索引列做函数或运算。
  - 隐式类型转换（字符串列传数字）。
  - 前导模糊 `LIKE '%xx'`。
  - `OR` 两侧存在无索引列。

- **回答模板**
  - 「先看表上有哪些索引，让 where 命中索引，再用 EXPLAIN 确认没有全表扫描。」

# Redis

> 来源：2026-8-25 百度 Q38-39；2026-8-31 百度 Q42-47。

## 数据类型

- **总表**

  | 类型 | 特点 | 典型场景 |
  |---|---|---|
  | String | 最基础 KV | 缓存、计数器（INCR）、分布式锁（SETNX） |
  | Hash | 字段级读写 | 对象存储、单字段更新 |
  | List | 双端链表 | 简单队列、最新列表；无 ack，消费即丢 |
  | Set | 无序去重 | 共同关注（SINTER）、抽奖去重、标签 |
  | ZSet | 带 score 排序 | 排行榜、延迟队列 |
  | Stream | 消费组 + ack + pending | 轻量 MQ |
  | Bitmap / HyperLogLog / Geo | 位图 / 基数估算 / 地理位置 | 签到 / UV 估算 / 附近的人 |

- **Stream 选型理由**
  - 消费组消费 + ack 确认 + XCLAIM 夺取超时未 ack 消息，支持补偿重试。
  - List 没有 ack，LPOP 消费即删除，不适合可靠消息队列。

## 持久化

- **RDB**
  - `BGSAVE` fork 子进程生成全量二进制快照。
  - 优点：文件紧凑、恢复快。
  - 缺点：两次快照之间宕机丢失数据较多。

- **AOF**
  - 追加写每条写命令，宕机后重放恢复。
  - `appendfsync` 三档：

    | 策略 | 特点 |
    |---|---|
    | always | 不丢数据，性能最差 |
    | everysec | 最多丢 1 秒，生产常用 |
    | no | 交给 OS，丢失窗口不可控 |

  - 文件膨胀 → AOF 重写（`BGREWRITEAOF`）：fork 子进程按当前数据状态生成等价最小命令集。

- **混合持久化**
  - Redis 4.0+ 开启 `aof-use-rdb-preamble`。
  - 重写时先写 RDB 格式全量数据，之后追加增量 AOF 命令。
  - 恢复时先加载 RDB，再重放少量 AOF：恢复快 + 丢数据少。
  - AOF 重放慢的根治不是优化重放，而是混合持久化。

- **生产组合**
  - RDB + AOF 同时开启，配合主从 + 哨兵 / 集群。
  - 单实例恢复慢靠主从切换兜底。

- **项目挂载**
  - Redis 作为链路数据源头开启 AOF everysec，最多丢 1 秒。
  - 再用 Stream ack + XCLAIM 补偿 + 定时对账兜底。


# 网络协议与 HTTP

> 来源：2026-8-31 百度 Q3-4、Q54-56；其余为补充。

## gRPC 与 HTTP + protobuf

- **HTTP/2 传输层**
  - 二进制分帧、多路复用：一个 TCP 连接并发多个请求，解决 HTTP/1.1 队头阻塞。
  - HPACK 头部压缩。
  - 双向流 / 全双工；HTTP/1.1 是一问一答的半双工。

- **Protobuf 序列化**
  - 强 schema 契约 + 代码生成（client/server stub）。
  - 二进制编码体积小，编解码快于 JSON。

- **gRPC 框架能力**
  - 四种通信模式：unary / client-streaming / server-streaming / bidi。
  - deadline 超时传递、取消、拦截器。
  - 客户端负载均衡（resolver + balancer）、健康检查。

- **结论**
  - 「HTTP 也能传 protobuf」只省了序列化体积，得不到流式、多路复用和框架生态。
  - 对外开放 API、浏览器直连、调试友好场景仍用 REST。

## gRPC Unary 调用全流程

1. **调用 stub**：客户端调用 protoc 生成的 stub 方法，传入 ctx 与请求 struct。
2. **拦截器链**：经过客户端一元拦截器，注入 metadata、auth、日志、tracing。
3. **序列化**：请求 struct → protobuf Marshal → 二进制 bytes。
4. **选连接**：resolver 将服务名解析为地址列表，balancer 选出 subconn（如 round_robin）。
5. **构造 HTTP/2 请求**：path 为 `/{package}.{Service}/{Method}`；HEADERS 帧携带 `:method: POST`、`content-type: application/grpc`、`te: trailers`、`grpc-timeout`；消息体前 5 字节为 1 字节压缩标志 + 4 字节长度，随后是 DATA 帧。
6. **传输**：所有帧在同一条 HTTP/2 长连接上按 stream 多路复用，头部经 HPACK 压缩。
7. **服务端接收**：按 path 路由到 handler（server stub）→ 服务端拦截器 → 反序列化 → 调用业务方法。
8. **响应返回**：响应 struct 序列化 → DATA 帧；随后发送 Trailers（HEADERS 帧：`grpc-status` / `grpc-message`）标志结束。
9. **客户端收尾**：反序列化响应；`grpc-status = 0` 返回结果，否则返回 `status.Error`；deadline 超时或 ctx 取消则中断 stream。

- **记忆主线**
  - stub → 拦截器 → 序列化 → resolver/balancer 选连接 → HTTP/2 帧多路复用 → 服务端路由 → 反序列化执行 → 响应 + Trailers。

## gRPC 客户端负载均衡的缺陷

- **连接放大**
  - 每个客户端与每个后端实例建长连接，N×M 连接数膨胀，后端 fd / 内存压力大。

- **服务发现耦合**
  - 客户端必须能访问注册中心 / 控制面。
  - DNS 解析性能差且不实时；xDS 依赖 Envoy 控制面，各语言生态成熟度不齐；自建 resolver 需处理推送实时性、全量 / 增量更新。

- **只均衡请求数，不均衡负载**
  - round_robin 只轮询请求数，不考虑后端实际负载与处理耗时，慢节点仍分到等量请求。

- **故障放大 / 重连风暴**
  - 后端抖动时所有客户端同时感知、同时重连重试，容易雪崩，缺少集中式收敛与保护。

- **策略变更需升级客户端**
  - 限流、熔断、灰度等治理逻辑分散在各客户端进程，不能像网关一样集中调整。

- **安全边界弱**
  - 后端地址列表对每个客户端可见，可绕过均衡直连任意后端。

- **对比与选型**
  - 服务端 L7 代理（Envoy/Nginx）：集中治理、客户端零成本，代价是多一跳延迟、代理需扩容。
  - L4 负载均衡 + gRPC 有经典坑：HTTP/2 长连接多路复用，少量连接承载全部流量，连接级均衡会导致流量严重不均。
  - 实习选型：内网环境、receiver 实例数可控，客户端 LB 省掉代理一跳，配合探活重连和故障切换，维护成本可接受。

## gRPC keep-alive

- **作用**
  - 基于 HTTP/2 PING 帧做应用层探活。
  - 检测半开连接：对端进程崩溃、网络分区、NAT / 防火墙掐断空闲连接后，客户端无感知，下一次 RPC 会挂到超时；keep-alive 主动 ping，fail fast 触发重连。
  - 不用 TCP keepalive 的原因：OS 默认 2 小时才探测，且只探测 TCP 层，检测不到应用层假死；HTTP/2 PING 在应用层，时间可控。

- **客户端配置**
  ```go
  kacp := keepalive.ClientParameters{
      Time:                10 * time.Second,
      Timeout:             5 * time.Second,
      PermitWithoutStream: true,
  }
  grpc.NewClient(addr, grpc.WithKeepaliveParams(kacp))
  ```

- **服务端配置**
  ```go
  ks := keepalive.ServerParameters{
      MaxConnectionIdle:     5 * time.Minute,
      MaxConnectionAge:      30 * time.Minute,
      MaxConnectionAgeGrace: 10 * time.Second,
      Time:                  30 * time.Second,
      Timeout:               10 * time.Second,
  }
  kep := keepalive.EnforcementPolicy{
      MinTime:             10 * time.Second,
      PermitWithoutStream: true,
  }
  grpc.NewServer(grpc.KeepaliveParams(ks), grpc.KeepaliveEnforcementPolicy(kep))
  ```

- **默认值**
  - 客户端 Time 默认 infinity（默认不发 ping，必须显式配置），Timeout 20s。
  - 服务端 Time 默认 2h，Timeout 20s。
  - Enforcement MinTime 默认 5 分钟。

- **经典坑**
  - `too_many_pings`：客户端 Time < 服务端 MinTime，且无活跃 stream 时，服务端发 GOAWAY（ENHANCE_YOUR_CALM）踢连接。原则：服务端 MinTime ≤ 客户端 Time。
  - `PermitWithoutStream` 未开启：周期性上报场景两次上报之间无 stream，keepalive 不生效。
  - `MaxConnectionAge` 可用于负载再均衡：定期强制重建连接，让 balancer 重新分配。

- **项目挂载**
  - probe 与 receiver 之间是长连接；探活依赖 keepalive 快速发现半开连接 + gRPC 自带 reconnect backoff 自动重连。
  - 混沌测试中 kill receiver，验证客户端能在 keepalive 超时内感知并切换到其他 receiver 实例。

## HTTP 方法与语义

- **方法语义**

  | 方法 | 语义 | 幂等 |
  |---|---|---|
  | GET | 读取资源 | 是 |
  | POST | 提交数据 / 触发处理 | 否 |
  | PUT | 全量替换 | 是 |
  | PATCH | 部分更新 | 通常否 |
  | DELETE | 删除资源 | 是 |
  | HEAD | 与 GET 相同但不返回 body，用于探测资源是否存在、获取元信息 | 是 |
  | OPTIONS | CORS 预检 | 是 |

- **HEAD**
  - 返回头信息（Content-Length、Last-Modified 等），不返回 body。
  - 用途是探测资源与元信息，不是「调试用」。

- **POST 能否删数据**
  - 功能上可以：handler 由服务端实现，想怎么处理都行。
  - 规范上不推荐：POST 表示非幂等的创建 / 提交语义。
  - 回答顺序：先说「功能上可以」，再说「规范上不推荐」。

- **易错点**
  - 不要把 HEAD 说成「调试方法」。
  - 不要把 POST 删数据直接答成「不可以」。

## merge 与 rebase

- **merge**
  - 新建 merge commit，保留真实分支历史，历史呈网状。
- **rebase**
  - 将本分支提交逐个重放到目标分支顶端，历史线性干净。
  - 改写 commit；已 push 的公共分支禁止 rebase（需 force push，危险）。
- **共同点**
  - 两者都可能产生冲突，冲突解决流程一致。

## 冲突解决流程

```bash
git checkout feature
git fetch origin
git merge origin/master        # 或 git rebase origin/master

# 手动编辑冲突文件，处理 <<<<<<< ======= >>>>>>> 标记
git add <resolved-files>
git commit                     # merge 场景
git rebase --continue          # rebase 场景；放弃则 git rebase --abort
```

- **团队规范**
  - 自己分支合入主干用 rebase/squash 保持历史干净。
  - 主干只允许 PR + merge。
  - 有冲突找相关同事一起确认业务逻辑归属。

# 附：面试表达与项目量化

## 项目数据量化

- **问题**
  - 过往面试被问：转储 QPS、receiver 写 MySQL 的 QPS、最大表行数、线上实例数。
- **准备方式**
  - 提前查好真实数字，或准备可解释的估算逻辑。
  - 不要回答「没统计过」。

## 压测方法论

- **回答结构**
  1. 维度：压什么指标、什么场景。
  2. 方法：工具、流量模型、持续时间。
  3. 数据：QPS、P99、错误率、资源水位。
  4. 决策：根据数据得出扩容 / 调优 / 降级结论。
- **易错点**
  - 避免只讲工具不讲指标，或只给结论不给数据。

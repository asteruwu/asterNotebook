# 计算机网络

> 定位：计算机网络后端高频面试题，按「问题 → 准确答案」组织。
> 标记：`[必会]` 必须脱口而出；`[高频]` 能说清结论和支撑点；`[加分]` 被追问时能答。

## [必会] 1. TCP 三次握手的过程？为什么需要三次而不是两次？

- **结论**：客户端 `SYN(seq=x)` → 服务端 `SYN+ACK(seq=y, ack=x+1)` → 客户端 `ACK(ack=y+1)`；三次是为了双向确认收发能力并同步初始序列号。

- **关键点**
  1. 状态流转：客户端 `CLOSED → SYN_SENT → ESTABLISHED`；服务端 `LISTEN → SYN_RCVD → ESTABLISHED`。
  2. 交换 ISN：双方各自随机选择初始序列号，作为可靠传输和去重的基准。
  3. 三次的必要性：两次只能确认「客户端能发、服务端能收」，无法确认「服务端能发、客户端能收」。
  4. 合并优化：服务端的 `SYN` 和 `ACK` 合并为一个报文，所以三次已经是最小成本。
  5. 第三次 ACK：可以携带数据，前两次不能。

- **对比**

  | 次数 | 确认内容 | 风险 |
  |---|---|---|
  | 两次 | 客户端发送、服务端接收 | 服务端无法确认客户端接收能力；历史 SYN 可能建立无效连接 |
  | 三次 | 双向收发能力 + 双方 ISN | 成本最小，仍无法防止伪造源 IP |

- **常见追问**
  - **ISN 为什么随机？** 避免旧连接的延迟报文被新连接误收，同时增加序列号预测难度。
  - **SYN Flood 怎么攻击？** 伪造源 IP 大量发 SYN，占满半连接队列；防御用 SYN Cookie、调大队列、限流。
  - **第三次握手丢了怎么办？** 服务端超时重传 `SYN+ACK`，客户端收到重复 `SYN+ACK` 后重新回 `ACK`。

## [必会] 2. TCP 四次挥手的过程？为什么 TIME_WAIT 要等 2MSL？

- **结论**：主动方 `FIN` → 被动方 `ACK` → 被动方 `FIN` → 主动方 `ACK`；四次是因为全双工，两个方向要各自关闭；`TIME_WAIT` 等 2MSL 保证最后一个 ACK 能重传、旧报文能消散。

- **关键点**
  1. 状态流转：主动方 `FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED`；被动方 `CLOSE_WAIT → LAST_ACK → CLOSED`。
  2. 四次的原因：被动方收到 `FIN` 后先回 `ACK`，等自己数据发完再发 `FIN`，两个报文不能合并。
  3. 2MSL 作用一：最后一个 `ACK` 丢失时，被动方会重传 `FIN`，主动方还能在 `TIME_WAIT` 内重新应答。
  4. 2MSL 作用二：让本次连接的残留报文在网络中过期，避免干扰使用相同四元组的新连接。
  5. 谁先关闭谁进入 `TIME_WAIT`；服务端主动关闭时由服务端承担。

- **对比**

  | 状态 | 出现方 | 含义 |
  |---|---|---|
  | TIME_WAIT | 主动关闭方 | 等待 2MSL，处理重传并消散旧报文 |
  | CLOSE_WAIT | 被动关闭方 | 已收到 FIN，但应用还没调用 close |

- **常见追问**
  - **为什么是 2MSL 而不是 1MSL？** 一来一回：ACK 到对端最多 1MSL，对端重传的 FIN 再回来最多 1MSL。
  - **大量 CLOSE_WAIT 说明什么？** 被动方代码没有正确关闭连接，通常是连接或资源泄漏。
  - **TIME_WAIT 过多怎么处理？** 调 `tcp_tw_reuse`、扩大端口范围、用长连接减少短连接；不建议随意开 `tcp_tw_recycle`。

## [必会] 3. TCP 如何保证可靠传输？

- **结论**：靠序列号 + 确认应答 + 超时重传 + 快速重传 + 校验和 + 滑动窗口，接收方按序号去重和重排。

- **关键点**
  1. 序列号：每个字节编号，接收方按序重组，重复报文直接丢弃。
  2. 累计确认：ACK 表示「该序号之前全部收到」，丢失时后续 ACK 会重复。
  3. 超时重传：RTO 由 RTT 动态估算（RTT 平滑 + 偏差），超时未确认就重发。
  4. 快速重传：收到 3 个重复 ACK 立即重传，不等 RTO 到期。
  5. 校验和：覆盖首部和数据，检测传输中的比特错误。
  6. 滑动窗口：窗口内的数据可连续发送，兼顾吞吐和接收方缓冲。

- **常见追问**
  - **快速重传和超时重传怎么选？** 能收到重复 ACK 说明网络仍通，优先快速重传；完全无响应才等超时。
  - **SACK 解决什么问题？** 选择性确认，告诉发送方缺的是哪几段，避免重传已收到的数据。
  - **重传后 RTT 怎么算？** Karn 算法：重传报文不采样 RTT，避免 ACK 归属不清。

## [必会] 4. 流量控制和拥塞控制有什么区别？拥塞控制有哪些阶段？

- **结论**：流量控制防止发送方压垮接收方，靠接收窗口 `rwnd`；拥塞控制防止压垮网络，靠拥塞窗口 `cwnd`；实际发送窗口取两者较小值。

- **关键点**
  1. 流量控制：接收方通过窗口字段通告可接收量；窗口为 0 时发送方发零窗口探测。
  2. 慢启动：`cwnd` 从 1 MSS 开始，每个 RTT 翻倍，指数增长到 `ssthresh`。
  3. 拥塞避免：超过 `ssthresh` 后每个 RTT 加 1 MSS，线性增长。
  4. 快重传：3 个重复 ACK 立即重传丢失段。
  5. 快恢复：重传后 `ssthresh` 和 `cwnd` 减半，进入拥塞避免，不回到慢启动。
  6. 超时处理：超时判定为严重拥塞，`cwnd` 回 1，重新慢启动。
  7. 现代算法：Linux 默认 CUBIC；BBR 基于带宽和 RTT 建模，不依赖丢包信号。

- **对比**

  | 维度 | 流量控制 | 拥塞控制 |
  |---|---|---|
  | 保护对象 | 接收方缓冲区 | 网络链路 |
  | 控制信号 | 接收窗口 rwnd | 丢包、延迟、ECN |
  | 作用位置 | 接收方通告，发送方遵守 | 发送方自主调整 |
  | 典型机制 | 滑动窗口、零窗口探测 | 慢启动、拥塞避免、快重传/快恢复 |

- **常见追问**
  - **发送窗口怎么定？** 取 `min(cwnd, rwnd)`，还要受发送缓冲和 MSS 约束。
  - **慢启动为什么叫「慢」？** 初始窗口小，但每 RTT 翻倍，实际增长很快。
  - **BBR 和 CUBIC 的区别？** CUBIC 以丢包为拥塞信号；BBR 主动探测带宽和最小 RTT，在高丢包链路上表现更好。

## [必会] 5. TCP 和 UDP 有什么区别？分别适合什么场景？

- **结论**：TCP 面向连接、可靠、字节流、有流量和拥塞控制；UDP 无连接、不可靠、面向报文、开销小、延迟低。

- **对比**

  | 维度 | TCP | UDP |
  |---|---|---|
  | 连接 | 三次握手建立，四次挥手关闭 | 无连接，直接发送 |
  | 可靠性 | 确认、重传、排序、去重 | 不保证送达、不保证顺序 |
  | 传输单位 | 字节流，无消息边界 | 数据报，保留消息边界 |
  | 控制机制 | 流量控制、拥塞控制 | 无 |
  | 头部大小 | 20 字节起，可扩展到 60 | 8 字节 |
  | 典型场景 | HTTP、MySQL、gRPC、文件传输 | DNS、音视频、游戏、QUIC |

- **关键点**
  1. TCP 头部更大、状态更多，适合要求完整性和顺序的业务。
  2. UDP 头部只有源端口、目的端口、长度、校验和，转发开销小。
  3. UDP 没有粘包概念，一次收发的数据报边界由协议保留，但可能丢包、乱序、重复。
  4. UDP 需要可靠性时在应用层补：QUIC 在 UDP 上实现重传、拥塞控制和多路复用。

- **常见追问**
  - **直播为什么用 UDP？** 实时性优先，丢几帧可接受；TCP 重传会造成更大延迟。
  - **TCP 粘包是 TCP 的缺陷吗？** 不是，TCP 本来就是字节流，消息边界应由应用层协议定义。
  - **DNS 为什么默认 UDP？** 查询小、一次一问一答，UDP 省去握手；响应过大或区域传送改用 TCP。

## [必会] 6. HTTP/1.1、HTTP/2、HTTP/3 有什么区别？各自解决了什么问题？

- **结论**：1.1 用长连接减少握手；2 用二进制分帧和多路复用解决 HTTP 层队头阻塞；3 用 QUIC over UDP 解决 TCP 层队头阻塞并加快建连。

- **关键点**
  1. HTTP/1.0：默认短连接，每个请求新建 TCP，开销大。
  2. HTTP/1.1：默认 `keep-alive` 持久连接；引入 `Host`、分块传输、缓存字段；管道化要求响应按序返回，仍有队头阻塞，实际很少用。
  3. HTTP/2：二进制分帧、Stream 多路复用、HPACK 头部压缩、服务端推送（已弱化）；同一连接并发多个流。
  4. HTTP/2 遗留问题：所有流共享一条 TCP 连接，一个丢包会阻塞全部流，即 TCP 层队头阻塞。
  5. HTTP/3：基于 QUIC，流之间独立，丢包只影响单流；集成 TLS 1.3，支持 1-RTT/0-RTT 建连和连接迁移。

- **对比**

  | 维度 | HTTP/1.1 | HTTP/2 | HTTP/3 |
  |---|---|---|---|
  | 传输层 | TCP | TCP | QUIC（UDP） |
  | 并发方式 | 多连接 / 管道化 | 单连接多路复用 | 单连接多流 |
  | 队头阻塞 | HTTP 层有 | TCP 层有 | 基本消除 |
  | 头部压缩 | 无 | HPACK | QPACK |
  | 建连开销 | TCP + TLS | TCP + TLS | 1-RTT，可 0-RTT |

- **常见追问**
  - **HTTP/2 多路复用为什么还有队头阻塞？** 多路复用只在应用层，底层仍是一条有序的 TCP 字节流。
  - **HTTP/3 为什么选 UDP？** UDP 无连接、无队头阻塞，QUIC 在用户态自己实现可靠传输和拥塞控制，部署升级也更容易。
  - **管道化为什么没普及？** 响应必须严格按请求顺序返回，前一个慢请求会阻塞后面，收益有限。

## [必会] 7. HTTPS 的握手过程？为什么用混合加密？

- **结论**：HTTPS = HTTP + TLS；先用非对称加密和证书协商出对称会话密钥，再用对称加密传输数据，兼顾安全与性能。

- **关键点**
  1. TLS 1.2（ECDHE）：`ClientHello`（随机数、套件）→ `ServerHello`（随机数、证书、密钥交换参数）→ 客户端验证证书、生成预主密钥 → 双方用随机数导出会话密钥 → `Finished` 校验握手完整性。
  2. 非对称加密：只用于身份认证和密钥交换，运算慢，不适合传大量数据。
  3. 对称加密：会话密钥协商完成后，用 AES 等对称算法加密应用数据，速度快。
  4. 证书校验：验证域名、有效期、CA 签名链，防止中间人替换公钥。
  5. 前向安全：ECDHE 使用临时密钥，服务器私钥泄露也解不出历史会话。
  6. TLS 1.3：握手压缩到 1-RTT，会话复用可 0-RTT；废除 RSA 密钥交换、CBC 等弱套件。

- **常见追问**
  - **中间人能截获公钥吗？** 能截获，但改不了证书链签名；客户端校验失败会中断连接。
  - **为什么需要三个随机数？** 增加随机性，防止攻击者预测会话密钥；1.3 已简化密钥导出。
  - **0-RTT 有什么风险？** 早期数据可能被重放，只适合幂等请求。

## [必会] 8. 常见 HTTP 状态码有哪些？301/302/304 有什么区别？

- **结论**：1xx 信息、2xx 成功、3xx 重定向、4xx 客户端错误、5xx 服务端错误；重点区分 301/302/307/308 和 304。

- **关键点**
  1. 301 永久重定向：可被缓存，SEO 权重转移。
  2. 302 临时重定向：默认不缓存，后续仍访问原地址。
  3. 307/308：保留原请求方法和 body；307 临时、308 永久。
  4. 304 协商缓存命中：资源未变，响应无 body，浏览器用本地副本。
  5. 401 未认证：缺少或无效凭证；403 已认证但无权限。
  6. 502 网关收到上游无效响应；503 服务暂不可用；504 网关等待上游超时。

- **对比**

  | 状态码 | 语义 | 是否缓存 | 方法与 body |
  |---|---|---|---|
  | 301 | 永久重定向 | 可缓存 | 可能被改成 GET |
  | 302 | 临时重定向 | 默认不缓存 | 可能被改成 GET |
  | 307 | 临时重定向 | 不缓存 | 保持原方法 |
  | 308 | 永久重定向 | 可缓存 | 保持原方法 |
  | 304 | 资源未修改 | 复用本地缓存 | 无 body |

- **常见追问**
  - **304 是怎么产生的？** 请求带 `If-None-Match` 或 `If-Modified-Since`，服务端比对后确认未变。
  - **499 是标准状态码吗？** 不是，是 Nginx 自定义的「客户端提前断开」。
  - **502 和 504 怎么排查？** 502 看上游是否启动、端口和协议是否正确；504 看上游处理耗时和网关超时配置。

## [必会] 9. HTTP 缓存机制？强缓存和协商缓存怎么配合？

- **结论**：先走强缓存，命中直接读本地、不发请求；强缓存失效后走协商缓存，由服务端判断是否返回 304。

- **关键点**
  1. 强缓存：`Cache-Control: max-age=秒`；`no-cache` 表示必须协商，`no-store` 表示完全不缓存。
  2. `Expires`：绝对时间，受客户端时钟影响，已被 `Cache-Control` 取代。
  3. 协商缓存一：`ETag` + `If-None-Match`，按内容标识判断，优先级高。
  4. 协商缓存二：`Last-Modified` + `If-Modified-Since`，秒级精度，内容没变但修改时间变时会误判。
  5. 命中协商缓存返回 304，不传 body，省带宽。
  6. 刷新行为：普通刷新会带协商请求；强制刷新绕过缓存重新拉取。

- **对比**

  | 维度 | 强缓存 | 协商缓存 |
  |---|---|---|
  | 是否发请求 | 否 | 是 |
  | 判断方 | 浏览器 | 服务端 |
  | 响应头 | `Cache-Control`、`Expires` | `ETag`、`Last-Modified` |
  | 命中结果 | 直接使用本地副本 | 304，使用本地副本 |

- **常见追问**
  - **`no-cache` 和 `no-store` 的区别？** `no-cache` 可以存但每次必须校验；`no-store` 禁止任何存储。
  - **为什么 ETag 优先于 Last-Modified？** ETag 基于内容，精度更高；Last-Modified 只有秒级且可能被无关修改刷新。
  - **强缓存没过期，服务端更新了资源怎么办？** 浏览器不会请求；靠文件名带 hash 或版本号改变 URL 来失效。

## [必会] 10. Cookie、Session、Token、JWT 有什么区别？

- **结论**：Cookie 是浏览器存储和自动携带机制；Session 是服务端保存的会话状态；Token/JWT 是自包含凭证，服务端无状态校验。

- **关键点**
  1. Cookie：`key=value` 加 `Domain`、`Path`、`Expires`、`HttpOnly`、`Secure`、`SameSite`；同域请求自动携带。
  2. Session：服务端存储会话数据，客户端只存 `SessionID`；集群需要共享存储或粘性会话。
  3. JWT：`header.payload.signature` 三段 Base64Url；签名保证不可篡改，但 payload 只是编码、不是加密。
  4. 安全配置：`HttpOnly` 防 XSS 读取，`Secure` 只走 HTTPS，`SameSite` 缓解 CSRF。
  5. 注销：Session 服务端删除即可；JWT 无状态，需要短过期 + 刷新令牌或黑名单。

- **对比**

  | 维度 | Cookie | Session | JWT |
  |---|---|---|---|
  | 存储位置 | 浏览器 | 服务端 | 客户端 |
  | 服务端状态 | 无 | 有 | 无 |
  | 跨域使用 | 受同源和 SameSite 限制 | 依赖 Cookie 或请求头 | 放 Authorization 头，跨域方便 |
  | 注销难度 | — | 容易 | 较难，需要黑名单或短 TTL |

- **常见追问**
  - **JWT 能主动撤销吗？** 默认不能；用黑名单、版本号或短过期 + 刷新令牌实现近似撤销。
  - **Cookie 和 Session 是一回事吗？** 不是，Cookie 是传输载体，Session 是服务端状态，Session 通常借 Cookie 传 ID。
  - **分布式 Session 怎么做？** Redis 集中存储、粘性会话或令牌化（JWT）去掉服务端状态。

## [必会] 11. DNS 解析的完整过程？递归和迭代有什么区别？

- **结论**：先查浏览器和系统缓存、hosts，再由本地 DNS 递归查询；本地 DNS 向根、顶级域、权威服务器逐级迭代，最终拿到 A/AAAA 记录。

- **关键点**
  1. 缓存顺序：浏览器缓存 → 操作系统缓存和 hosts → 本地 DNS 缓存。
  2. 本地 DNS：通常由运营商或内网提供，对客户端承担递归查询。
  3. 迭代查询：本地 DNS 依次问根服务器、`.com` 顶级域、权威 NS，拿到下一跳地址。
  4. 权威应答：权威服务器返回 `A`/`AAAA`，本地 DNS 按 TTL 缓存后返回客户端。
  5. 记录类型：`A`/`AAAA` 地址、`CNAME` 别名、`MX` 邮件、`NS` 授权、`TXT` 校验。
  6. 传输协议：默认 UDP 53；响应超过 512 字节、区域传送或加密场景用 TCP/DoT/DoH。

- **对比**

  | 模式 | 发起方 | 工作方式 |
  |---|---|---|
  | 递归查询 | 客户端 → 本地 DNS | 本地 DNS 负责查到底，直接给最终结果 |
  | 迭代查询 | 本地 DNS → 各级服务器 | 每级只给下一跳，由本地 DNS 继续追问 |

- **常见追问**
  - **DNS 为什么用 UDP？** 查询报文小、一问一答，省去 TCP 握手，延迟低。
  - **CDN 怎么用 DNS 调度？** 域名 CNAME 到 CDN 调度域，权威 DNS 按来源 IP 返回最近节点。
  - **DNS 缓存会带来什么问题？** 记录变更后要等 TTL 过期才生效，迁移时需提前调小 TTL。

## [必会] 12. epoll 的原理？select、poll、epoll 有什么区别？

- **结论**：epoll 用内核事件表和就绪链表，只返回就绪 fd，取事件 O(1)；select/poll 每次全量拷贝并线性扫描，复杂度 O(N)。

- **关键点**
  1. `select`：`fd_set` 位图，默认上限 1024；每次调用拷贝全集，返回后还要遍历找就绪 fd。
  2. `poll`：`pollfd` 数组，去掉 1024 限制；仍需全量拷贝和遍历。
  3. `epoll_create`：创建 epoll 实例，内核维护红黑树存注册的 fd。
  4. `epoll_ctl`：注册、修改、删除 fd，只需操作一次，不必每次调用重传。
  5. `epoll_wait`：等待就绪链表，有事件时直接返回就绪项。
  6. 触发模式：LT 水平触发，未处理会持续通知；ET 边沿触发，只通知一次，必须一次读到 `EAGAIN`，通常配非阻塞 fd。

- **对比**

  | 维度 | select | poll | epoll |
  |---|---|---|---|
  | fd 上限 | 1024（`FD_SETSIZE`） | 无硬限制 | 无硬限制 |
  | 事件传递 | 每次全量拷贝 | 每次全量拷贝 | 内核维护，`epoll_wait` 只取就绪 |
  | 查找复杂度 | O(N) | O(N) | O(就绪数) |
  | 触发模式 | 仅 LT | 仅 LT | LT / ET |

- **常见追问**
  - **ET 为什么必须配非阻塞？** 必须循环读到 `EAGAIN`，阻塞 fd 会在最后一次读上卡住。
  - **epoll 一定比 select 快吗？** 连接多且活跃少时优势明显；连接少且全部活跃时差距不大。
  - **惊群问题是什么？** 多个进程等待同一事件被同时唤醒；用 `EPOLLEXCLUSIVE` 或单线程 accept + 分发缓解。

## [必会] 13. 从输入 URL 到页面展示，中间发生了什么？

- **结论**：解析 URL → DNS 解析 → 建立 TCP（HTTPS 再加 TLS）→ 发送 HTTP 请求 → 服务端处理返回 → 浏览器解析渲染 → 加载子资源。

- **关键点**
  1. URL 解析：拆出协议、域名、端口、路径、查询参数。
  2. DNS 解析：逐级查缓存和 DNS 服务器，得到目标 IP。
  3. 建立连接：TCP 三次握手；HTTPS 再执行 TLS 握手协商密钥。
  4. 发送请求：构造请求行、请求头、请求体，经代理或网关到服务端。
  5. 服务端处理：路由、鉴权、业务逻辑、查缓存和数据库，返回响应。
  6. 浏览器渲染：HTML 解析成 DOM，CSS 解析成 CSSOM，合成渲染树，布局后绘制。
  7. 子资源与连接：加载 JS/CSS/图片；连接复用或四次挥手关闭。

- **常见追问**
  - **哪些环节可以优化？** DNS 预解析、预连接、CDN、HTTP/2 多路复用、缓存、压缩、首屏直出。
  - **DOMContentLoaded 和 load 的区别？** 前者在 HTML 解析完成触发；后者等图片等全部资源加载完。
  - **JS 会阻塞渲染吗？** 会，普通 `<script>` 阻塞解析；用 `defer`/`async` 或放到 body 末尾。

## [高频] 14. TCP 粘包、拆包是什么原因？怎么解决？

- **结论**：TCP 是字节流、没有消息边界，一次读取可能拿到半个或几个消息；解决靠应用层协议定界，不是靠 TCP 本身。

- **关键点**
  1. 根本原因：TCP 只保证字节顺序，不保留发送方每次 write 的边界。
  2. 加剧因素：Nagle 算法合并小包、接收缓冲区大小、MSS/MTU 分片、读取时机。
  3. 定界方案一：固定长度，简单但浪费带宽。
  4. 定界方案二：长度前缀，先读长度再读 body，gRPC/protobuf 的帧格式就是这种。
  5. 定界方案三：特殊分隔符，如 `\r\n`、`\0`，需处理转义。
  6. 定界方案四：自描述格式，如 HTTP 的 `Content-Length` 或 `Transfer-Encoding: chunked`。

- **常见追问**
  - **UDP 会粘包吗？** 不会，UDP 保留数据报边界；但会丢包、乱序、重复。
  - **为什么 HTTP 需要 chunked？** 响应长度未知时无法先给 `Content-Length`，用分块编码边生成边发送。
  - **Nagle 和粘包是一回事吗？** 不是，Nagle 只是合并小包，粘包的本质是字节流没有边界。

## [高频] 15. TCP Keep-Alive 和 HTTP Keep-Alive 有什么区别？

- **结论**：TCP Keep-Alive 是传输层探活，检测死连接；HTTP Keep-Alive 是应用层连接复用，让一个 TCP 连接承载多个请求。

- **关键点**
  1. TCP Keep-Alive：连接空闲达到阈值后发探测包，多次无响应则关闭；用于清理半开连接。
  2. 默认参数：Linux 空闲约 2 小时开始探测，间隔 75 秒，失败 9 次断开；可按需调整。
  3. HTTP Keep-Alive：HTTP/1.1 默认持久连接，通过 `Connection: keep-alive` 复用，减少握手和慢启动开销。
  4. 复用限制：受服务端空闲超时（如 Nginx `keepalive_timeout`）和单连接最大请求数约束。
  5. 应用层心跳：比 TCP 探活更可控，WebSocket ping/pong、gRPC keepalive 都属此类。

- **对比**

  | 维度 | TCP Keep-Alive | HTTP Keep-Alive |
  |---|---|---|
  | 层级 | 传输层 | 应用层 |
  | 目的 | 探活，发现半开连接 | 复用连接，减少建连开销 |
  | 默认状态 | 需应用显式开启或调参 | HTTP/1.1 默认开启 |
  | 控制方式 | 内核参数、`setsockopt` | `Connection` 头、服务端超时配置 |

- **常见追问**
  - **半开连接怎么产生？** 一方断电或网络中断，对端没有收到 FIN，仍认为连接有效。
  - **为什么 TCP Keep-Alive 默认那么久？** 早期为节省网络资源；实时业务应改用应用层心跳缩短检测时间。
  - **长连接怎么防止被中间设备断开？** 应用层定时心跳，保持连接活跃并及时发现失效。

1. 这个是 receiver 主动去拉的还是（probe）去同步的？就是这个探针（数据）是谁发送的？

   Probe 作为 grpc 客户端，调用 receiver 服务端提供的 rpc 方法，主动把自己收集好的数据上报给 receiver

2. 讲一讲你负责的这部分有什么难点？

   压测，需要去对比 grpc 几种不同的通信模式，收集性能数据指标，最后综合判断选一个最适合周期性上报场景的模式。最后选了 ur，除此以外还测了 bs 和 cs。 ur 直接用了现成压测工具 ghz，流式通信是自己搭建了比较简单的客户端和服务端，通过配置文件修改连接数和上报周期，最终利用公司统一监控平台去获取主机比如 cpu、内存的实时数据，还有自己去统计 rps、错误率等数据（被打断）

3. 就是你觉得搭这个压测链路比较难嘛，具体难在哪里？

   对比 cs 和 bs 的时候，遇到了一个比较疑惑的点；按照常理 bs 内存占用应该高于 cs，实际观察到的现象是 cs 几乎是 bs 两倍，比如在几万连接的时候 bs 就占用 5-6G 内存，但是 cs 可以达到 10G 甚至更高；后面用 pprof 去排查，去看具体是哪些部分在占用内存，发现常居高位的是 sizePool 和 cs.Buffer，推断：

   1. grpc 默认有 retry，会把要上报的信息多缓存一份在内存中，等到收到 commit，即确认消息成功发送、对端有响应才会释放 retry 内存（被打断）

4. 你是说 cs 有 retry，但是 bs 没有？

   都有的，这是默认机制

5. 那不是说觉得 bs 内存占用会更高，但是观察到 cs 才是？

   因为直觉来说会这么觉得，但实际观察到的是 cs，单向的更高；而刚才说到的 retry，会多缓存一份，只有 commit 了才释放。但推测由于 cs 一直是单向上报的场景，bs 的客户端和服务端之间是有来有回的，不会像 cs 那样只有客户端一直上报，不收到服务端任何响应，也不会去给客户端发送消息。所以这部分 retry 的内存可能就会更快释放。这是推测的第一个点

   第二点是调查之后发现 retry 申请的内存不是严格按照消息体大小申请的，比如说消息体是 1kb，实际申请到的会是 4kb，这部分是按照桶来申请的。也就是实际占用内存会比消息体实际大小更高

   再加上 retry 长时间没有 commit 导致这一部分内存没有办法释放掉，就导致在监控平台观测到 cs 的内存占用显著更高

6. 那你说的这个内存申请，bs 不会这么申请吗？

   bs 也是的

7. 所以说无论是 retry 还是桶申请，bs 和 cs 都是一样的，为什么能从这里分析出它们内存不一致的原因呢？

   主要还是 commit 的时机。因为 retry 这部分内存需要确认对端已经成功收到消息并且有响应回来，才会被释放掉；bs 的话就是客户端服务端之间有即时的通信，客户端马上就可以得到服务端的回应或者收到那边推送下来的消息，这样相比只有单向上报、持续上报的 cs 更快地 commit，从而更快地释放掉这部分内存

10. 这个 sizePool 和 cs.Buffer 有什么区别？

    前者可以理解为像内存池这样的概念，如果流式通信每次发消息都去申请新内存可能会有资源浪费，所以就会用到内存池；buffer 就是指申请的那部分内存，像 retry 就要从 buffer 里申请一部分来缓存消息体

11. 就是 grpc 自己的概念是吧，它自己的一些内存管理

12. 你了解这个持久化还有分析的模块，它们具体是做什么的吗？

    分析的话工作主要是有两个循环，一个是 scan 循环，扫描数据库里探针收集到的数据，如果有异常，触发二次探测，ssh 到有异常的主机，检测是否真的有问题；如果判断有问题，会推到滑动窗口中，等待做后续判断；假设说判断完真的有问题，就会进入切换流程

13. 那它采集的信息是什么？

    db 实例自身的状态信息，db 实例所在的主机的 cpu、内存信息；（追问还有别的吗？就想知道采集的能分析出问题的所有指标）也会去采集 db 实例自身的信息，这里确实不太知道具体会采集什么；但肯定会尝试去连接 db，如果连不上的话也会把它处理成一个异常事件，和前面的数据信息一起上报给 receiver

15. 能不能从总体角度，去看这整个系统最复杂的点在哪里，复杂度体现在哪里？哪里最有挑战性？

    分析（analysis）需要结合 probe 收集到的数据，结合人为制定的规则和策略去判断是否真的有问题；包括后续判断为真，切换，也会涉及到不同的切换策略，像集群切换、实例级别的切换又或者机器上的切换。切换还涉及到需要搞清楚 db 当前的角色，比如是主库还是从库？以及它的从库是否正常。假如说它是主库它故障了，它的从库状态怎么样，需要去了解这个 db 集群的架构（打断）

16. 假设要你来负责这个分析组件，你会拆分成哪些模块，有哪些能力，怎么拆分？不用太细节，就分模块

    大致思路还是分成 4 个：

    1. 扫描数据库：筛选有问题的异常数据
    2. 判断：根据用户预定的阈值、策略去判断这些数据是否真的有效、db 是否真的有问题，给出是否要执行下一步的结果；
    3. 切换：切换到从库，或者下线
    4. （没给出具体角色名）职责是去 etcd 或者保存有集群最新状态信息的组件拉取当前 db 的信息元数据，比如身份角色，集群状态，给切换提供必要的信息

17. 这个第四个是分析模块应该做的吗？感觉它更多是去收集元数据，而不是分析问题，更多是元数据的存储？

29. 不是有个下单功能吗？从用户点击下单，到下单成功，中间哪些是一定同步，哪些一定是异步的逻辑？

    同步：先扣库存再去调支付接口，必须确保库存扣减成功、收到响应才能支付；支付成功后订单状态更新，后续涉及到发货，发货前提是订单状态更新为 paid，才能够去触发发货；（追问：发货不能异步发吗？答：确实可以，但需要订单支付的前提）

    异步：订单创建到订单落库，中间有消息队列；redis 库存增量扣减更新到 mysql；订单状态更新落库，类似于从 pending 到 paid 这个状态，是事件驱动的，会先发到消息队列，最后再异步落库

30. 能不能一句话总结一下什么时候要同步，什么时候要异步？

    要求强因果关联就同步；异步允许时间延迟，对一致性要求没有那么高（最终一致）就异步

31. 还有就是你要扛一些秒杀流量

32. 这里用 rockermq 主要是做异步的吗？那 redis stream 是什么？这个我没用过

    可以理解为一种轻量的消息队列，也有消费者组，下游消费完需要 ack；除此以外还有 pending list，没有被消费的消息就放在这里面，可以通过其他的手段，去 pending list 夺取消费权，进行其他处理

33. 为什么有 rocketmq 还要 redis stream？都是队列功能，异步而已

    主要还是想把它和库存扣减绑定在一起，把扣库存和写 stream 的扣减记录都放在了一个 lua 脚本里，确保扣减完库存 redis 里一定会有扣减记录和订单记录，因为都在原子的 lua 脚本里；后续如果要把 redis 扣减更新到 mysql，就有消息队列确保我的更新可靠，因为必须更新成功了才会回复 ack，不然就会一直在队列里面

34. 我觉得 rmq 也可以解决这个问题

35. 那写 redis 也可能丢失呀

    所以我是有开 aof 做持久化的

36. 那 mq 也有持久化的

    其实我主要考虑的还是说一定要把库存扣减和写队列绑定在一起，它们得是一个事务，要么同时成功要么同时失败，假设说库存已经扣减成功但是还没有投递到 mq，这个时候 mq 挂机了，那这一部分记录它就没有了。但如果我把它们放在 redis stream，当作一个原子化的事务去处理，那就有扣减就一定会有记录

37. 这个扣减不是在 mq 消息消费之后才执行的吗？为什么会是在投递到 mq 之前去扣减？

    因为秒杀的话流量会比较大嘛，所以会选择把 redis 前置，扣减动作先发生在 redis；后续再有异步 worker 从 redis stream 拿出扣减记录，再更新到 mysql

38. 那能不能把所有流程都放在 mq 之后？无论是 redis 还是 mysql。就先投递到 mq，然后告诉说在排队，等到后续再到数据库扣减，如果成功了，就说你抢成功了。跟你这个方案有什么区别？

    我觉得是可以跑起来的。但是消息队列本身我们是把它放在异步场景下，如果里面有很多消息积压的话就一定会有延迟，尤其还是在扣减库存之后才能支付，那这样给到用户，就会出现下游的延迟问题，流量越大会越明显。但如果我把 redis 前置，它的处理是很快的，因为是同步的，所以马上就能给到用户一个响应

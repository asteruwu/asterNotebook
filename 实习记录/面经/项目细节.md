## 一、压测方法论（8-25 Q2/Q3 答非所问，最需要重练）

**面试官问法**："怎么做的压测？协议以及压测数据，怎么对比、怎么选择？"

**四段式回答（背熟）**：

1. **对象与变量控制**：对比 Unary / Client Streaming / Bidirectional Streaming 三种模式。Unary 用第三方压测工具 ghz；CS 和 BS 没有现成工具，自己写了最简客户端和服务端，通过**配置文件控制连接数和上报间隔**，保证除通信模式外其他变量一致。
2. **观测指标**：客户端和服务端 CPU 占用、内存消耗、RPS、消息上报 P99 延迟、错误率。CPU/内存从蓝鲸监控平台直接取数，应用层指标从程序内统计。
3. **极限判定标准（这是亮点，一定要说）**：不同模式用不同极限依据——Unary 以**错误率突破**为极限（单机并发 6-7w，QPS 2w 出头）；CS/BS 以**客户端内存耗尽**为极限（分别最多 1.5w / 5.5w 连接）。
4. **决策**：场景是**低频周期性上报**，不需要流式能力；Unary 内存开销可控、实现和维护最简单，**基于内存资源消耗选了 Unary**。

**协议设计的回答**（Q3"是重新设计了一套协议吗"）：

> 协议不复杂，不是自研私有协议——传输用 gRPC（HTTP/2 + protobuf），protobuf 定义了探针采集的数据结构和元信息（实例信息、采集项、时间戳等），做的是最基础的"采集完信息然后上报"的场景。复杂度不在协议本身，在链路的可靠性：负载均衡、故障切换、探活重连。

### 表行数的"估算逻辑"兜底话术（查不到确切数字时用）

> "精确行数我没有背下来，但可以推算：30w 实例 × 每实例上报周期 T 秒 × 每周期 1 条记录 × 保留 N 天 ÷ 分表数，量级大约是 X 亿/天，所以我们按时间维度做滚动清理/分区，单表实际保持在 Y 以内。"

**核心原则：不知道精确值没关系，"没统计过"绝对不行，给推算过程和量级。**

### 应对"30w 实例会把表写爆"（8-25 Q21）

> "按裸算确实如此，所以容量规划上：① 上报是低频周期性的（周期 T 秒），不是每个请求一条，实际写入 QPS = 实例数 ÷ 周期，被周期摊薄了；② receiver 多实例分摊 + 批量写；③ 表按时间滚动清理/归档，行数有上界。另外 30w 实例是 v1 的存量数据，v2 的 grpc 链路还在开发中、尚未全量上线。"

## 三、部署与架构事实（防追问串线）

**三个组件**（8-25 Q5 答对了，保持）：

* **probe**：与 db 实例同机部署，周期性采集 db 自身状态 + 主机状态，通过 gRPC 上报 receiver
* **receiver**：集中接收、持久化到 MySQL（5 张表）
* **analysis**：分析库中数据判断 db 异常 → 二次探测确认 → 触发切换

**容易串线的点**：

* probe 和 db **同机部署**，但 probe 上报的目标 receiver 在**别的机器**（8-25 Q13）。
* 我的链路是 **v2 的备选通道**，还没上线，现在生产用的是腾讯 GSE 云通道（8-25 Q14/Q18）——**主动说清"开发中/备选"状态，别等面试官问出来说"没上线"显得遮掩**。
* 修的网络故障阻塞问题：**iptables 注入网络故障 → 发现持久化静默阻塞半小时、无告警、无 fail fast → MySQL DSN 加读写超时修复**。这是主动发现隐患的故事，讲的时候带上状态（测试环境验证，随 v2 上线）。

# 测试报告

## 0. 适用范围

- 读者：开发、QA、评审者、发布决策者。
- 用途：证明系统在什么范围、什么版本、什么环境下达到了什么质量水平，支持发布决策。
- 组织轴：范围 → 策略 → 用例 → 结果 → 缺陷 → 结论。
- 结尾：发布建议 + 遗留风险 + 后续动作。
- 更新：一次测试一轮报告；修复后补回归结果，不覆盖历史结论。

通用规则见 [01-通用规范](01-通用规范.md)。

## 1. 核心原则

1. **结论第一屏**：通过 / 有条件通过 / 不通过，以及阻塞项。
2. **可复现**：版本、环境、配置、命令、数据、步骤齐全。
3. **未执行不算通过**：结果只有通过、失败、阻塞、未执行四种。
4. **失败用例有证据**：预期、实际、复现步骤、日志或截图。
5. **缺陷有级别和影响**：P0~P3，写清影响范围和是否有绕过。
6. **指标有目标值**：没有目标的数字不构成结论。
7. **范围写清不测什么**：避免「测过了」被误解为「全都测过了」。
8. **结论不含糊**：不用「基本没问题」「应该可以」。

### 测试计划与测试报告

- 只做计划时，保留第 1~3 节，第 4~7 节改为「计划执行安排」。
- 只做报告时，第 1~3 节压缩为表格，重点放在第 4~7 节。
- 计划与报告同文档时，用 `## 3. 测试策略` 区分「计划」和「实际执行」。

## 3. 槽位词表

| 槽位 | 含义 | 示例 |
|---|---|---|
| `测试范围` | 本次测什么 | probe → receiver → MySQL 主链路 |
| `范围外` | 本次不测什么 | 不测多 receiver 容灾 |
| `验收标准` | 什么算通过 | 主链路无丢数据；断连 30s 内恢复 |
| `测试版本` | 被测代码版本 | `commit 4f2a1c` / `v1.2.0` |
| `环境` | 操作系统、依赖、配置 | Linux / Go 1.24 / MySQL 8.0 |
| `测试数据` | 输入数据与规模 | 10 万条探测记录 |
| `策略` | 测试类型和方法 | 功能、异常、性能、回归 |
| `用例 ID` | 唯一编号 | `TC-001` |
| `场景` | 用例覆盖的业务场景 | 单 probe 连续上报 |
| `前置条件` | 执行前的状态 | receiver 已启动，MySQL 可写 |
| `步骤` | 可复现的操作 | 1. 启动 probe；2. 发送 1000 条 |
| `预期` | 期望结果 | 数据库记录数与发送数一致 |
| `实际` | 实际结果 | 1000 条全部落库 |
| `结果` | 通过 / 失败 / 阻塞 / 未执行 | 通过 |
| `证据` | 日志、截图、查询结果 | 关键日志行、SQL 查询结果 |
| `缺陷 ID` | 唯一编号 | `BUG-001` |
| `严重级别` | P0 / P1 / P2 / P3 | P1 |
| `复现率` | 必现 / 偶现 / 未复现 | 必现 |
| `影响` | 对功能、数据、用户的影响 | 上报中断，数据丢失 |
| `指标` | 性能、稳定性、资源 | P99、QPS、错误率 |
| `目标值` | 指标合格线 | P99 < 50ms |
| `实测值` | 实际测量结果 | P99 45ms |
| `结论` | 发布判断 | 有条件通过 |
| `遗留风险` | 未解决的风险 | 单 receiver 单点 |
| `后续动作` | 修复、回归、监控 | BUG-001 修复后回归 |

## 4. 测试范围与策略

### 范围

必须写清：

- **范围内**：功能、模块、链路、接口。
- **范围外**：明确不测的内容，以及原因。
- **验收标准**：可检验的通过条件。
- **测试数据**：规模、来源、脱敏方式。
- **依赖**：外部服务、中间件、账号、权限。

示例：

```markdown
## 1. 测试范围

- **范围内**
  1. probe → receiver → MySQL 主链路。
  2. 单 probe 连续上报、断连重连。
  3. receiver 连接数上限。
- **范围外**
  - 多 receiver 容灾切换（依赖 6.2，未实现）。
  - 跨公网部署。
- **验收标准**
  - [ ] 主链路无丢数据。
  - [ ] 断连 30s 内自动恢复。
  - [ ] P99 < 50ms。
```

### 策略

| 测试类型 | 目标 | 通过标准 | 工具 / 方法 |
|---|---|---|---|
| 功能测试 | 主链路和分支可用 | 用例全部通过 | 手工 + 自动化 |
| 异常测试 | 依赖故障可恢复 | 故障恢复后链路自动恢复 | 断网、杀进程、超时注入 |
| 性能测试 | 吞吐和延迟达标 | P99、QPS 达到目标 | 压测脚本 |
| 回归测试 | 旧功能不受影响 | 旧用例全部通过 | 回归套件 |
| 兼容测试 | 新旧配置 / 客户端可用 | 旧配置行为不变 | 配置矩阵 |

规则：

- 每类测试写清目标、通过标准和工具，不写「做了测试」。
- 异常测试必须包含：故障注入方式、恢复方式、恢复时间。
- 性能测试必须包含：负载模型、样本量、持续时间、环境。

## 5. 用例与结果

### 用例表

| 用例 ID | 场景 | 前置条件 | 预期 | 实际 | 结果 |
|---|---|---|---|---|---|
| TC-001 | 单 probe 连续上报 1000 条 | receiver 已启动 | 数据库记录数 = 1000 | 1000 | 通过 |
| TC-002 | receiver 重启后重连 | probe 正在上报 | 30s 内恢复 | 12s 恢复 | 通过 |
| TC-003 | 连接数超限 | 连接数达到上限 | 返回 `ResourceExhausted` | 返回 500 | 失败 |

规则：

- 用例 ID 连续，不复用。
- 一个用例只验证一个场景。
- 「实际」写结果，不写过程。
- 「结果」只用四个固定词。
- 未执行的用例保留，标 `未执行` 和原因。

### 失败用例

每个失败用例单独成节：

```markdown
### TC-003 连接数超限

- **复现步骤**
  1. 启动 receiver，连接上限设为 10。
  2. 启动 11 个 probe，同时上报。
  3. 查询第 11 个 probe 的日志和响应。
- **预期**：返回 `codes.ResourceExhausted`，probe 切换地址或告警。
- **实际**：返回 HTTP 500，probe 持续重试，未告警。
- **复现率**：必现。
- **证据**
  - 日志：`level=error msg="push failed" code=500`
  - 查询：`SELECT COUNT(*) FROM t_dbha_status;` 结果 0。
- **定位**：`ProbeServer.PushData` 未做连接数判断。
- **关联缺陷**：`BUG-001`。
```

规则：

- 失败用例必须有复现步骤、预期、实际、证据。
- 证据只保留关键日志行；不贴完整日志。
- 截图只保留关键区域，alt 写明界面和状态。
- 定位到文件 / 函数 / 配置项；定位不了写 `**未定位**` 和下一步。
- 偶现问题写复现次数 / 总次数，不写「偶尔」。

## 6. 缺陷汇总

| 缺陷 ID | 级别 | 描述 | 复现率 | 状态 | 影响 | 负责人 |
|---|---|---|---|---|---|---|
| BUG-001 | P1 | 连接数超限返回 500，未返回 `ResourceExhausted` | 必现 | 待修复 | probe 无法区分错误，持续重试 | 自己 |

### 级别定义

| 级别 | 定义 | 示例 |
|---|---|---|
| P0 | 阻塞发布：核心链路不可用、数据损坏、安全问题 | 上报全链路中断；数据写错表 |
| P1 | 核心功能不可用，无绕过 | 连接数超限处理错误；重连失效 |
| P2 | 非核心功能异常，有绕过 | 指标少一个 label；日志缺字段 |
| P3 | 体验、文案、边界问题 | 错误提示不清晰；文档笔误 |

规则：

- 级别按影响定，不按修复难度定。
- 缺陷状态固定：`待修复 / 修复中 / 待验证 / 已关闭 / 不修复`。
- `不修复` 必须写原因和影响。
- 缺陷描述写「现象 + 条件 + 影响」，不写猜测。

## 7. 指标与发布结论

### 指标表

| 指标 | 目标值 | 实测值 | 结论 |
|---|---|---|---|
| P99 延迟 | < 50ms | 45ms | 达标 |
| 吞吐 | > 1000 条/s | 1200 条/s | 达标 |
| 错误率 | < 0.1% | 0.3% | 未达标 |
| 断连恢复时间 | < 30s | 12s | 达标 |
| 内存占用 | < 200MB | 180MB | 达标 |

规则：

- 指标必须有目标值；没有目标值不写进结论。
- 实测值给样本量、持续时间、环境。
- 未达标项必须解释原因和影响。
- 不贴完整监控截图；只保留关键曲线或数据点。

### 发布结论

结论只有三种：

| 结论 | 条件 | 后续动作 |
|---|---|---|
| 通过 | 无 P0/P1；验收标准全部满足 | 可发布 |
| 有条件通过 | 无 P0；P1 有明确绕过或修复计划 | 限期修复 + 回归 + 监控 |
| 不通过 | 存在 P0，或核心验收标准未满足 | 修复后重新测试 |

结论写法：

```markdown
## 7. 结论与风险

- **结论**：有条件通过。
- **阻塞项**：无。
- **遗留缺陷**
  - BUG-001（P1）：连接数超限返回 500；计划 2026-11-05 修复并回归。
- **遗留风险**
  - 单 receiver 单点；多实例容灾未实现。
- **发布建议**
  1. 先灰度 10% probe。
  2. 观察错误率和重连指标 24h。
  3. 无异常后全量。
- **后续动作**
  - [ ] 修复 BUG-001。
  - [ ] 补充连接数超限用例。
```

规则：

- 结论必须和缺陷、指标一致；不能「有 P0 但通过」。
- 遗留风险写影响和监控方式。
- 发布建议写灰度、观察指标、回滚条件。
- 后续动作可勾选、可跟踪。

## 9. 检查清单

- [ ] 第一屏有结论、测试版本、环境、阻塞项。
- [ ] 测试范围写清「测什么」和「不测什么」。
- [ ] 环境、版本、配置、数据规模齐全。
- [ ] 每类测试有目标、通过标准和方法。
- [ ] 用例有 ID、场景、前置、预期、实际、结果。
- [ ] 结果只用通过 / 失败 / 阻塞 / 未执行。
- [ ] 失败用例有复现步骤、预期、实际、证据、定位。
- [ ] 缺陷有级别、复现率、状态、影响、负责人。
- [ ] 指标有目标值和实测值，未达标有解释。
- [ ] 结论与缺陷、指标一致，没有「有 P0 但通过」。
- [ ] 遗留风险和发布建议可执行。
- [ ] 没有大段原始日志、无关截图、模糊结论。

## 10. 反面模式

- ❌ 只写通过率，不写范围和环境。
- ❌ 失败用例没有复现步骤和证据。
- ❌ 把未执行算作通过。
- ❌ 结论写「基本没问题」「应该可以」。
- ❌ 有 P0 缺陷仍然给「通过」。
- ❌ 指标没有目标值，只贴数字。
- ❌ 环境、版本、配置缺失，结果无法复现。
- ❌ 贴整屏日志或无关截图，关键信息被淹没。
- ❌ 缺陷级别按修复难度定，不按影响定。
- ❌ 遗留风险不写，发布后才发现。
- ❌ 把测试计划当测试报告，只有安排没有结果。

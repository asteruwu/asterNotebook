# 学习笔记

## 0. 适用范围

- 读者：未来的自己。
- 用途：学会、记住、能复述、能做对题。
- 组织轴：认知依赖，按「定义 → 机制 → 示例 → 边界」展开。
- 结尾：课程笔记用 `# 课后习题`；技术笔记用练习题、对比表或排查清单。
- 更新：按主题追加；新知识插入对应 `##` / `###`，不改动其他节。

通用语言、列表、表格、公式、代码、证据规则见 [01-通用规范](01-通用规范.md)。

## 1. 先判断笔记类型

| 类型 | 典型对象 | 主体写法 | 结尾 |
|---|---|---|---|
| 课程理论 | 通信原理、信息论、信号与系统、概率论、DSP | 定义 → 公式 → 性质 → 示例 → 结论 | `# 课后习题` |
| 编程语言 / 工具 | Rust、Go、Shell、Docker、K8s | 核心职责 → 用法 → 约束 → 示例 → 对比 | 练习题或小结 |
| 中间件 / 架构 | Redis、MySQL、RocketMQ、Nginx、分布式理论 | 核心职责 → 机制 → 架构设计 → 工程落地 | 面试常考 / 调优 |
| 网络协议 | IP、TCP、HTTP、DNS | 定义 → 报文 / 流程 → 关键字段 → 示例 → 排查 | 常考对比 |
| 公式汇总 | 各科 `公式汇总.md` | 只列公式与一句话结论，不推导 | 无 |
| 习题 / 练习 | 章末习题、编程练习 | 题目 → 思路 → 推导 / 代码 → 结论 | 无 |

写作前先判断类型，再选对应的槽位词和结尾形态。

## 2. 文件与标题骨架

### 文件组织

- 课程笔记：`学期/课程/第X章.md`，一章一文件；`公式汇总.md` 独立。
- 技术笔记：`主题/技术名.md`，如 `中间件/Redis.md`；大型主题另建 `_大纲.md`。
- 文件名用中文主题名，不用日期、不用序号前缀。
- 图片放 `dio图表/<课程或主题>/`，笔记中用相对路径引用。

### 标题层级

- `#`：一个知识大块 / 一个功能分区。
  - 课程笔记用主题名，如 `# 信道容量`、`# Z变换与收敛域`。
  - 技术笔记可用 `# Part1. 基础必备`、`# 基础架构与核心组件`。
- `##`：子主题，如 `## 连续信道容量`、`## NameServer`。
- `###`：具体知识点、机制、例题分组。
- **不要**把「第X章」写进标题；文件名已经承担了这个信息。
- 标题下空一行再写正文；层级不跳级。
- 正文中**不使用 `---` 分隔线**；仅技术笔记开头的「编排准则清单」后允许一次。

### 开头与结尾

- 不写「本章将介绍……」「下面我们来看……」这类导语，直接进入第一个知识点。
- 不写「本章总结」；需要收束时，用 `## 小结` 下的几条加粗结论。
- 章末统一 `# 课后习题`，题号用 `## 1-4`。
- 技术笔记可在文首放一段引用块「笔记核心编排准则清单」，只写约束，不写内容。

## 3. 知识点原子块

每个知识点都应能独立成块，推荐结构：

````markdown
### 知识点名

- **定义**：一句话说清它是什么。

- **公式**
  $$
  ...
  $$
  其中 $x$ 表示……，$y$ 表示……。

- **性质 / 特点**
  1. ……
  2. ……

- **示例**
  已知……，求……。

  根据
  $$
  ...
  $$
  代入……可得
  $$
  ...
  $$
  所以……。

- **结论**：用一句加粗结论收束。
````

### 槽位词表

按笔记类型选用，保持全文一致：

- 课程理论：`定义`、`公式`、`性质`、`特点`、`判断方法`、`步骤`、`示例`、`结论`、`注意`。
- 编程语言：`核心职责`、`基础用法`、`语法约束`、`设计特征`、`使用边界`、`示例`、`对比`。
- 中间件 / 架构：`核心职责`、`核心定位`、`组件机制`、`架构设计特色`、`端到端流转`、`工程落地`、`常见问题`。
- 网络协议：`定义`、`作用`、`工作流程`、`报文结构`、`关键字段`、`示例`、`排查`。

### 原子块规则

- 每个标签独占一行，格式为 `- **标签**：内容`，或 `- **标签**` 后换行缩进。
- 一个列表项只讲一件事；出现「另外」「同时」「顺便」时，考虑拆项。
- 先定义后展开；工程类笔记可先给「核心职责」再展开机制。
- 一个 `###` 下只放一个知识点；内容过多时拆成多个 `###`。
- 列表嵌套不超过 3 层；超过就改用小标题分段。
- 块与块之间空一行，保持视觉呼吸。

## 4. 语言风格

- 全中文；术语、API、命令、字段名保留英文。
- 用陈述句和短句；一句话只表达一个判断。
- 结论、易错点、关键术语用 `**加粗**`。
- 不寒暄、不设问、不感叹、不写「我们」开头的空话。

### 推导连接词

课程笔记允许并鼓励完整的推导语气：

> 因为……，所以……；根据……；代入……；可得……；由此可得……；于是……。

技术笔记则压缩为：

> 负责……；通过……实现……；本质是……；对应……；区别在于……。

### 禁止项

- 禁止通俗比喻（「就像一个仓库」「好比快递员」）。
- 禁止空泛评价（「非常重要」「十分强大」），除非后面紧跟具体原因。
- 禁止重复标题；标题已经说了，正文不要再说一遍。
- 禁止大段连续文字；超过 3 行没有列表 / 公式 / 代码 / 表格，就应改写。
- 禁止装饰性 emoji、彩色高亮、无意义的分隔线。

## 5. 公式规范

- 行内公式：`$...$`，前后留空格，如 `其中 $T$ 表示码元周期`。
- 块级公式：`$$` 独立成段，前后空行。
- 多行推导用 `aligned` 对齐等号：

```latex
$$
\begin{aligned}
y &= f(x) \\
  &= g(x)
\end{aligned}
$$
```

- 公式后必须解释符号：`其中 $x$ 表示……`。
- 中文单位、中文条件放 `\text{}`：`\text{bit/s}`、`\text{其他}`。
- 多个条件用 `\qquad` 分隔：`|z|>|a|,\qquad a>0`。
- 关键公式可单独再列一次结论；不要在正文里重复三遍。
- `公式汇总.md` 只保留 `### 名称` + 公式 + 一句结论，不写推导过程。

## 6. 代码规范

- 代码块必须标注语言：`rust`、`go`、`bash`、`lua`、`mysql`。
- 代码前用一句话说明目的；代码后不逐行复述。
- 示例尽量最小可运行；保留必要的 `use`、`fn main`、类型标注。
- 只在非显然处写注释；错误示例用注释标出：

  ```rust
  // println!("{s1}"); // 编译错误：s1 已失效
  ```

- 语言特性用「核心职责 → 基础用法 → 语法约束 / 设计特征 → 示例」组织。
- 易混概念用对比表或并列小节，如 Move vs Copy、`&T` vs `&mut T`。
- 不贴大段无关输出；命令输出只保留关键行。
- 练习题给完整可运行代码，并在题面列出明确要求（参数类型、实现方式、输出格式）。

## 7. 例题、习题与练习

- 章末用 `# 课后习题`，按 `## 1-4` 分题。
- 例题可用 `> 示例`、`> 示例1`、`> 【连续能量】示例2` 作为引用块小标题。
- 解题顺序固定：
  1. 一句话思路（复杂题建议写）。
  2. 写出依据的公式。
  3. 代入数值 / 表达式。
  4. 化简并给出结果与单位。
  5. 必要时给结论或判断。
- 不写「解：」「答案：」，直接开始推导。
- 多小问用有序列表 1. 2. 3.，每问内部再嵌公式。
- 中间结果保留，不跳步；最终结果加粗或单独成行。
- 编程练习题：题面 → 要求列表 → 完整代码；代码后不加长篇解释。

## 8. 强调、提示与引用

- `**加粗**`：术语首次出现、关键结论、易错点、命令 / 字段名。
- Obsidian callout 用于真正的提醒，不用于普通正文：

```markdown
> [!IMPORTANT]
>
> **【核心结论】** 二进制系统中 $R_b=R_B$。

> [!NOTE]
>
> 补充机制、边界条件、实现细节。
```

- 课程笔记可用普通引用块当小标题：`> 公式`、`> 结论`、`> 示例`、`> 判断方法`。
- 技术笔记的 callout 常带方括号标签：`【核心定位】`、`【重难点 / 架构】`。
- 一个 callout 只讲一件事；不要整节内容都塞进 callout。

## 9. 图表与视觉

- 图统一用 drawio 导出的 `.svg`，放在 `dio图表/<课程或主题>/`。
- 引用用相对路径：`![第4章.drawio](../../dio图表/信号与系统/第4章.drawio.svg)`。
- 需要控制大小时用 `<img src="..." alt="..." style="zoom:120%;" />`。
- 新建架构图遵守：黑白灰三色、节点黑色实线、分层用灰色 subgraph、连线标注动作语义、禁止彩色装饰。
- 图的 alt 文本写清图的内容，不写「图片1」。
- 能用表格说清的对比，不必画图。

## 10. 呈现思路

组织内容时按以下路径之一展开，不要平铺直叙：

1. **自顶向下**：先给整体框架 / 分层，再逐层展开。适合中间件、网络协议、系统设计。
2. **定义 → 机制 → 示例 → 边界**：适合课程概念和语言特性。
3. **对比式**：A vs B，先给对比表，再逐项解释差异与适用场景。
4. **流程式**：按时间 / 调用顺序列出 1. 2. 3.，适合执行链路、协议交互、故障恢复。
5. **分层式**：接入层 → 服务层 → 消息层 → 存储层，适合架构笔记。
6. **问题驱动**：先给问题或现象，再给原因、方案、代价。适合调优与排查。
7. **结论前置**：工程类笔记先给核心结论，再展开论证；课程笔记则通常先定义后结论。

每节开头用一句话点明「这一节解决什么问题」，但不要写成段落。

## 11. 可检索性与可维护性

- **标题即索引**：标题用名词短语，不用「概述」「其他」「补充」这类空标题。
- **关键词前置**：`**核心职责：路由管理与服务发现**`，先给结论词，再解释。
- **一节一概念**：不要把两个无关知识点塞进同一个 `###`。
- **术语统一**：同一个概念全文用同一个词；首次出现可中英对照，后文不反复切换。
- **符号统一**：同一符号全文含义一致；换符号时明确说明。
- **独立可读**：每节脱离上下文也能读懂，不依赖「上面说过」。
- **便于追加**：新知识按主题插入对应 `##` / `###`，不改动其他节。
- **交叉引用**：相关章节用「具体可参考××笔记」一句话带过，不复制内容。

## 12. 不同笔记类型的编排差异

| 维度 | 课程理论 | 编程语言 | 中间件 / 架构 | 网络协议 |
|---|---|---|---|---|
| 开头 | 直接给定义 / 公式 | `核心职责` | `核心职责` 或架构图 | 定义 + 作用 |
| 主体 | 公式推导 + 例题 | 用法 + 约束 + 代码 | 机制 + 架构设计 + 流程 | 报文 / 流程 + 字段 |
| 重点 | 计算正确、条件完整 | 语法边界、易错点 | 高并发、高可用、底层原理 | 交互过程、排查 |
| 示例 | 数值例题 | 最小可运行代码 | 生产场景 / 配置 | 抓包 / 命令输出 |
| 结尾 | `# 课后习题` | 练习题 | 面试常考 / 调优 | 对比表 / 排查清单 |
| 语气 | 解释性稍强 | 精确、克制 | 去比喻、架构视角 | 机制说明为主 |

## 13. 工作流

默认按「大纲 → 确认 → 分块写入」执行：

1. **确认范围**：明确要写哪一章 / 哪一节、参考什么资料、写到什么深度。
2. **先列大纲**：只给 `#` / `##` / `###` 骨架，不写正文；大型笔记可单独建 `_大纲.md`。
3. **等确认**：大纲通过后再写；用户要求一次成文时除外。
4. **分块写**：一次写一个知识块或一个小节，写完告知「已写入……」。
5. **不擅自扩写**：不加入用户没要求的知识点、例子、总结。
6. **保持术语一致**：新写内容沿用已有笔记的槽位词和命名。
7. **完成后自检**：按第 16 节清单过一遍。

写入前说明将要写什么，写入后说明写了什么；不要静默大段改写。

## 16. 八股 / 面试题变体

当写作目标是面试八股，而不是学习笔记时，切换以下规则：

- **单位是问题**：每个 `##` 是一道面试官能直接问出的题，标题用问法；不以知识点标题展开。
- **只收高频**：必会 > 高频 > 加分；低频、偏门、纯学术细节不写，或只留一行「加分项」。
- **结论先行**：第一句给结论，随后 2~3 个支撑点；口述长度控制在 30 秒~2 分钟。
- **不展开教材**：不写完整定义和推导；需要时用对比表、一行公式、短代码。
- **标注优先级**：`[必会]`、`[高频]`、`[加分]`；复习先清必会。
- **答案结构**：结论 → 关键机制 → 对比 / 边界 → 常见追问。
- **项目挂载**：只在对口时补一句，不强行关联。
- **复盘分离**：个人错题记录单独放，模块文件只写标准答案。
- **一题一屏**：答案尽量在一屏内读完。

参考：`实习记录/面经/八股/模块规划.md`。

## 18. 反面模式

- ❌ 用大段散文解释一个本可以用列表说清的概念。
- ❌ 每个知识点都写成「是什么、为什么、怎么做」三段落。
- ❌ 公式堆在一起不解释变量。
- ❌ 例题只给答案，不给推导。
- ❌ 代码贴一大段，没有说明目的。
- ❌ 标题写成「概述」「其他」「补充说明」。
- ❌ 同一概念一会儿中文一会儿英文。

# Roadmap

## 0. 适用范围

- 读者：自己、协作方、导师或上级。
- 用途：把目标拆成可执行、可跟踪、可调整的阶段，回答「现在做到哪、下一步做什么、卡在哪里」。
- 组织轴：时间 + 依赖。
- 结尾：变更记录 + 下一步。
- 更新：持续维护；状态按周更新，变更留痕。

通用规则见 [01-通用规范](01-通用规范.md)。

## 1. 核心原则

1. **Roadmap 不是待办清单**：待办是「做什么」，Roadmap 是「哪个阶段交付什么、怎么验收」。
2. **每个阶段一个主目标**：阶段内可以有多项任务，但只能有一个主目标。
3. **交付物可验收**：交付物必须是名词或动词短语，能被检查；「学习 XX」不算交付物。
4. **验收标准可检验**：写清「做到什么程度算完成」，不写「基本掌握」。
5. **状态必须更新**：过期状态比没有状态更危险。
6. **完成和取消都保留**：不删除历史，只标记状态和原因。
7. **日期绝对化**：写 `2026-11-10`，不写「下周」「月底」。
8. **依赖和阻塞显式化**：卡在谁、下一步是什么、预计何时解除。
9. **任务功能化**：每个阶段再拆成以功能为单位的任务，用有序列表从前往后罗列，不写任务级工期与负责人。

## 2. 文档骨架

```markdown
# <目标> Roadmap

> **文档状态**：已定稿
> **执行状态**：进行中
> **版本**：v1.0
> **更新**：2026-11-03
> **周期**：2026-11-03 ~ 2027-02-28
> **目标**：一句话
> **当前阶段**：P1
> **下一步**：……

## 1. 目标与边界

## 2. 阶段总览

## 3. 阶段明细

## 4. 依赖与风险

## 5. 变更记录
```

### 各节职责

| 节 | 必须回答 | 不写什么 |
|---|---|---|
| 目标与边界 | 成功标准、非目标、约束 | 激励性文字 |
| 阶段总览 | 一共有几个阶段、各自时间与状态 | 任务流水账 |
| 阶段明细 | 每个阶段的目标、交付物、验收、依赖，以及按序罗列的任务 | 与总览重复的整表 |
| 依赖与风险 | 什么会拖慢进度、怎么应对 | 泛泛的「有风险」 |
| 变更记录 | 改了什么、为什么、影响什么 | 日常任务打卡 |

## 3. 槽位词表

| 槽位 | 含义 | 示例 |
|---|---|---|
| `目标` | 最终要达成的结果 | 独立完成 gRPC 上报链路改造并上线 |
| `成功标准` | 可量化的完成判据 | P99 < 50ms；断连 30s 内自动恢复 |
| `非目标` | 明确不做的事 | 不做多租户隔离 |
| `约束` | 时间、资源、技术、外部依赖 | 每周可投入 10h；依赖 etcd 上线 |
| `主目标` | 当前阶段唯一的核心目标 | 打通 probe → receiver 直连 |
| `交付物` | 阶段结束时能拿出来的东西 | 设计文档、可运行代码、测试报告 |
| `验收标准` | 怎么判断交付物合格 | 单实例链路跑通；异常断连可恢复 |
| `依赖` | 前置阶段、外部资源、人 | 依赖 P0 的 proto 定义 |
| `阻塞项` | 当前阻止推进的具体问题 | 测试环境 etcd 未就绪 |
| `风险` | 可能影响进度或质量的因素 | 连接数超限导致上报中断 |
| `负责人` | 谁推进 | 自己 / 导师 / 运维 |
| `周期` | 开始与结束日期 | 2026-11-03 ~ 2026-11-16 |
| `状态` | 固定词表 | 未开始 / 进行中 / 阻塞 / 已完成 / 已取消 |
| `下一步` | 解除阻塞或推进的动作 | 11-05 前找运维开通 etcd 权限 |

## 4. 阶段拆分规则

- 每个阶段建议 1~4 周；超过 4 周必须再拆里程碑。
- 阶段按依赖排序，不按「想做的顺序」排序。
- 每个阶段只设一个主目标；同一阶段出现两个主目标时拆阶段。
- **每个阶段自带测试**：一个完整阶段 = 功能实现 + 单元测试 + 集成测试，测试随功能同阶段收口，不设单独的「测试阶段」。
- 阶段之间要有明确入口和出口：上一阶段的交付物是下一阶段的输入。
- 阶段数量控制在 3~7 个；超过 7 个时先合并或分层。
- 阶段命名用「动词 + 对象」或「名词 + 结果」，如 `P1 打通直连链路`、`P2 多实例容灾`。
- 不用「阶段一」「阶段二」这类无信息标题；编号可以保留，名称必须有意义。

### 交付物写法

| 不要写 | 应该写 |
|---|---|
| 学习 gRPC | 产出 `resolver + lb` 最小示例，能跑通一次 RPC |
| 优化性能 | 把 P99 从 120ms 降到 50ms，附压测报告 |
| 写测试 | 覆盖 5 条主链路 + 3 条异常链路，附测试报告 |
| 调研中间件 | 产出 3 个候选的对比表 + 推荐结论 |
| 看源码 | 产出调用链路图 + 关键函数清单 |

### 验收标准写法

- 用可观察的结果描述，不用主观判断。
- 能自动化就写自动化：单测、压测、脚本、CI。
- 不能自动化就写检查步骤：命令、页面、日志、数据库查询。
- 验收标准至少 1 条，建议 3 条以内；超过 5 条说明阶段太大。

示例：

```markdown
- **验收标准**
  - [ ] `go test ./...` 全部通过。
  - [ ] 单 probe → 单 receiver 连续上报 30 分钟，无丢数据。
  - [ ] 手动断连 receiver，30s 内自动重连，日志无 panic。
```

### 阶段任务罗列

每个阶段下的任务由执行者（人或 agent）在开工前自行拆分，直接用有序列表从前往后列出，不加标签、不加字段。

- **单位是功能**：一条任务对应一个可独立完成、可独立验证的功能切片，不是「写代码」「改 bug」「联调」这类动作。
- **拆到不可再分**：一条任务只动一个功能面；出现「并且」「同时」「顺便」就拆成两条。
- **顺序即依赖**：从 1 连续编号，前一条的产出是后一条的输入；无依赖时按「先通路、后增强」排。
- **测试随任务走**：实现类任务之后紧跟该功能的单元测试；阶段末尾补一条集成测试任务，验证本阶段新增功能在完整链路上生效。
- **不跨阶段**：一条任务只属于一个阶段，跨阶段说明粒度没拆开。
- **只写任务**：不写工期、负责人、状态、工时，这些由阶段级字段承担。
- **命名**：动词 + 对象 + 产出物，如「实现 `TokenBucket`：`Allow(now)` 按 elapsed × qps 补令牌，上限 burst」。
- **已完成阶段保留任务列表**，供复盘，不删除。

示例（同一个阶段，两种粒度）：

| 不要写 | 应该写 |
|---|---|
| 写限流 | 实现 `TokenBucket`：按 elapsed × qps 补令牌，上限 burst |
| 做限流 filter | 实现 `RateLimitFilter`：按 `req.RouteID` 分发到对应 `Limiter`；路由无配置时放行 |
| 改配置和编译 | `RouteRuleConfig` 增 `RateLimit{QPS,Burst}`；`Calculate` 展平成参数表 |
| 补测试 | `rate_limit` 单测覆盖放行 / 超限 429 / 无参数放行 / 并发安全 |
| 写完功能再统一补测试 | 实现任务后紧跟该功能单测；阶段末一条集成测试任务收口 |

## 5. 状态、日期与依赖

### 状态词表

| 状态 | 含义 | 使用条件 |
|---|---|---|
| 未开始 | 还没动 | 没有开始任何工作 |
| 进行中 | 正在做 | 已投入时间且有进展 |
| 阻塞 | 无法推进 | 有明确外部阻塞，不是单纯排期不足 |
| 已完成 | 验收通过 | 验收标准全部满足 |
| 已取消 | 不再做 | 写明原因和替代方案 |

- 不用「差不多」「快好了」「基本完成」。
- `阻塞` 必须跟 `阻塞项`：卡在什么、谁负责、下一步、预计解除日期。
- 已完成阶段保留在文档中；如果文档过长，移到 `归档` 节，不删除。

### 日期规则

- 全部用 `YYYY-MM-DD`。
- 周期写「开始 ~ 结束」，不写「两周左右」。
- 逾期未完成时更新状态和原因，不改历史日期。
- 里程碑日期变化时写入变更记录。

### 依赖规则

- 依赖分三类：阶段依赖、资源依赖、人的依赖。
- 每条依赖写清：依赖什么、谁提供、什么时候需要、没有它怎么办。
- 外部依赖没有承诺时，标 `**风险**`，不要当成已确定条件。

## 6. 开发型与学习型 Roadmap

### 开发型

- 交付物：代码、配置、接口、测试、文档、上线结果。
- 验收标准：功能可用、异常可恢复、指标达标、可回滚。
- 每阶段补一句「怎么验证」和「怎么回滚」。
- 上线相关阶段必须写：灰度、监控、回滚、负责人。

### 学习型

- 交付物：笔记、题目正确率、可运行项目、能讲清楚的输出。
- 验收标准：能独立复现、能解释原理、能做对题、能写代码。
- 「学习 XX」必须转成可观察结果，否则不算交付物。
- 学习型阶段可以按主题拆分，但每个主题仍要有验收标准。

示例：

| 不要写 | 应该写 |
|---|---|
| 学完 Go 并发 | 能独立写出 worker pool + 超时控制 + 优雅退出，附代码 |
| 看完 Redis | 能画出 Redis 单线程模型，解释 6 种数据结构底层编码 |
| 准备面试 | 八股必会题 100 题能口述 80% 以上，附错题清单 |

## 7. 更新与变更

- 每周更新一次状态；有阻塞时当天更新。
- 更新时只改状态、日期、下一步和变更记录，不重写已完成内容。
- 变更记录表：

  | 日期 | 变更 | 原因 | 影响 |
  |---|---|---|---|
  | 2026-11-03 | P2 延后一周 | etcd 权限未开通 | 总周期 +5 天 |
  | 2026-11-08 | 取消 P3 多租户 | 需求变更 | 范围缩小 |

- 阶段取消时，写清：取消原因、已完成部分、替代方案、对后续阶段的影响。
- 不把变更记录写成日志流水；只记影响计划的变化。

## 9. 检查清单

- [ ] 每个阶段有且只有一个主目标。
- [ ] 每个阶段有交付物和验收标准。
- [ ] 交付物可验收，不是「学习 / 优化 / 调研」这类空动词。
- [ ] 验收标准可检验，能落到命令、指标、日志或产物。
- [ ] 每个阶段都包含对应功能的单元测试与集成测试，没有单独的「测试阶段」。
- [ ] 每个阶段都有按序编号的任务列表，一条任务对应一个功能切片。
- [ ] 任务没有跨阶段，也没有「并且 / 同时」式复合任务。
- [ ] 任务不写工期、负责人、状态。
- [ ] 日期全部绝对化，周期明确。
- [ ] 依赖和阻塞项有负责人、下一步和预计解除日期。
- [ ] 风险有概率、影响和应对，不是泛泛而谈。
- [ ] 已完成、已取消的条目保留，取消有原因。
- [ ] 状态用固定词表，没有「差不多」「基本完成」。
- [ ] 没有待办流水账、激励语和情绪化表达。
- [ ] 变更记录有日期、原因和影响。

## 10. 反面模式

- ❌ 把 Roadmap 写成按天排列的待办清单。
- ❌ 只有时间，没有交付物和验收标准。
- ❌ 把测试单独拆成一个阶段，或先写完所有功能再统一补测试。
- ❌ 任务写成「写代码」「改 bug」「联调」这类没有产出的动作。
- ❌ 一条任务跨两个阶段，或按人、按天排列任务。
- ❌ 给每条任务加预估工时、负责人、截止日期。
- ❌ 阶段目标写成「学习 XX」「优化 XX」「调研 XX」。
- ❌ 一个阶段塞进多个主目标，导致无法判断是否完成。
- ❌ 状态长期不更新，文档与实际进度脱节。
- ❌ 阻塞项只写「卡住了」，不写卡在谁、下一步是什么。
- ❌ 风险只写「可能有风险」，没有概率、影响和应对。
- ❌ 完成项删除，导致无法复盘。
- ❌ 用「加油」「冲刺」「努力」代替计划。

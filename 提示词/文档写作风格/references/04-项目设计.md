# 项目设计

## 0. 适用范围

- 读者：实现者、联调方、Code Reviewer、未来的自己。
- 用途：让实现者知道系统由哪些组件组成、每个组件怎么实现、组件之间怎么交互、改哪些文件、怎么验证。
- 组织轴：组件全景 → 组件设计与实现 → 组件交互 → 数据与状态 → 异常与边界 → 落地与验证。
- 结尾：改动清单 + 验证方式。
- 更新：持续维护；组件、接口、链路变更留版本和变更记录。
- 输入：已确定的实现范围；选型过程见 [05-调研分析](05-调研分析.md)。

通用规则见 [01-通用规范](01-通用规范.md)。

## 1. 核心原则

1. **第一屏给组件全景**：有哪些组件、各自职责、主链路怎么走、改动落在哪。
2. **组件写到能开工**：职责、边界、依赖、内部状态、实现要点、文件落点，缺一项就还不能开工。
3. **交互写到能联调**：调用方、被调方、传什么数据、什么顺序、超时和失败怎么处理。
4. **接口给定义**：签名、结构体、IDL、字段约束，不写散文。
5. **流程给链路**：入口、调用顺序、分支、结束状态、异常出口。
6. **实现给落点**：关键分支给伪代码或短代码，标明文件 / 函数，不贴完整实现。
7. **状态写生命周期**：谁创建、谁更新、谁销毁，并发下怎么保护。
8. **改动精确到文件**：每个组件对应到文件、函数、配置，并标改动标记。
9. **验证可执行**：每条主链路和异常链路都有可复现的验证方式。
10. **不写代码教程**：设计文档解释「组件怎么实现」，不是「这个 API 怎么用」。

### 各节职责

| 节 | 必须回答 | 不写什么 |
|---|---|---|
| 组件全景 | 有哪些组件、依赖方向、主链路 | 大段背景、技术教程 |
| 组件设计与实现 | 每个组件怎么实现、落在哪个文件 | 完整实现代码 |
| 组件交互 | 组件怎么调用、传什么、失败怎么办 | 只有图、没有语义 |
| 数据与状态 | 数据长什么样、状态怎么迁移、配置怎么生效 | 与本次改动无关的表 |
| 异常、边界与可观测性 | 错误从哪来、怎么传播、怎么发现 | 泛泛的「有风险」 |
| 落地与验证 | 改哪些文件、怎么兼容、怎么验证 | 「自测通过」 |

## 3. 槽位词表

| 槽位 | 含义 | 示例 |
|---|---|---|
| `组件` | 独立实现、可独立验证的模块 | `ReceiverClient`、`ProbeSource` |
| `核心职责` | 组件负责什么 | 维护 gRPC stream 并上报数据 |
| `职责边界` | 组件不负责什么 | 不解析地址、不做业务聚合 |
| `依赖` | 组件依赖的其他组件 / 外部资源 | gRPC `ClientConn`、`Resolver` |
| `被依赖` | 谁调用它 | `probe.Post()` |
| `内部状态` | 组件持有的状态、所有权、并发保护 | `stream`（`mu` 保护）、`lastErr` |
| `生命周期` | 创建、启动、运行、关闭 | `New()` → 首次 `Post()` 建流 → `Close()` |
| `实现要点` | 关键分支、算法、并发控制 | stream 为 nil 时惰性创建，持锁检查 |
| `文件落点` | 组件实现所在的文件 / 包 | `internal/probe/client/receiver.go` |
| `接口` | 签名、IDL、结构体、字段 | `Post(ctx, content) error` |
| `调用方` | 谁发起调用 | `probe.Post()` |
| `被调方` | 谁接收调用 | `ReceiverClient.SendMessage()` |
| `交互数据` | 传什么、格式、约束 | `content []byte`，单条 ≤ 1MB |
| `调用语义` | 同步 / 异步、超时、重试、幂等 | 同步、超时 3s、不重试、按 msgID 幂等 |
| `并发归属` | goroutine / 线程池由谁创建和回收 | `ProbeSource` 持有 worker pool，上限 8 |
| `取消传播` | 超时与取消从哪注入、下层是否响应 | `ctx` 由 `Post()` 注入，透传到 `Send()` |
| `时序` | 调用顺序、分支、结束状态 | 启动、上报、落库、重连 |
| `数据模型` | 字段、类型、约束、索引、生命周期 | `t_dbha_status` 表结构 |
| `状态机` | 状态、事件、迁移条件、动作 | Disconnected → Connecting → Ready |
| `配置` | 配置项、默认值、作用组件、生效方式 | `channel.name: gse|grpc`，默认 gse |
| `错误传播` | 哪层抛出、包装、消化 | `Send` 返回 `Unavailable`，上层重置 stream |
| `边界条件` | 空值、超时、重复、乱序、超限、部分失败 | 空 `content` 直接返回 `InvalidArgument` |
| `可观测性` | 日志、指标、追踪、告警 | 连接数 Gauge、错误数 Counter |
| `改动点` | 文件 / 函数 / 配置的改动 | `receiver.go` 新增 `Name()` |
| `兼容处理` | 旧版本、旧配置、旧数据怎么办 | 默认走 GSE，`name` 切换 |
| `验证方式` | 命令、用例、可观察结果 | `go test -race ./...`；断连 30s 内恢复 |

### 改动标记

在组件标题、接口或改动清单前使用固定标记，表示相对本次设计的改动类型：

- `[沿用]`：本次不改，文档只说明其作用与交互。
- `[新增]`：本次新建的组件 / 接口 / 文件。
- `[改造]`：本次修改的组件 / 接口 / 文件。
- `[移除]`：本次删除的组件 / 接口 / 文件，写明替代者。

- 标记相对本次设计固定，不随实现进度改写。
- 不用「待定」「暂不考虑」「以后再说」这类未落地标记。

## 4. 组件设计与实现

### 组件清单

- 用表格列出全部组件，一个组件一行，先给全景再逐个展开。

| 组件 | 核心职责 | 文件落点 | 改动标记 |
|---|---|---|---|
| `probe.Reporter` | 定义上报接口 | `internal/probe/reporter.go` | 沿用 |
| `ReceiverClient` | 维护 gRPC stream 并上报数据 | `internal/probe/client/receiver.go` | 新增 |
| `ProbeSource` | 接收并落库 probe 上报 | `internal/receiver/source/probe.go` | 改造 |

### 组件划分规则

- 一个组件一个 `##`，标题写组件名，不写「模块 A」。
- 一个组件只有一个核心职责；出现两个职责时拆成两个组件。
- 依赖单向，不出现循环依赖；被依赖关系在第 5 节写成链路，不在本节展开。
- 组件粒度以「能落到包 / 文件」为准；落不到文件的，说明还没拆够。
- 组件必须能独立验证；不能独立验证时先补构造方式和依赖注入。
- 每个组件写全：职责边界、依赖与被依赖、内部状态、生命周期、实现要点、关键分支、文件落点。
- 不把部署拓扑和代码分层混在一张图里；需要时分开画。

### 组件卡片

每个组件用固定槽位展开，写到照着就能开工：

````markdown
## 2.1 ReceiverClient [新增]

- **核心职责**：维护 gRPC stream，向 receiver 上报数据。
- **职责边界**：不解析地址、不选择 receiver、不做业务聚合。
- **依赖**：gRPC `ClientConn`；`Resolver` 提供地址。
- **被依赖**：`probe.Post()`。
- **内部状态**：`stream`（`mu` 保护）、`lastErr`、`closed`。
- **生命周期**：`New()` 创建 → 首次 `Post()` 惰性建流 → `Close()` 关闭。
- **实现要点**
  1. 惰性建流：`stream == nil` 时调 `createStream()`，持锁检查，避免并发重复建流。
  2. 失败重建：`Send()` 返回错误时置 `stream = nil`，下一次 `Post()` 重建。
  3. 幂等关闭：`Close()` 用 `sync.Once`。
  4. 取消传播：`ctx` 透传给 `Send()`，超时由调用方控制。
- **关键分支**

  ```go
  func (c *ReceiverClient) Post(ctx context.Context, content []byte) error {
      stream, err := c.getOrCreate(ctx)
      if err != nil {
          return err
      }
      if err := stream.Send(&pb.Message{Content: content}); err != nil {
          c.resetStream()
          return err
      }
      return nil
  }
  ```

- **文件落点**：`internal/probe/client/receiver.go`。
````

规则：

- **实现要点**按可检查的动作写，不写「处理好并发」这类空话。
- **关键分支**只给最少代码，能说明分支即可；完整实现以文件落点为准。
- **内部状态**写清所有权和并发保护方式：锁、原子、channel、不可变。
- **生命周期**写清创建者、启动顺序、关闭顺序、异常时谁来清理。
- 依赖外部资源时写清初始化失败的行为：阻塞启动 / 降级 / 报错退出。

## 5. 组件交互

### 交互清单

- 用表格先列全部交互，再逐条展开；一条交互一行，不合并多个调用。

| 调用方 | 被调方 | 接口 | 交互数据 | 调用语义 | 失败处理 |
|---|---|---|---|---|---|
| `probe.Post()` | `ReceiverClient` | `Post(ctx, content)` | `content []byte`，单条 ≤ 1MB | 同步、超时 3s、不重试 | 返回错误，上层记录并丢弃 |
| `ReceiverClient` | `ReceiverServer` | `SendMessage()` | `pb.Message{msgID, content}` | 流式、按 msgID 幂等 | 重置 stream，下次重建 |
| `ProbeSource` | `sink` | `Write(row)` | `StatusRow` | 批量、10s 刷盘 | 重试 3 次，仍失败告警 |

### 接口定义

- 给签名、结构体、IDL 或请求 / 响应示例。
- 标注：输入、输出、错误码、幂等性、超时、重试语义、并发安全。
- 接口变更写兼容处理：新增字段是否可选、旧调用方是否可用、默认值是什么。
- 不贴完整实现；只在关键分支给伪代码或短代码。

示例：

```go
type Reporter interface {
    Name() string
    Post(ctx context.Context, content []byte) error
    GetBaseInfo() BaseInfo
    Close() error
}
```

### 调用链路与时序

- 用有序列表或调用链代码块，按时间顺序展开。
- 每条链路写清：入口、关键分支、出口、结束状态。
- 异常链路单独列出，不混在正常链路里。
- 调用链只保留关键函数，不贴整棵调用树。
- 需要时序图时用黑白灰；节点黑色实线，分层用灰色 subgraph，连线标注动作语义。
- 每张图后给一句话结论，不复述图中所有节点。

示例：

```text
probe.Post()
  -> ReceiverClient.Post()
     -> getOrCreate()          // stream == nil 时建流
     -> stream.SendMessage()
        -> ProbeSource.OnMessage()
           -> sink.Write()
```

- **结束状态**：stream 保持就绪，`StatusRow` 已落库。
- **异常链路**：`Send()` 失败 → `resetStream()` → 返回错误 → 上层告警；stream 置空，下次 `Post()` 重建。

### 并发与生命周期

- **并发归属**：goroutine / 线程池由谁创建、谁回收、数量上限。
- **共享状态**：谁读写、锁粒度、是否有无锁路径。
- **启动与关闭**：依赖方与被依赖方的先后顺序，等待中的请求怎么处理。
- **取消传播**：`ctx` / 超时从哪一层注入，下层是否响应取消。
- **背压**：队列容量、满时的行为（阻塞 / 丢弃 / 降级）。

### 数据流转

- 写清数据从哪来、经过哪些组件、在哪转换、在哪落盘。
- 每次格式转换标出：输入结构、输出结构、字段映射、丢失了什么。
- 写清跨组件传递的标识：`msgID` / `traceID`，以及怎么贯穿全链路。

## 6. 数据与状态

### 数据模型

- 给表 / 结构体 / 文档结构，标字段类型、约束、默认值、索引。
- 写清数据生命周期：谁写、谁读、保留多久、怎么清理。
- 写清哪个组件持有、哪个组件修改。

| 字段 | 类型 | 约束 | 默认值 | 说明 |
|---|---|---|---|---|
| `msg_id` | string | 非空、唯一 | — | 幂等键 |
| `content` | bytes | ≤ 1MB | — | 上报内容 |
| `created_at` | int64 | 非空 | `now()` | 写入时间 |

- **索引**：`uk_msg_id(msg_id)`、`idx_created_at(created_at)`。
- **生命周期**：`ProbeSource` 写，状态查询读，保留 30 天，定时清理。

### 状态机

- 用表格列状态、事件、迁移条件、动作。

| 当前状态 | 事件 | 条件 | 下一状态 | 动作 |
|---|---|---|---|---|
| Disconnected | 首次 `Post()` | 地址可用 | Connecting | 建流 |
| Connecting | 建流成功 | — | Ready | 置 `stream` |
| Ready | `Send()` 失败 | 任意错误 | Disconnected | 置空 stream、记错误 |
| Ready | `Close()` | — | Closed | `sync.Once` 关闭 |

- 写清状态的持有组件、并发保护方式、异常时能否回到初始状态。

### 配置

| 配置项 | 类型 | 默认值 | 作用组件 | 生效方式 | 取值范围 |
|---|---|---|---|---|---|
| `channel.name` | string | `gse` | `probe` | 启动加载 | `gse` / `grpc` |
| `grpc.timeout_ms` | int | `3000` | `ReceiverClient` | 启动加载 | 100 ~ 30000 |

- 写清配置缺失、非法值、热更新失败时组件的行为。

## 7. 异常、边界与可观测性

### 错误传播

- 列出错误来源：网络、依赖、输入、并发、资源上限。
- 写清传播路径：哪一层抛出、哪一层包装、哪一层消化。
- 写清处理策略：重试、降级、熔断、丢弃、告警、人工介入。
- 写清错误码与调用方行为的对应关系。

| 错误 | 来源 | 传播 | 处理 | 调用方看到 |
|---|---|---|---|---|
| `Unavailable` | `Send()` 失败 | 原样返回 | 重置 stream、下次重建 | 本次上报失败 |
| `ResourceExhausted` | 连接数超限 | 包装为 `ErrBusy` | 退避 1s 重试 3 次 | 延迟或失败 |
| `InvalidArgument` | `content` 超限 | 直接返回 | 不重试 | 参数错误 |

### 边界条件

- 逐项写清：空值、超时、重复、乱序、超限、部分失败、并发写、启动期依赖不可用。
- 每个边界写清：触发条件、组件行为、对下游的影响。
- 每个异常都能回答：用户看到什么、日志里有什么、指标上怎么发现。

### 日志、指标与告警

- **日志**：关键事件、字段（组件名、msgID、耗时、错误码）、级别。
- **指标**：指标名、类型、维度、采集点，如连接数 Gauge、错误数 Counter。
- **告警**：触发条件、阈值、持续时间、通知对象。
- 每条异常链路对应到至少一个日志事件或指标。

## 8. 落地与验证

### 改动清单

- 用表格精确到文件 / 函数 / 配置，一个改动一行。

| 文件 / 模块 | 改动标记 | 改动内容 | 对应组件 | 验证方式 |
|---|---|---|---|---|
| `internal/probe/client/receiver.go` | 新增 | 实现 `Reporter` 接口，惰性建流与失败重建 | `ReceiverClient` | `go test -race ./internal/probe/client` |
| `internal/receiver/source/source.go` | 改造 | 新增 `case "probe"` | `ProbeSource` | 集成用例 TC-01 |
| `conf/probe.yaml` | 改造 | 新增 `channel.name` | `probe` | 默认配置回归 |

- 改动标记用第 3 节的固定词表，不自造同义词。
- 每个组件至少对应一行改动；标 `[沿用]` 的组件在组件卡片里说明为什么不动。

### 兼容与迁移

存量改造必须写：

1. **现状**：旧链路、旧配置、旧数据、旧接口。
2. **改动点**：新增什么、修改什么、删除什么。
3. **兼容策略**：默认行为是否不变；新旧字段如何共存；旧调用方是否可用。
4. **迁移步骤**：按 1. 2. 3. 列出，标每步的验证点。
5. **回滚操作**：触发条件、可执行步骤、回滚后的数据一致性处理、验证方式。

- 回滚步骤必须可执行，不写「回滚代码」四个字。
- 回滚不可行时明确写 `**不可回滚**` 和原因。

### 验证方式

- 用表格按组件、链路分行，给可复现的命令 / 步骤和预期结果。

| 验证项 | 范围 | 命令 / 步骤 | 预期结果 |
|---|---|---|---|
| 建流并发安全 | `ReceiverClient` | `go test -race ./internal/probe/client` | 无 data race，stream 只建一次 |
| 主链路连通 | probe → sink | 起单实例，连续上报 30 分钟 | 无丢数据，`StatusRow` 落库 |
| 断连恢复 | `ReceiverClient` | 手动断连 receiver | 30s 内重建 stream，无 panic |
| 参数边界 | `probe.Post()` | 传入空 `content` | 返回 `InvalidArgument`，不发 RPC |

- 每个组件给单元测试，组件之间给集成测试，主链路给端到端验证。
- 异常链路用注入方式验证：断连、超时、乱序、超限、依赖不可用。
- 验证结果写可观察输出：命令、日志、指标、数据库查询，不写「通过」。

## 9. 存量改造变体

当设计对象是现有系统时，用以下骨架替代第 2 节的通用骨架：

```markdown
# <项目> 改造设计

> **状态**：草稿
```

## 10. 更新与维护

- 状态词表沿用 [SKILL.md 第 4 节](../SKILL.md)：草稿 / 评审中 / 已定稿 / 已废弃。
- 组件、接口、链路变更时升版本，并在变更记录里写原因和影响。
- 更新时先读现有内容，增量修改，不静默重写。
- 移除的组件保留在改动清单里，标 `[移除]` 并写明替代者，不直接删除。
- 实现完成后用变更记录体现进度，不改写改动标记。
- 组件或接口与代码不一致时，先更新文档对应章节，再继续实现。

## 12. 检查清单

- [ ] 第一屏能回答：组件构成、主链路、改动落点。
- [ ] 组件清单给了核心职责、文件落点和改动标记。
- [ ] 每个组件写到能开工：职责边界、依赖与被依赖、内部状态、生命周期、实现要点、关键分支。
- [ ] 每个接口给了签名 / IDL / 结构体，并标了错误码、超时、幂等、重试、并发安全。
- [ ] 每条调用链路有入口、分支、出口、结束状态；异常链路单独列出。
- [ ] 调用语义、并发归属、取消传播、背压都写清了。
- [ ] 数据模型标了类型、约束、索引、生命周期；状态机标了迁移条件。
- [ ] 配置写了默认值、作用组件、生效方式和非法值行为。
- [ ] 异常有来源、传播路径、处理策略、可观测性。
- [ ] 改动清单精确到文件 / 函数，标了改动标记。
- [ ] 每条主链路和异常链路都有可复现的验证方式。
- [ ] 存量改造有现状、改动点、兼容策略、迁移步骤、回滚操作。
- [ ] 没有大段完整实现、代码教程、与组件无关的背景介绍。
- [ ] 版本、状态、变更记录完整。
- [ ] 图是黑白灰，连线有动作语义。

## 13. 反面模式

- ❌ 只给一张架构图，组件内部状态、实现要点、文件落点全都没有。
- ❌ 组件职责写成「负责处理逻辑」这类空话。
- ❌ 只列组件清单，不写组件之间怎么调用、传什么、失败怎么办。
- ❌ 接口用散文描述，没有签名或字段定义。
- ❌ 只写正常链路，不写异常、超时、重试、并发冲突。
- ❌ 贴大段完整实现，把设计文档写成代码清单。
- ❌ 改动清单只写模块名，不落到文件 / 函数。
- ❌ 验证方式写「自测通过」「应该没问题」。
- ❌ 存量改造不写兼容和迁移。
- ❌ 正文大段讲背景和范围，组件实现只有一段话。
- ❌ 组件、接口已变，文档和改动清单不更新。

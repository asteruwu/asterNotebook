# 项目设计

## 0. 适用范围

- 读者：评审者、导师、实现者、未来的自己。
- 用途：让评审者判断方案是否成立，让实现者知道改什么、怎么改、怎么验证。
- 组织轴：问题 → 约束 → 方案 → 决策 → 设计 → 落地。
- 结尾：待确认问题 + 风险。
- 更新：持续维护；方案变更留版本和变更记录。

通用规则见 [01-通用规范](01-通用规范.md)。

## 1. 核心原则

1. **第一屏给结论**：解决什么问题、采用什么方案、影响哪些模块、代价是什么。
2. **方案必须对比**：至少两个候选，包含「保持现状 / 不做」。
3. **每个决策写代价**：只写优点不写代价，视为分析不完整。
4. **接口给定义**：签名、结构体、IDL、字段约束，不写散文。
5. **流程给链路**：调用顺序、开始状态、结束状态、异常分支。
6. **存量改造写兼容**：现状、改动点、兼容策略、迁移步骤、回滚方案。
7. **待确认有 owner 和 deadline**：没有负责人的问题不是待确认，是隐患。
8. **不写代码教程**：设计文档解释「为什么这样设计」，不是「这个 API 怎么用」。

## 3. 槽位词表

| 槽位 | 含义 | 示例 |
|---|---|---|
| `核心问题` | 现在有什么问题，不解决会怎样 | GSE 通道断连后无自愈，数据静默丢失 |
| `目标` | 本次要达成的结果 | 打通 gRPC 直连通道，作为 GSE 的替代或补充 |
| `非目标` | 明确不做的事 | 不做多 receiver 地址管理 |
| `约束` | 技术、时间、兼容、外部依赖 | 不能改已约定的接口；需兼容旧配置 |
| `方案对比` | 候选方案与评估维度 | 自研 vs 成熟框架 vs 保持现状 |
| `决策` | 选哪个方案 | 采用 gRPC resolver + balancer |
| `理由` | 为什么选它 | 代码量少、职责清晰、重连已封装 |
| `代价` | 选它要付出什么 | 需要理解框架行为；定制能力受限 |
| `架构` | 组件、分层、部署关系 | probe → receiver → sink → MySQL |
| `模块职责` | 每个模块负责什么、不负责什么 | resolver 只解析地址 |
| `接口` | 签名、IDL、结构体、字段 | `Post(ctx, content) error` |
| `数据模型` | 字段、约束、索引、生命周期 | `t_dbha_status` 表结构 |
| `关键流程` | 主链路、分支、异常路径 | 启动、上报、持久化、重连 |
| `异常与边界` | 错误从哪来、怎么传播、在哪消化 | 连接数超限返回 `ResourceExhausted` |
| `可观测性` | 日志、指标、追踪、告警 | 连接数 Gauge、错误数 Counter |
| `改动清单` | 文件、函数、配置的改动 | `receiver.go` 新增 `Name()` |
| `兼容与迁移` | 旧版本、旧配置、旧数据怎么办 | 默认走 GSE，`name` 切换 |
| `回滚` | 出问题怎么退回去 | 配置改回 GSE，不删旧代码 |
| `风险` | 技术、进度、运维风险 | 单 receiver 单点 |
| `待确认` | 还没定的事 | 是否需要自动切换通道 |

### 状态标记

在模块、接口或改动点前使用固定标记：

- `[已实现]`：代码已存在，文档只做说明。
- `[计划实现]`：本次要做的改动。
- `[待确认]`：方案未定，需要评审或实验。
- `[不做]`：明确排除，写明原因。

## 4. 方案对比与决策

### 对比表

至少包含「保持现状 / 不做」作为基线。

| 维度 | 方案 A | 方案 B | 保持现状 |
|---|---|---|---|
| 改动范围 | 小 / 中 / 大 | …… | 无 |
| 实现复杂度 | …… | …… | …… |
| 性能影响 | …… | …… | …… |
| 可维护性 | …… | …… | …… |
| 兼容性 | …… | …… | …… |
| 工期 | …… | …… | …… |
| 主要风险 | …… | …… | …… |

规则：

- 维度固定，不因方案不同而增删；需要增删时说明原因。
- 单元格写判断或数据，不写「较好」「一般」；必要时给判定标准。
- 对比表之后只解释「不显然」的格子，不复述整张表。
- 评分只在权重和评分标准明确时使用；不制造虚假精确。

### 决策记录

每个关键决策写成：

```markdown
### 决策：采用 gRPC resolver + balancer

- **选项**
  1. 自研地址管理与重连
  2. gRPC resolver + balancer
  3. 保持现状，仅用本地配置
- **选择**：方案 2。
- **理由**
  1. 代码量最小，不需要改现有数据结构。
  2. resolver 与 balancer 职责清晰，重连已封装。
  3. 后续多地址场景可直接扩展。
- **代价**
  1. 需要理解框架的 resolver / picker 行为。
  2. 定制能力受框架限制。
- **验证**：单实例链路跑通；断连后 30s 内恢复。
```

规则：

- 一个决策一个 `###`。
- 「理由」和「代价」都必须有；没有代价说明还没想清楚。
- 「验证」写可执行的检查，不写「应该没问题」。

## 5. 架构、接口与流程

### 架构

- 先给分层或组件图，再逐层说明职责。
- 图用黑白灰；节点黑色实线；分层用灰色 subgraph；连线标注动作。
- 每层写：负责什么、不负责什么、依赖谁、被谁依赖。
- 不把部署拓扑和代码分层混在一张图里；需要时分开画。

### 接口

- 给签名、结构体、IDL 或请求 / 响应示例。
- 标注：输入、输出、错误码、幂等性、超时、重试语义。
- 接口变更必须写兼容策略：新增字段是否可选、旧客户端是否可用、默认值是什么。
- 不贴完整实现；只在关键分支给伪代码或短代码。

示例：

```go
type Reporter interface {
    Name() string
    Post(ctx context.Context, content []byte) error
    GetBaseInfo() BaseInfo
    Close() error
}
```

### 数据模型

- 给表 / 结构体 / 文档结构，标字段类型、约束、默认值、索引。
- 写清数据生命周期：谁写、谁读、保留多久、怎么清理。
- 涉及迁移时写：迁移步骤、双写 / 双读、回滚条件。

### 关键流程

- 用有序列表或调用链代码块，按时间顺序展开。
- 每条流程写清：入口、关键分支、出口、结束状态。
- 异常路径单独列出，不混在正常流程里。
- 调用链只保留关键函数，不贴整棵调用树。

示例：

```text
probe.Post()
  -> ReceiverClient.SendMessage()
     -> stream == nil ? createStream() : stream.Send()
        -> monitorConnection()
```

## 6. 异常、兼容与回滚

### 异常与边界

- 列出错误来源：网络、依赖、输入、并发、资源上限。
- 写清传播路径：哪一层抛出、哪一层包装、哪一层消化。
- 写清处理策略：重试、降级、熔断、丢弃、告警、人工介入。
- 写清边界条件：空值、超时、重复、乱序、超限、部分失败。
- 每个异常都要能回答：用户看到什么、日志里有什么、指标上怎么发现。

### 兼容与迁移

存量改造必须写：

1. **现状**：旧链路、旧配置、旧数据、旧接口。
2. **改动点**：新增什么、修改什么、删除什么。
3. **兼容策略**：默认行为是否不变；新旧字段如何共存；旧客户端是否可用。
4. **迁移步骤**：按 1. 2. 3. 列出，标每步的验证点。
5. **回滚条件**：出现什么现象必须回滚；回滚怎么操作。

### 回滚

- 回滚方案必须是可执行的，不写「回滚代码」四个字。
- 写清：回滚触发条件、回滚步骤、回滚后的数据一致性处理、验证方式。
- 如果回滚不可行，明确写 `**不可回滚**` 和原因，并在上线前升级评审级别。

## 8. 更新与评审

- 设计文档评审前必须是 `草稿`；评审后改 `评审中`；确认落地后改 `已定稿`。
- 方案变更时升版本，并在变更记录里写原因和影响。
- 评审意见不直接删；用 `**评审意见**` 标明是否采纳。
- 已废弃方案保留在「方案对比」或「附录」中，写清为什么不选。
- 待确认问题必须有：问题、影响、负责人、截止日期、未决时的默认决策。

## 10. 检查清单

- [ ] 第一屏能回答：问题、方案、影响、代价。
- [ ] 方案对比至少两个候选，包含「保持现状 / 不做」。
- [ ] 每个决策都有选择、理由、代价、验证方式。
- [ ] 接口给了签名 / IDL / 结构体，不是散文描述。
- [ ] 关键流程有入口、出口、结束状态和异常分支。
- [ ] 异常来源、传播路径、处理策略、可观测性都说清了。
- [ ] 存量改造有现状、改动点、兼容策略、迁移步骤、回滚方案。
- [ ] 改动清单精确到文件 / 模块，并标了实现状态。
- [ ] 待确认问题有负责人、截止日期、未决时的默认决策。
- [ ] 没有代码教程、大段实现、与设计无关的背景介绍。
- [ ] 版本、状态、变更记录完整。
- [ ] 图是黑白灰，连线有动作语义。

## 11. 反面模式

- ❌ 只写方案，不写取舍和代价。
- ❌ 只列优点，不列缺点和风险。
- ❌ 方案对比只有一列，没有基线。
- ❌ 接口用散文描述，没有签名或字段定义。
- ❌ 把实现细节当设计，贴大段代码。
- ❌ 只写正常链路，不写异常、超时、重试、回滚。
- ❌ 存量改造不写兼容和迁移，默认「应该没问题」。
- ❌ 待确认问题没有负责人和截止日期。
- ❌ 设计文档写成项目介绍或技术教程。
- ❌ 方案变更不留版本和变更记录。

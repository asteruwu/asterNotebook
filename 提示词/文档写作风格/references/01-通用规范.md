# 通用规范

所有文档类型共享本文件的规则；类型文件只补充差异，不重复这里的内容。

## 1. 标题与骨架

- `#`：文档主题或一个功能分区。
- `##`：子主题。
- `###`：具体知识点、模块、阶段或用例组。
- 标题用名词短语，不用完整句子。
- 标题连起来能当目录；读目录就能知道文档讲了什么。
- 标题下空一行再写正文；层级不跳级。
- 正文不使用 `---` 分隔线；用标题分段。

### 编号规则

| 文档类型 | 是否编号 | 规则 |
|---|---|---|
| 学习笔记 | 不编号 | 文件名承载顺序；标题不写「第X章」 |
| Roadmap | 可编号 | 阶段用 `P0/P1/P2`，阶段内小节用 `1.1` |
| 项目设计 | 编号 | `# 1.`、`## 1.1`，便于评审引用 |
| 调研分析 | 编号 | `# 1.`、`## 1.1` |
| 测试报告 | 编号 | 章节编号；用例用 `TC-001`，缺陷用 `BUG-001` |

- 编号在同一文档内连续，不跳号。
- 不用「第一章」「第二节」这类文字编号。
- 标题本身不承载状态；状态放在文档头或条目内。

### 禁用标题

- 「概述」「其他」「补充」「杂项」「相关内容」。
- 「总结」单独成节时，必须是真正的结论收束，不是正文复述。

## 2. 原子块与槽位

每个信息块应能独立阅读，推荐结构：

```markdown
### 名称

- **标签**：一句话结论。

- **标签**
  1. ……
  2. ……

- **标签**

  | 列 | 列 |
  |---|---|
  | …… | …… |
```

规则：

- 标签独占一行，格式 `- **标签**：内容`，或 `- **标签**` 后换行缩进。
- 一个列表项只讲一件事；出现「另外」「同时」「顺便」时拆项。
- 先定义后展开；工程文档可先给结论再展开机制。
- 一个 `###` 只放一个概念；内容过多时拆成多个 `###`。
- 列表嵌套不超过 3 层；超过改用小标题分段。
- 块与块之间空一行，保持视觉呼吸。
- 同一文档内槽位词保持一致，不混用「职责 / 作用 / 定位」等同义词。

## 3. 列表、层级与表格

- 缩进统一 **2 个空格**。
- **无序列表**：平级知识、属性、组件、命令、风险。
- **有序列表**：流程、步骤、优先级、时间顺序、解题顺序。
- **表格**：对比、选型、状态汇总、指标、缺陷清单。
- 标签行：短句末尾不加句号，完整句子加句号；全文保持一致。
- 列表项内嵌公式时，公式缩进到列表项内容下，前后各空一行。
- 对比性内容一律用表格，表头加粗。
- 表格单元格不写长段落；超过两行说明应移到表外。
- 表格列宽按内容分配；数字列右对齐，文本列左对齐。
- 并列概念可用 `**A**` / `**B**` 分段，不必强行套列表。

### 表格最小列

| 场景 | 必需列 |
|---|---|
| 方案对比 | 维度、候选方案、结论或备注 |
| 阶段总览 | 阶段、周期、目标、交付物、状态 |
| 测试结果 | 用例 ID、场景、预期、实际、结果 |
| 缺陷汇总 | 缺陷 ID、级别、描述、状态、影响 |
| 风险 | 风险、概率、影响、应对、负责人 |

## 4. 语言风格

### 基本语气

- 全中文；术语、API、命令、字段名保留英文，如 `CommitLog`、`SETNX`、`&mut T`。
- 用陈述句和短句；一句话只表达一个判断。
- 动词开头，直接说「是什么 / 做什么 / 为什么」。
- 结论、易错点、关键术语用 `**加粗**`。
- 不寒暄、不设问、不感叹、不写「我们」开头的空话。
- 不用「可能」「大概」「应该」掩盖未验证的判断；确实不确定时标 `**推断**`。

### 连接词

学习笔记允许完整推导语气：

> 因为……，所以……；根据……；代入……；可得……；由此可得……；于是……。

工程文档压缩为：

> 负责……；通过……实现……；本质是……；对应……；区别在于……；代价是……。

### 禁止项

- 禁止通俗比喻（「就像一个仓库」「好比快递员」）。
- 禁止空泛评价（「非常重要」「十分强大」），除非后面紧跟具体原因。
- 禁止重复标题；标题已经说了，正文不要再说一遍。
- 禁止大段连续文字；超过 3 行没有列表 / 公式 / 代码 / 表格，就应改写。
- 禁止装饰性 emoji、彩色高亮、无意义分隔线。
- 禁止「如上所述」「显而易见」「众所周知」。
- 禁止把「业界最佳实践」当作证据；必须给来源或实测。

## 5. 公式

- 行内公式：`$...$`，前后留空格，如 `其中 $T$ 表示码元周期`。
- 块级公式：`$$` 独立成段，前后空行。
- 多行推导用 `aligned` 对齐等号：

```latex
$$
\begin{aligned}
y &= f(x) \\
  &= g(x)
\end{aligned}
$$
```

- 公式后必须解释符号：`其中 $x$ 表示……`。
- 中文单位、中文条件放 `\text{}`：`\text{bit/s}`、`\text{其他}`。
- 多个条件用 `\qquad` 分隔：`|z|>|a|,\qquad a>0`。
- 关键公式可单独再列一次结论；不要在正文里重复三遍。
- 公式汇总只保留「名称 + 公式 + 一句结论」，不写推导。

## 6. 代码

- 代码块必须标注语言：`go`、`rust`、`bash`、`sql`、`yaml`、`proto`。
- 代码前用一句话说明目的；代码后不逐行复述。
- 示例尽量最小可运行；保留必要的导入、类型标注和上下文。
- 只在非显然处写注释；错误示例用注释标出：

  ```go
  // ch <- v // 阻塞：channel 已满且无消费者
  ```

- 不贴大段无关输出；命令输出只保留关键行。
- 配置片段只展示改动字段，并保留必要上下文。
- 设计文档给接口签名、结构体或 IDL，不贴完整实现。
- 测试报告给可复现命令和关键输出，不贴完整日志。

## 7. 强调、提示与引用

- `**加粗**`：术语首次出现、关键结论、易错点、命令 / 字段名。
- Obsidian callout 用于真正的提醒，不用于普通正文：

```markdown
> [!IMPORTANT]
>
> **【核心结论】** 二进制系统中 $R_b=R_B$。

> [!NOTE]
>
> 补充机制、边界条件、实现细节。

> [!WARNING]
>
> 会导致数据丢失、发布阻塞或不可逆后果。
```

- 课程笔记可用普通引用块当小标题：`> 公式`、`> 结论`、`> 示例`、`> 判断方法`。
- 技术文档的 callout 常带方括号标签：`【核心定位】`、`【重难点 / 架构】`。
- 一个 callout 只讲一件事；不要整节内容都塞进 callout。
- 引用来源用普通链接或文末「来源」清单，不用 callout 伪装成提醒。

## 8. 证据与来源

### 证据分级

按可信度从高到低：

1. **实测**：可复现的实验、压测、抓包、日志。
2. **源码 / 配置 / 接口定义**：版本明确，路径可查。
3. **官方文档 / 标准 / RFC**：注明版本或发布日期。
4. **二手资料**：博客、文章、视频；只作为线索或观点。
5. **个人推断**：必须标注，不得写成事实。

### 标注规则

- 事实直接陈述，并用来源或数据支撑。
- 推断写成 `**推断**：……`，并给出依据和验证方式。
- 观点写成 `**观点**：……`，说明立场和适用条件。
- 来源格式：`来源：<标题>，<版本 / 日期>，<URL>`。
- 实验格式：`环境 / 命令 / 输入 / 输出 / 结论`。
- 数据必须给样本量、时间范围和测量方法。
- 不引用没读过的资料；不编造 URL、版本号、论文或数据。
- AI 生成的内容必须验证后才能写成事实；未验证的标 `**待验证**`。

## 9. 图表与视觉

- 图统一用 drawio 导出的 `.svg`，放在 `dio图表/<课程或主题>/`。
- 引用用相对路径：`![第4章.drawio](../../dio图表/信号与系统/第4章.drawio.svg)`。
- 需要控制大小时用 `<img src="..." alt="..." style="zoom:120%;" />`。
- 新建架构图遵守：黑白灰三色、节点黑色实线、分层用灰色 subgraph、连线标注动作语义、禁止彩色装饰。
- 流程图必须有开始、结束、判断分支和异常路径。
- 图的 alt 文本写清图的内容，不写「图片1」。
- 能用表格说清的对比，不必画图。
- 每张图后给一句话结论，不复述图中所有节点。
- 测试截图只保留关键区域，裁掉无关界面；alt 写明界面和状态。

## 10. 版本、状态与变更

- 工作文档必须有元信息块，见 [SKILL.md 第 4 节](../SKILL.md)。
- 状态词表固定，不自造。
- 持续维护的文档用变更记录：

  | 日期 | 变更 | 原因 | 影响 |
  |---|---|---|---|
  | 2026-11-03 | 初稿 | 方案评审 | 无 |

- 结构性修改升主版本，补充升次版本。
- 已完成、已取消的条目保留，不删除；取消项写明原因。
- 已废弃文档保留并标记 `已废弃`，不直接删除。
- 更新持续维护的文档时，先读现有内容，再增量修改；不静默重写。

## 11. 可检索性与可维护性

- **标题即索引**：标题用名词短语，不用空标题。
- **关键词前置**：`**核心职责：路由管理与服务发现**`，先给结论词，再解释。
- **一节一概念**：不要把两个无关知识点塞进同一个 `###`。
- **术语统一**：同一概念全文用同一个词；首次出现可中英对照，后文不反复切换。
- **符号统一**：同一符号全文含义一致；换符号时明确说明。
- **独立可读**：每节脱离上下文也能读懂，不依赖「上面说过」。
- **便于追加**：新内容按主题插入对应 `##` / `###`，不改动其他节。
- **交叉引用**：相关文档用「具体可参考××」一句话带过，不复制内容。
- **锚点稳定**：标题不频繁改名；确需改名时更新所有引用。

## 12. 改写对照

| 不要写 | 应该写 |
|---|---|
| 我们首先来了解一下什么是…… | `- **定义**：……` |
| 简单来说，它就像一个…… | `- **核心职责**：……` |
| 这个功能非常重要，大家要注意 | `> [!IMPORTANT]` + 具体后果 |
| 经过一系列复杂的处理之后 | 按 1. 2. 3. 列出处理步骤 |
| 由此我们可以得出结论 | `**结论**：……` |
| 预计下周完成 | `2026-11-10 前完成` |
| 性能有明显提升 | `P99 从 120ms 降到 45ms（样本 10k）` |
| 基本没问题 | `通过（3 个 P2 遗留，无 P0/P1）` |
| 业界最佳实践 | `来源：……；实测：……` |
| 参与 / 负责了…… | `交付 X，影响 Y，指标 Z` |
| 应该可以兼容 | `已用 v1.2 配置回归，旧字段保留，缺省行为不变` |
| 可能存在风险 | `风险：连接数超限；概率：中；影响：上报中断；应对：备用地址切换` |

## 13. 反面模式

- ❌ 用大段散文解释一个本可以用列表说清的概念。
- ❌ 每个知识点都写成「是什么、为什么、怎么做」三段落。
- ❌ 公式堆在一起不解释变量。
- ❌ 例题只给答案，不给推导。
- ❌ 代码贴一大段，没有说明目的。
- ❌ 标题写成「概述」「其他」「补充说明」。
- ❌ 同一概念一会儿中文一会儿英文。
- ❌ 用彩色图、装饰性图标、花哨分隔线。
- ❌ 在正文里写「如上所述」「显而易见」。
- ❌ 把总结写成又一遍正文。
- ❌ 结论没有证据，证据没有来源。
- ❌ 状态、日期、版本前后不一致。
- ❌ 同一结论在多个章节重复出现。

## 14. 通用检查清单

- [ ] 标题层级连续，标题连起来能当目录。
- [ ] 每个信息块有明确标签。
- [ ] 没有超过 3 行的纯文字段落。
- [ ] 对比内容用了表格，表格内没有长段落。
- [ ] 结论、建议或判断在开头能找到。
- [ ] 每个判断都有证据、来源或明确标注为推断。
- [ ] 公式后解释了符号，单位用 `\text{}`。
- [ ] 代码块标注语言，示例可运行或可复现。
- [ ] 列表嵌套不超过 3 层。
- [ ] 术语、符号、单位全文一致。
- [ ] 状态、日期、版本用词统一。
- [ ] 没有比喻、空话、装饰性 emoji、多余分隔线。
- [ ] 新内容能独立阅读，不依赖上下文。
- [ ] 没有重复标题、重复结论、重复内容。
- [ ] 图片路径正确，alt 文本有意义。

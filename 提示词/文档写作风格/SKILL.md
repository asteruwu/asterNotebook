# Aster 文档写作风格

## 0. 定位

一句话：**用同一套结构纪律覆盖所有文档；只替换组织轴和槽位，不替换表达底线。**

三条边界：

- 适用于：学习笔记、Roadmap、项目设计、调研分析、测试报告、工作总结。
- 不适用于：文学创作、对外营销文案、需要完整叙事的个人散文。
- 所有类型共享「通用硬规则」；类型差异只体现在读者、用途、组织轴、槽位、证据标准和结尾。

## 1. 四层模型

| 层 | 作用 | 是否可变 |
|---|---|---|
| 不变层 | 结构先行、标题即索引、标签槽位、列表化、去水存精、证据驱动 | 所有文档不变 |
| 类型层 | 读者、用途、组织轴、槽位词表、证据标准、结尾形态 | 按类型切换 |
| 状态层 | 状态、版本、日期、负责人、变更记录 | 工作文档必填，笔记可省 |
| 过程层 | 判类型 → 列骨架 → 等确认 → 分块写入 → 自检 | 所有文档不变 |

**先判类型，再定骨架，最后写内容。**

## 2. 类型路由

| 类型 | 一句话用途 | 组织轴 | 默认读者 | 参考 |
|---|---|---|---|---|
| 学习笔记 | 学会并记住 | 认知依赖：定义 → 机制 → 示例 → 边界 | 未来的自己 | [02-学习笔记](references/02-学习笔记.md) |
| Roadmap | 把目标拆成可执行、可跟踪的阶段 | 时间 + 依赖 | 自己 / 协作方 | [03-Roadmap](references/03-Roadmap.md) |
| 项目设计 | 让评审者判断，让实现者落地 | 问题 → 约束 → 方案 → 决策 → 落地 | reviewer / 实现者 | [04-项目设计](references/04-项目设计.md) |
| 调研分析 | 支撑一个决策 | 问题 → 结论 → 证据 → 对比 → 边界 | 决策者 / 自己 | [05-调研分析](references/05-调研分析.md) |
| 测试报告 | 证明质量，支持发布决策 | 范围 → 策略 → 用例 → 结果 → 结论 | 开发 / QA / 发布决策者 | [06-测试报告](references/06-测试报告.md) |
| 工作总结 | 汇报产出，沉淀经验 | 结果 → 过程 → 问题 → 下一步 | 上级 / 自己 | [07-工作总结](references/07-工作总结.md) |

判定顺序：

1. 读者是谁？
2. 读完要做什么决定或动作？
3. 内容按什么轴展开最省读者的力？
4. 选主类型；跨类型时以主用途为准，其他类型的槽位只作为附录。

## 3. 通用硬规则

1. **结构先行**：先有骨架再填内容；标题连起来能当目录。
2. **标题即索引**：标题用名词短语；禁用「概述」「其他」「补充」「杂项」。
3. **标签化**：每个信息块用固定槽位，格式 `- **标签**：内容`。
4. **列表化**：能列表不写段落；平级用无序，步骤用有序，对比用表格。
   - **分点先给短标签**：所有列表项先写 2–8 字重点标签，再写具体内容；标签用名词或动宾短语，不能是整句话。
5. **一段一义**：一个列表项只讲一件事；出现「另外 / 同时 / 顺便」就拆项。
6. **超过 3 行必改写**：连续文字超过 3 行，改为列表、表格、公式、代码或图。
7. **结论前置**：工程文档先给结论、建议或判断；学习笔记按认知顺序。
8. **证据驱动**：每个判断都有依据：实测、数据、代码、命令、公式或来源。
9. **去水存精**：删导语、过渡句、比喻、空泛评价、装饰性 emoji、无意义分隔线。
10. **术语统一**：同一概念全文一个词；首次中英对照，后文不切换。
11. **独立可读**：每节脱离上下文也能读懂；交叉引用只给链接，不复制内容。
12. **单一信息源**：同一结论只写一次；其他地方引用，不重复。

## 4. 文档头与状态

工作文档（Roadmap、项目设计、调研分析、测试报告、工作总结）在标题下放元信息块：

```markdown
> **状态**：草稿 | 评审中 | 已定稿 | 已废弃
> **版本**：v1.0
> **更新**：2026-11-03
> **读者**：……
> **结论**：一句话
```

- 状态词表固定，不自造同义词。
- 日期用绝对日期 `YYYY-MM-DD`，不用「下周」「最近」。
- 版本号用 `v主.次`；结构性修改升主版本，补充升次版本。
- Roadmap 用 `文档状态` + `执行状态` 两个字段，避免把「进行中」当成文档状态。
- 学习笔记不加元信息块；技术笔记可在文首放「核心编排准则清单」。
- 个人复盘可只保留周期和一句话，省略状态和版本。
- 变更记录只用于持续维护的文档；一次性快照不写。

## 5. 状态与标记词表

| 场景 | 词表 | 使用位置 |
|---|---|---|
| 文档状态 | 草稿 / 评审中 / 已定稿 / 已废弃 | 文档头 |
| 任务状态 | 未开始 / 进行中 / 阻塞 / 已完成 / 已取消 | Roadmap |
| 实现状态 | 已实现 / 计划实现 / 待确认 / 不做 | 设计文档 |
| 测试结果 | 通过 / 失败 / 阻塞 / 未执行 | 测试报告 |
| 缺陷级别 | P0 / P1 / P2 / P3 | 测试报告 |
| 复习优先级 | 必会 / 高频 / 加分 | 八股 |

不在同一文档混用同义状态词，如「完成 / 已搞定 / done」。

## 6. 语言与格式底线

- 全中文；术语、API、命令、字段名保留英文。
- 用陈述句和短句；一句话只表达一个判断。
- 不用「我们」开头的空话；不设问、不感叹、不寒暄。
- 结论、易错点、关键术语用 `**加粗**`。
- 缩进统一 2 个空格；列表嵌套不超过 3 层。
- 对比一律用表格；表格单元格不写长段落。
- 行内公式 `$...$`，块级公式独立成段；公式后解释符号。
- 代码块标注语言；代码前说明目的，代码后不逐行复述。
- 图用黑白灰；alt 文本写清图的内容。
- 引用块只用于真正的提醒；一个 callout 只讲一件事。

详细规则见 [01-通用规范](references/01-通用规范.md)。

## 7. 工作流

默认按「判类型 → 列骨架 → 等确认 → 分块写入 → 自检」执行：

1. **判类型**：按第 2 节确定主类型、读者和用途。
2. **列骨架**：只给 `#` / `##` / `###` 和每节一句话目标，不写正文。
3. **标缺口**：列出需要用户确认的事实、数据、决策和范围。
4. **等确认**：骨架通过后再写；用户要求一次成文时除外。
5. **分块写**：一次写一节或一个信息块；写完告知「已写入……」。
6. **不擅自扩写**：不加入用户没要求的内容、数据、结论。
7. **自检**：通用清单 + 类型清单各过一遍。
8. **更新状态**：持续维护的文档更新状态、版本和变更记录。

写入前说明将要写什么，写入后说明写了什么；不要静默大段改写。

## 8. 通用自检清单

- [ ] 类型判断正确，读者和用途明确。
- [ ] 标题连起来能当目录，没有空标题。
- [ ] 每个信息块有标签，不是自由散文。
- [ ] 每个无序、有序列表条目先有 2–8 字短标签，标签不是整句话。
- [ ] 没有超过 3 行的纯文字段落。
- [ ] 对比用了表格，表格内没有长段落。
- [ ] 结论、建议或判断在开头能找到。
- [ ] 每个判断都有证据或来源。
- [ ] 状态、日期、版本用词统一。
- [ ] 术语、符号、单位全文一致。
- [ ] 没有比喻、空话、装饰性 emoji、多余分隔线。
- [ ] 新内容能独立阅读，不依赖上下文。
- [ ] 没有重复标题、重复结论、重复内容。

## 9. 扩展新类型

新增文档类型时，先补齐 7 项契约，再写模板：

| 项 | 要回答的问题 |
|---|---|
| 读者 | 谁会读？读到什么程度？ |
| 用途 | 读完要做什么决定或动作？ |
| 组织轴 | 按认知、时间、论证、证据还是执行顺序展开？ |
| 槽位 | 固定使用哪些标签？ |
| 证据 | 什么算合格证据？ |
| 结尾 | 以什么形态收束？ |
| 更新 | 一次性快照，还是持续维护？ |

落地步骤：

1. 在 `references/` 新增 `0X-类型名.md`。
2. 文件内包含：适用场景、读者、组织轴、槽位词表、硬规则、快速模板、检查清单、反面模式。
3. 更新本文件的类型路由表。
4. 与其他类型重叠时，写明边界和优先级。

常见扩展候选：

- **需求文档**：读者 = 开发 / 测试；轴 = 背景 → 目标 → 用户故事 → 验收标准 → 非功能需求；结尾 = 待确认。
- **会议纪要**：读者 = 参会人；轴 = 结论 → 决议 → 行动项 → 待确认；结尾 = 行动项表。
- **故障复盘**：读者 = 团队；轴 = 时间线 → 影响 → 根因 → 处理 → 改进项；结尾 = 改进项与负责人。

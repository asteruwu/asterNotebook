# 函数与命名

## 1. 三层函数模型

| 层 | 回答的问题 | 典型长度 | 关键特征 |
|---|---|---|---|
| 编排层 | 这个流程分几步 | ≤ 30 行 | 只有顺序调用、错误检查、简单赋值 |
| 步骤层 | 这一步具体做什么 | ≤ 50 行 | 一个循环或一组分支，完成一个业务步骤 |
| 叶子层 | 这个判断 / 计算是什么 | ≤ 20 行 | 纯函数，输入决定输出 |

判断方法：

- 读函数时，如果需要在脑子里模拟 `for` 和 `if` 的细节，它是步骤层或叶子层。
- 读函数时，如果一眼能看出「先做什么、再做什么」，它是编排层。
- 编排层不应该出现业务计算的细节；步骤层不应该出现两层以上的无关职责。

## 2. 编排函数

### 模板

```go
func BuildApp(configPath string) (*App, error) {
    raw, err := LoadConfig(configPath)
    if err != nil {
        return nil, err
    }

    cfg, err := ValidateConfig(raw)
    if err != nil {
        return nil, err
    }

    deps, err := NewDependencies(cfg)
    if err != nil {
        return nil, err
    }

    return NewApp(cfg, deps), nil
}
```

规则：

- 每一行是一个命名步骤，步骤名本身就是注释。
- 编排函数只做三件事：调用步骤、检查错误、返回结果。
- 不在编排函数里写 `for` 循环的业务体；循环本身属于步骤层。
- 不在编排函数里做字段计算；需要计算就抽成步骤或叶子。
- 错误只在边界处理，不在这里包装过多上下文。
- 顺序变化时，编排函数应该是最先被读到、也最容易改的函数。

### 允许的长编排

装配型编排可以略长，但只允许「结构体字面量 + 命名步骤」：

```go
func AssembleRuntime(cfg Config, plan *Plan) (*Runtime, error) {
    repos, repoErrs := buildRepositories(plan.Repositories, cfg.Registry)
    handlers, handlerErrs := buildHandlers(plan.Handlers, cfg.Registry)

    errs := append(repoErrs, handlerErrs...)
    if len(errs) > 0 {
        return nil, fmt.Errorf("assemble: %w", errors.Join(errs...))
    }

    routes, pipelines := assembleRoutes(plan.Routes)
    attachPolicies(handlers, plan.Policies)

    return &Runtime{
        Server:  ServerConfig{ /* ... */ },
        Service: ServiceConfig{ /* ... */ },
        Storage: StorageConfig{ /* ... */ },
    }, nil
}
```

判断标准：如果把结构体字面量去掉，函数是否只剩命名步骤？如果是，长度可以放宽到 50 行。

### 编排函数不写步骤注释

编排函数只调用命名步骤，步骤名就是注释。

不推荐：

```go
func (s *OrderService) Process(ctx context.Context, req Request) (*Response, error) {
    // 0. 参数校验
    // 1. 幂等检查
    // 2. 加载聚合
    // 3. 执行领域逻辑
    // 4. 持久化
    // 5. 发布事件
}
```

推荐：

```go
func (s *OrderService) Process(ctx context.Context, req Request) (*Response, error) {
    if err := s.validate(req); err != nil {
        return nil, err
    }
    if err := s.ensureIdempotent(ctx, req); err != nil {
        return nil, err
    }
    entity, err := s.load(ctx, req.ID)
    if err != nil {
        return nil, err
    }
    if err := s.apply(ctx, entity, req); err != nil {
        return nil, err
    }
    if err := s.persist(ctx, entity); err != nil {
        return nil, err
    }
    return s.publish(ctx, entity)
}
```

规则：

- 不需要用编号注释解释流程；函数名按顺序读就是流程。
- 如果一段流程必须靠编号才能看清，说明步骤没有命名；抽成函数。
- 行内注释默认不写。

## 3. 步骤函数

### 一个步骤一个函数

```go
// CollectItems 遍历输入，产出名称、实体和校验错误三张表
func CollectItems(inputs []Input) (
    names []string,
    items []Item,
    errs []error,
) {
    // ...
}
```

规则：

- 函数名是一个动词短语，说明这一步做什么。
- 参数和返回值尽量显式；避免通过包级变量传状态。
- 一个步骤函数可以有循环，但循环体内只做「收集 / 转换 / 校验」中的一类事。
- 一个步骤函数可以有分支，但分支之间是同一件事的不同情况。
- 多个返回值超过 3 个时，用结果结构体代替。

### 步骤函数的拆分边界

| 信号 | 处理 |
|---|---|
| 循环体内超过 15 行 | 把循环体抽成 `buildXxx` / `appendXxx` |
| 一个 `if/else` 两边都超过 10 行 | 抽成两个步骤函数 |
| 函数名需要「和」 | 拆成两个函数 |
| 同时读写多个不相关的 map | 拆成多个收集步骤 |
| 同时做校验和转换 | 先校验，再转换，分成两个函数 |

## 4. 叶子函数

叶子函数是最小可复用单元，优先纯函数。

```go
func qualifiedName(scope, name string) string {
    return scope + "." + name
}

func makeID(name string, idx int) string {
    return name + "#" + strconv.Itoa(idx)
}

func cleanPath(p string) string {
    if p == "" {
        return "/"
    }
    return path.Clean(p)
}
```

规则：

- 不访问全局变量、不读环境变量、不写日志、不做 I/O。
- 输入相同，输出相同；便于表驱动测试。
- 名字精确到能看出输入输出，例如 `pathMatchesPrefix`、`normalizeHost`、`dedupeStrings`。
- 通用叶子放进 `pkg/tools`；带业务类型的叶子留在业务包。
- 叶子函数不调用步骤函数；调用方向只能是「编排 → 步骤 → 叶子」。

## 5. 拆分手法

### 5.1 抽循环体

拆分前：

```go
func buildOrders(orders []OrderInput) map[string]*Order {
    out := make(map[string]*Order)
    for _, o := range orders {
        // 20 行：构造明细、建索引、校验字段、写表
    }
    return out
}
```

拆分后：

```go
func buildOrders(orders []OrderInput) map[string]*Order {
    out := make(map[string]*Order, len(orders))
    for _, o := range orders {
        out[o.ID] = buildOrder(o)
    }
    return out
}

func buildOrder(o OrderInput) *Order {
    return &Order{
        ID:    o.ID,
        Items: buildItems(o.Items),
    }
}

func buildItems(inputs []ItemInput) []Item {
    items := make([]Item, 0, len(inputs))
    for _, in := range inputs {
        items = append(items, Item{SKU: in.SKU, Qty: in.Qty})
    }
    return items
}
```

### 5.2 抽分支

拆分前：

```go
if hasDiscount && discount == nil {
    errs = append(errs, ...)
} else if !hasDiscount && discount != nil {
    errs = append(errs, ...)
} else if hasDiscount && discount != nil {
    errs = append(errs, validateDiscount(discount)...)
}
```

拆分后：

```go
switch {
case hasDiscount && discount == nil:
    errs = append(errs, discountMissing())
case !hasDiscount && discount != nil:
    errs = append(errs, discountUnexpected())
case hasDiscount && discount != nil:
    errs = append(errs, validateDiscount(discount)...)
}
```

规则：分支条件超过 2 个布尔变量时，先抽谓词函数，再写 `switch`。

### 5.3 早返回，去掉 else

拆分前：

```go
if user, ok := users[id]; !ok {
    return nil, ErrNotFound
} else {
    result = user
}
```

拆分后：

```go
user, ok := users[id]
if !ok {
    return nil, ErrNotFound
}
result = user
```

规则：

- 错误、空值、边界先返回。
- `return` 后面不再写 `else`。
- 正常路径保持在最外层，异常路径提前退出。
- 嵌套超过 3 层时，优先用 `continue` / `return` 把深层逻辑提到浅层。

### 5.4 参数用配置结构体

拆分前：

```go
func NewPool(addr string, maxConn, minIdle int, dial, borrow, idle, wait time.Duration) *Pool
```

拆分后：

```go
func NewPool(addr string, cfg PoolConfig) *Pool
```

规则：

- 参数超过 5 个，改为配置结构体。
- 布尔参数超过 1 个，改为选项结构体或拆成两个函数。
- 配置结构体只承载数据，不承载行为。

### 5.5 返回值用结果结构体

拆分前：

```go
func Calculate(...) (items []Item, totals []Total, errs []error)
```

拆分后：

```go
type Plan struct {
    Items  []Item
    Totals []Total
}

func Calculate(...) *Plan
```

规则：

- 返回超过 3 个值，用结构体。
- 多个返回值属于同一概念时，用结构体命名这个概念。
- 结构体字段按「输入 → 中间 → 输出」排列。

### 5.6 I/O 与计算分离

拆分前：

```go
func process(path string) error {
    data, err := os.ReadFile(path)
    // 解析
    // 校验
    // 写回
}
```

拆分后：

```go
func process(path string) error {
    data, err := read(path)
    if err != nil {
        return err
    }
    cfg, err := parse(data)
    if err != nil {
        return err
    }
    if err := validate(cfg); err != nil {
        return err
    }
    return write(path, cfg)
}
```

规则：I/O、解析、校验、转换、写回分别是步骤；纯计算下沉到叶子。

### 5.7 分支表驱动

拆分前：

```go
switch kind {
case "daily":
    // 10 行
case "weekly":
    // 10 行
default:
    // 10 行
}
```

拆分后：

```go
var reporters = map[string]func(Config) (Reporter, error){
    "daily":  newDailyReporter,
    "weekly": newWeeklyReporter,
}
```

规则：分支超过 3 个、每个分支结构相似时，用 map 或注册表；分支逻辑差异大时，保留 `switch`。

## 6. 命名

### 基本规则

- 函数名 = 动词 + 对象：`LoadConfig`、`BuildPlan`、`ValidateOrder`、`AttachMetadata`。
- 名词函数表示纯转换：`qualifiedName`、`flattenItems`、`cloneOrDefault`。
- 判断函数用 `is` / `has` / `can` / `should`：`isValid`、`hasPermission`、`canRetry`。
- 构造函数用 `New`：`NewRepository`、`NewService`。
- 选项 / 配置用 `Config`：`PoolConfig`、`ServerConfig`。
- 错误用 `Err`：`ErrNotFound`、`ErrConflict`。
- 常量用 `Default` / `Max` / `Min`：`DefaultTimeout`、`MaxRetries`。
- 接口用能力名词，不加 `I` 前缀：`Repository`、`Notifier`、`Handler`。

### 泛名禁用表

| 不要用 | 改为 |
|---|---|
| `handleData` | `routeRequest` / `buildPlan` |
| `process` | `compileConfig` / `transformRequest` |
| `doCheck` | `validateOrder` |
| `getData` | `loadConfig` |
| `utils` | `pkg/tools/<领域>.go` + 具体函数名 |
| `res` | `verified` / `plan` / `cfg` |
| `flag` | `ok` / `alive` / `found` |
| `tmp` | 说明它代表什么 |

入口函数可以用 `Handle` / `Process`，因为它们本身就是流程名；内部函数必须具体。

### 一致性

- 同一概念全文一个词：`user` 不要和 `usr`、`account` 混用。
- 缩写只在项目内通用时使用：`cfg`、`conn`、`req`、`resp`、`err`、`ctx`。
- 不要为了短而缩写：`cfg` 可以，`c`、`s`、`x` 不行。
- 名字长度与作用域成正比：包级函数用完整名，短循环变量用 `i`、`r`、`s`。

## 7. 注释

- 默认不写。很多函数不需要注释。
- 需要时一行说明函数做什么，以函数名开头。
- 行内注释尽量避免；能用命名或结构表达，就不写。
- 不写控制流、没做什么、设计意图、方案取舍、历史背景。
- 不写编号步骤注释；把步骤抽成命名函数。
- TODO 一行，写做什么和解除条件。

```go
// Get 返回指定用户的当前配置。
func Get(userID string) (*Config, error)
```

```go
// 调用方必须已持有 p.mu。
func (p *Pool) removeLocked(w *waiter)
```

完整规则见 [05-注释.md](05-注释.md)。

## 8. 长度与嵌套基准

经验值：

| 类型 | 建议 | 上限 | 超过后 |
|---|---|---|---|
| 编排函数 | ≤ 30 行 | 50 行 | 检查是否有内联细节 |
| 步骤函数 | ≤ 50 行 | 80 行 | 抽循环体或分支 |
| 叶子函数 | ≤ 20 行 | 30 行 | 拆成两个纯函数 |
| 嵌套 | ≤ 3 层 | 4 层 | 抽内层函数 |

判断方法：

- 一屏读不完，先找可命名的段落。
- 一段代码需要滚动才能看完，通常已经可以抽函数。
- 函数里有 3 个以上 `if` 且互不相关，拆。
- 函数里有 2 个以上循环且目的不同，拆。

## 9. 反模式

- ❌ 一个函数里 `for` + `if/else` + 业务计算全都有。
- ❌ 编排函数里写字段计算、字符串拼接、错误映射。
- ❌ 函数名 `handle`、`process`、`do`、`run` 混用，看不出职责。
- ❌ `return` 后面还写 `else`。
- ❌ 参数超过 5 个还继续加。
- ❌ 返回值超过 3 个还用多返回值。
- ❌ 注释逐行翻译代码。
- ❌ 复制粘贴一段逻辑，只改一两个字段。
- ❌ 用布尔参数控制函数行为：`process(req, true)`。
- ❌ 同一概念在同一个包里出现三种叫法。

## 10. 检查清单

- [ ] 编排函数只调用命名步骤，没有内联业务逻辑。
- [ ] 每个步骤函数只做一件事，名字能说清。
- [ ] 叶子函数是纯函数，没有 I/O 和全局状态。
- [ ] 生产代码函数不超过 50 行；编排函数不超过 30 行。
- [ ] 嵌套不超过 3 层，超过已抽函数。
- [ ] 错误和边界先处理，没有 `else` after `return`。
- [ ] 参数不超过 5 个，返回值不超过 3 个。
- [ ] 没有泛名、缩写滥用、同义词混用。
- [ ] 注释说明做什么和边界，不复述代码，不解释设计意图。
- [ ] 拆分后调用方向仍然是「编排 → 步骤 → 叶子」。

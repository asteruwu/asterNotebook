# 测试、提交与评审

## 1. 测试布局

| 测试类型 | 位置 | 目的 |
|---|---|---|
| 单元测试 | 与被测代码同包，`*_test.go` | 验证函数、分支、边界 |
| 包级集成测试 | 包内 `*_test.go` 或 `testdata/` | 验证包内协作 |
| 端到端测试 | `integration/` 或 `e2e/` | 验证完整链路 |
| 假实现 | `integration/fake/` 或 `testutil/` | 提供可控的依赖行为 |

规则：

- 单元测试与被测代码同包，便于访问未导出函数。
- 跨包行为放 `integration/`，不要在每个包里重复搭完整链路。
- 假实现只实现被用到的行为，不模拟整个系统。
- 测试文件命名 `xxx_test.go`，和被测文件同名。
- 测试代码也要遵守函数拆分规则；测试辅助函数放文件顶部。

## 2. 表驱动测试

### 模板

```go
func TestCalculateTotal(t *testing.T) {
    cases := []struct {
        name  string
        items []Item
        want  int
    }{
        {"empty", nil, 0},
        {"single", []Item{{Qty: 2, Price: 10}}, 20},
        {"with discount", []Item{{Qty: 2, Price: 10}}, 18},
    }

    for _, c := range cases {
        t.Run(c.name, func(t *testing.T) {
            got := CalculateTotal(c.items)
            if got != c.want {
                t.Errorf("CalculateTotal() = %d, want %d", got, c.want)
            }
        })
    }
}
```

规则：

- 每个用例有 `name`，用 `t.Run` 单独运行。
- 用例结构体字段按「输入 → 期望」排列。
- `t.Run` 内部只写调用和断言，不写复杂准备。
- 用例名描述场景，不写 `case1`。
- 表驱动适合「同一逻辑、不同输入」；不同流程用独立测试函数。
- 子测试可以并行时加 `t.Parallel()`，但共享状态时不要加。

## 3. 测试辅助

### t.Helper

```go
func newTestRepository(t *testing.T) *Repository {
    t.Helper()
    repo, err := NewRepository(":memory:")
    if err != nil {
        t.Fatalf("new repository: %v", err)
    }
    return repo
}
```

规则：

- 所有测试辅助函数第一行调用 `t.Helper()`。
- `t.Helper()` 让失败行号指向调用方，而不是辅助函数内部。
- 辅助函数只做构造，不做断言；断言留在测试函数里。

### t.Cleanup

```go
func newTestService(t *testing.T) *Service {
    t.Helper()
    svc := NewService(newTestRepository(t))
    t.Cleanup(func() { _ = svc.Close() })
    return svc
}
```

规则：

- 资源创建后立即注册 `t.Cleanup`，不要依赖测试末尾手动关闭。
- 多个资源按创建逆序清理。
- 清理函数里的错误可以忽略，但要写 `_ =`。
- 不要在 `t.Cleanup` 里做断言。

### 构造函数辅助

把冗长的配置构造抽成命名函数：

```go
func testItems(qty int) []Item
func testConfig(timeout time.Duration) Config
func testServer(t *testing.T) *Server
```

规则：

- 辅助函数名说明它构造什么。
- 默认值合理，参数只暴露需要变化的字段。
- 测试里不重复写大段配置字面量。

## 4. 断言

### 失败级别

- `t.Fatalf`：准备失败、后续无法继续，例如 `NewRepository` 失败。
- `t.Errorf`：值不符合预期，但可以继续检查其他字段。
- `t.Fatal` / `t.Error`：没有格式化参数时使用。

规则：

- 失败消息包含 `got` 和 `want`。
- 错误断言用 `errors.Is`，不用字符串比较。
- 切片比较用 `slices.Equal`。
- 不引入断言库；标准库足够。
- 一个测试检查多个相关字段时，用多个 `t.Errorf`，不要第一个失败就退出。

### 错误断言

```go
if !errors.Is(err, gerrors.ErrNotFound) {
    t.Fatalf("err = %v, want %v", err, gerrors.ErrNotFound)
}
```

规则：

- 哨兵错误用 `errors.Is`。
- 包装错误也适用 `errors.Is`。
- 需要检查错误类型时用 `errors.As`。
- 不比较 `err.Error()` 字符串。

## 5. 并发测试

- 并发用例必须跑 `-race`。
- 用等待辅助函数代替裸 `time.Sleep`：

```go
func waitFor(t *testing.T, cond func() bool) {
    t.Helper()
    deadline := time.Now().Add(time.Second)
    for time.Now().Before(deadline) {
        if cond() {
            return
        }
        time.Sleep(time.Millisecond)
    }
    t.Fatal("condition not met before deadline")
}
```

规则：

- 等待条件 + 超时，不用固定长睡眠。
- 必须睡眠时，优先用等待辅助函数；无法替代时写一行说明在等什么。
- 并发测试覆盖：竞争、超时、关闭、恰好一次唤醒。
- 测试结束前确保所有 goroutine 退出；用 `t.Cleanup` 关闭资源。
- 不在测试里使用无限循环；所有循环都有退出条件。

## 6. 集成测试

集成测试复用同一套 helper，不重复接线：

```go
func startTestServer(t *testing.T, cfg Config) *Server {
    t.Helper()

    srv, err := NewServer(cfg)
    if err != nil {
        t.Fatalf("new server: %v", err)
    }
    t.Cleanup(func() { _ = srv.Close() })

    go func() {
        if err := srv.Start(); err != nil {
            t.Logf("server stopped: %v", err)
        }
    }()

    return srv
}
```

规则：

- 集成测试复用同一套 helper，不重复接线。
- 假依赖用随机端口或临时目录，避免冲突。
- 每个测试自己构造配置，不依赖全局配置。
- 测试结束后关闭服务、连接、临时资源。
- 端到端用例覆盖主链路 + 异常链路，不只测 happy path。
- 端到端测试可以超过 50 行：它是一条线性场景时，用命名 helper 分段；出现两个独立场景时拆成两个测试。

## 7. 测试命名与注释

- 测试名描述行为：`TestGetReturnsNotFound`、`TestCalculateTotalWithDiscount`、`TestConcurrentPut`.
- 不写 `Test1`、`TestFoo`、`TestService`。
- 测试名说清场景，通常不需要额外注释；测试名无法表达背景时，补一句：

  ```go
  // TestGetReturnsNotFound 存储中不存在时返回 ErrNotFound。
  ```

- 子测试名用「条件 + 预期」：`"empty input returns zero"`。
- 失败消息写清「哪个字段、实际值、期望值」。

## 8. 提交规范

### 格式

```text
[vXX]type(scope): subject
```

示例：

```text
[v12]feat(order): add refund flow
[v12]refactor(payment): split validation from persistence
[v12]fix(http): normalize path before routing
[v12]docs(api): update error codes
[v12]test(order): cover duplicate refund
```

### 规则

- `[vXX]`：当前版本或阶段。
- `type`：`feat`、`fix`、`refactor`、`docs`、`test`、`chore`。
- `scope`：包路径或领域，如 `order`、`payment`、`http`、`all`。
- `subject`：英文、小写、祈使句、不加句号；尽量不超过 72 字符，超出时把细节放 body。
- 一次提交只做一件事；重构和功能分开，文档和代码分开。
- 需要解释「为什么」或「影响」时写 body；body 不重复 subject。
- 不写 `update`、`fix bug`、`changes`、`wip` 这类无信息提交。

### 提交粒度

| 场景 | 提交方式 |
|---|---|
| 新增一个能力 | 一个 `feat`，包含实现 + 测试 |
| 纯重构 | 一个 `refactor`，行为不变 |
| 修复 bug | 一个 `fix`，尽量带回归测试 |
| 文档更新 | 一个 `docs` |
| 配置样例更新 | 跟相关功能同一个提交，或单独 `docs(config)` |

## 9. 提交前检查

```bash
gofmt -w .
go vet ./...
go test ./... -race
```

规则：

- `gofmt -l .` 必须为空。
- `go vet` 不能有输出。
- 测试必须通过，并发用例带 `-race`。
- 新增导出函数必须有注释。
- 新增错误、常量必须归位到 `pkg/errors`、`pkg/constant`。
- 新增依赖要说明理由；优先标准库，确需第三方时保持最小。

## 10. 评审流程

1. **读 diff 范围**：确认提交只做一件事。
2. **看函数**：编排是否只编排，步骤是否原子，嵌套是否超限。
3. **看命名**：名字是否说明职责，是否有泛名。
4. **看包**：依赖方向是否正确，工具是否放错包。
5. **看错误与常量**：是否集中、是否包装、是否魔法值。
6. **看测试**：是否覆盖边界、异常、并发；是否可清理。
7. **看提交**：格式、scope、subject 是否准确。

评审意见写法：

- 指出问题 + 原因 + 建议，不只说「不好」。
- 区分「必须改」和「可以优化」。
- 对例外要求作者给出一句话解释。

## 11. 反模式

- ❌ 测试名 `Test1`、`TestService`，看不出行为。
- ❌ 一个测试函数覆盖十几个无关场景。
- ❌ 复制粘贴配置字面量，不用辅助函数。
- ❌ 用 `time.Sleep` 当同步手段。
- ❌ 测试失败只打印 `failed`，没有 got/want。
- ❌ 用字符串比较错误。
- ❌ 忘记 `t.Cleanup`，泄漏连接、监听器、goroutine。
- ❌ 并发测试不跑 `-race`。
- ❌ 提交 `update code`、`fix bug`、`wip`。
- ❌ 一个提交同时包含功能、重构、格式化、文档。
- ❌ 测试通过但 `go vet` 或 `gofmt` 不通过。

## 12. 检查清单

- [ ] 单元测试与被测代码同包；集成测试在 `integration/`。
- [ ] 表驱动用例有 `name`，用 `t.Run`。
- [ ] 测试辅助函数调用 `t.Helper()`。
- [ ] 资源创建后注册 `t.Cleanup`。
- [ ] 错误断言用 `errors.Is`，切片比较用 `slices.Equal`。
- [ ] 失败消息包含 got/want。
- [ ] 并发用例跑 `-race`，没有裸睡眠同步。
- [ ] 测试覆盖主链路、异常链路、边界。
- [ ] 提交格式 `[vXX]type(scope): subject`。
- [ ] 一次提交一个意图。
- [ ] `gofmt -l .`、`go vet ./...`、`go test ./... -race` 通过。

# Aster 代码风格

## 0. 定位

一句话：**编排函数是目录，不是正文；细节下沉到命名清楚的步骤函数。**

适用范围：

- Go 服务端项目：HTTP / gRPC / CLI、任务处理、数据管道。
- 新代码编写、旧代码重构、代码评审。
- 不适用于：生成代码、一次性脚本、必须内联的性能热点。

四条主原则：

1. **可读性优先**：先写清楚，再写短；不为压缩行数牺牲结构。
2. **编排与细节分离**：编排函数只调用命名步骤，不写循环体和业务细节。
3. **一个函数一个问题**：函数名能用一句话说清；说不清就拆。
4. **依赖单向、边界清晰**：入口负责接线，模块之间不互相 import，工具包不依赖业务。

示例约定：本文中的包名、类型名、业务名均为抽象示意，不对应任何具体项目。

## 1. 函数分三层

| 层 | 职责 | 建议长度 | 允许 | 禁止 | 典型命名 |
|---|---|---|---|---|---|
| 编排层 | 按顺序调用步骤、处理错误、返回结果 | ≤ 30 行（装配型 ≤ 50 行） | 错误检查、简单赋值、顺序调用 | 循环体、复杂分支、业务计算 | `Build`、`Run`、`Process`、`Handle` |
| 步骤层 | 完成一个业务步骤 | ≤ 50 行 | 循环、分支、调用叶子函数 | 同时承担多个职责 | `CollectItems`、`AssembleRoutes`、`ValidateOrder` |
| 叶子层 | 纯计算或小工具 | ≤ 20 行 | 纯逻辑、类型转换、判断 | I/O、全局状态、业务编排 | `QualifiedName`、`CleanPath`、`FlattenItems` |

- 三层是职责划分，不是目录结构。
- 编排层可以没有返回值；有返回值时只做透传，不加工。
- 步骤层可以有 `for` 和 `if`，但每个分支只做一件事。
- 叶子层尽量纯函数，输入决定输出，方便单测。

## 2. 硬规则

1. **编排函数只编排**：按顺序调用命名步骤，不写 `for` 里的业务逻辑。
2. **函数原子化**：一个函数只做一件事；超过 50 行先问「能不能拆成两个」。
3. **嵌套不超过 3 层**：超过就把内层抽成命名函数；循环用 `continue` 做守卫。
4. **早返回**：错误和边界先处理；禁止 `return` 后面再写 `else`。
5. **命名即文档**：动词 + 对象；禁止 `handleData`、`process`、`do`、`util` 这类泛名，入口函数除外。
6. **无业务依赖的工具进 `pkg/tools`**：无状态、不 import 业务包；优先纯函数，允许通用 I/O 包装；带业务类型就留在业务包。
7. **错误集中到 `pkg/errors`**：按域分组、哨兵错误、`%w` 包装、`errors.Join` 聚合。
8. **常量集中到 `pkg/constant`**：按域分组、`DefaultXxx` 命名、类型化枚举、禁止魔法值。
9. **依赖单向**：入口 → 模块；模块之间不互相 import；接口定义在消费方。
10. **配置分三层**：原始配置 → 校验后的配置 → 运行时对象；装配函数只装配。
11. **测试表驱动**：`t.Run` + `t.Helper` + `t.Cleanup` + `errors.Is`；并发用例跑 `-race`。
12. **提交单意图**：`[vXX]type(scope): subject`；重构、功能、文档分开提交。
13. **注释默认不写**：需要时一句话说明函数做什么；行内注释尽量避免；能用命名步骤代替就不写注释；不写设计意图、控制流、没做什么。

## 3. 拆分信号

出现以下任一情况，立即拆分：

- 函数名需要用「和 / 并且」连接两件事。
- 一个函数里同时有 `for`、`if/else` 和业务计算。
- 嵌套超过 3 层。
- 函数超过 50 行，或一屏看不完。
- 参数超过 5 个。
- 返回值超过 3 个。
- 同时做 I/O 和纯计算。
- 需要靠编号注释才能看清流程，说明步骤没有命名；抽成命名函数。
- 需要写「这里顺便处理……」的注释。

拆分顺序：

1. 先把循环体抽成函数。
2. 再把分支体抽成函数。
3. 最后把纯计算抽成叶子函数。
4. 每抽一层，先命名，再决定参数和返回值。

## 4. 命名规则

| 场景 | 规则 | 示例 |
|---|---|---|
| 构造 | `NewX` | `NewRepository`、`NewService` |
| 构建 | `BuildX` | `BuildApp`、`BuildIndex` |
| 加载 | `LoadX` | `LoadConfig`、`LoadTemplate` |
| 计算 | `CalculateX` | `CalculateTotal`、`CalculatePlan` |
| 校验 | `ValidateX` | `ValidateOrder`、`ValidateConfig` |
| 装配 | `AssembleX` | `AssembleRuntime`、`AssembleRoutes` |
| 展平 | `FlattenX` | `FlattenItems`、`FlattenPolicy` |
| 附加 | `AttachX` | `AttachMetadata`、`AttachPolicies` |
| 判断 | `isX` / `hasX` / `canX` / `shouldX` | `isValid`、`hasPermission` |
| 错误 | `ErrXxx` | `ErrNotFound`、`ErrConflict` |
| 常量 | `DefaultXxx` / `XxxMax` / `XxxMin` | `DefaultTimeout`、`MaxRetries` |
| 配置 | `XxxConfig` | `ServerConfig`、`PoolConfig` |
| 接口 | 能力名词，不加 `I` 前缀 | `Repository`、`Notifier`、`Handler` |

- 名字要能读出「做什么」，必要时能读出「对谁做」。
- 布尔返回值用 `ok`、`found`、`alive`，不用 `flag`、`res`。
- 缩写保持项目一致：`cfg`、`conn`、`req`、`resp`、`err`；不要自造缩写。
- 同一个概念全文一个词；不要 `user` / `usr` / `account` 混用。
- `Process` / `Handle` 只能作为模块入口方法名；内部步骤函数必须具体。

## 5. 包与依赖

```text
cmd/                   入口，唯一接线点
internal/
  transport/           协议接入：HTTP、gRPC、CLI
  service/             用例编排、业务规则
  repository/          存储访问
  model/               领域模型，叶子包
pkg/
  errors/              哨兵错误，按域分组
  constant/            共享常量，按域分组
  tools/               无业务依赖的工具
```

规则：

- `cmd` 只做三件事：读配置、按依赖逆序构造模块、启动服务。
- `transport`、`service`、`repository` 之间不互相 import；由入口注入接口或函数值。
- `model` 是叶子包，零项目依赖。
- `pkg/errors`、`pkg/constant`、`pkg/tools` 是叶子工具包，不 import 业务包。
- 接口定义在消费方，实现放在提供方；构造函数返回具体类型，调用方接收接口。
- 需要跨层回调时，用函数值注入，避免反向依赖。
- 导入分组：标准库 → 第三方 → 本项目，组间空行；别名固定，例如 `gerrors`、`gconst`。

## 6. 错误与常量

- 哨兵错误集中在 `pkg/errors`，按域分组，例如 `config`、`transport`、`service`、`repository`。
- 业务代码不散落 `errors.New`；需要新错误时先加到错误包。
- 包装用 `fmt.Errorf("%w: context", sentinel)`；聚合用 `errors.Join`。
- 判断用 `errors.Is` / `errors.As`，不比较字符串。
- 对外状态码映射集中在一个函数；不要在每层写 `switch`。
- 校验阶段收集全部错误再返回，不遇到第一个错误就退出。
- 常量按域分组，段注释统一；默认值命名 `DefaultXxx`，上下限命名 `XxxMin` / `XxxMax`。
- 枚举用类型化常量，例如 `type Role string`。
- 默认值集中在一个函数里应用，不散落在构造函数各处。

## 7. 日志

- 统一用 `log`，不用 `fmt.Println` 打生产日志。
- 每条日志带组件前缀：`[main]`、`[http]`、`[service]`、`[repo]`。
- 消息小写，不加句号；错误附在末尾。
- 请求级错误在边界记录一次，不在每一层重复 log-and-return。
- 不记录 token、密钥、完整请求体等敏感信息。
- 高频路径用指标统计，不靠日志逐条打印。

## 8. 工作流

1. **读调用链**：先读目标函数、调用方和被调用方，确认编排边界。
2. **列步骤**：用一行一个动词短语写出流程，不写代码。
3. **分层**：给每一步标「编排 / 步骤 / 叶子」。
4. **先命名**：每个步骤先定函数名；名字定不下来，说明职责没想清。
5. **写编排**：先写只调用步骤的编排函数。
6. **写步骤**：一次写一个步骤；超过 50 行就继续拆。
7. **写叶子**：纯计算和小工具最后写，优先放进 `pkg/tools`。
8. **自检**：按第 9 节清单过一遍。
9. **验证**：`gofmt -w`、`go vet ./...`、`go test ./... -race`。

重构旧代码时：

- 先补测试，再拆函数；不要一边改行为一边重构。
- 一次只拆一个函数，保持编译通过。
- 拆分后对比行为，确保错误链和返回值不变。

## 9. 评审清单

### 函数

- [ ] 编排函数只调用命名步骤，没有内联业务逻辑。
- [ ] 每个函数只做一件事，名字能说清职责。
- [ ] 生产代码函数不超过 50 行；编排函数不超过 30 行（装配型不超过 50 行）。
- [ ] 嵌套不超过 3 层。
- [ ] 错误和边界先处理，没有 `else` after `return`。
- [ ] 参数不超过 5 个；超过时用配置结构体。
- [ ] 没有同时做 I/O 和纯计算。

### 包与依赖

- [ ] 入口是唯一接线点。
- [ ] 模块之间没有互相 import。
- [ ] `pkg/tools` 没有业务依赖。
- [ ] 接口定义在消费方，实现放在提供方。
- [ ] 配置按「原始 → 校验后 → 运行时」分层。

### 错误与常量

- [ ] 新错误加在 `pkg/errors`，按域分组。
- [ ] 错误用 `%w` 包装，判断用 `errors.Is`。
- [ ] 校验错误聚合返回，不是遇错即返。
- [ ] 对外状态码映射集中在一处。
- [ ] 常量加在 `pkg/constant` 或文件顶部，没有魔法值。
- [ ] 默认值集中应用。

### 测试与提交

- [ ] 表驱动，`t.Run`，`t.Helper`，`t.Cleanup`。
- [ ] 错误断言用 `errors.Is`。
- [ ] 并发用例跑 `-race`。
- [ ] 测试名描述行为，不写 `Test1`。
- [ ] 提交格式 `[vXX]type(scope): subject`，一次一个意图。

### 注释

- [ ] 能删的注释已删；大多数函数没有注释。
- [ ] 保留的注释只有一句，说明功能或非显然语义。
- [ ] 没有行内注释；没有编号步骤注释。
- [ ] 没有控制流复述、没做什么、设计意图、方案取舍。
- [ ] TODO 只有一行，写做什么和解除条件。
- [ ] 注释与代码同步，没有过时注释或注释掉的代码。

## 11. 边界与例外

以下情况允许突破常规长度限制，但必须满足附加条件：

| 场景 | 允许 | 条件 |
|---|---|---|
| 并发状态机 | 超过 50 行 | 用编号阶段注释；锁的持有范围写清楚；单一关闭路径 |
| 协议解析 / 编解码 | 超过 50 行 | 一个函数只处理一种协议；帧边界和错误路径显式 |
| 配置校验笛卡尔积 | 嵌套 4 层 | 每层只做一件事；内层超过 20 行时抽函数 |
| 性能热路径 | 内联、少抽象 | 有基准测试数据；不靠注释解释设计 |
| 生成代码 | 不适用 | 不手改；重新生成 |

判断标准：**例外必须在评审中一句话说清「为什么不能拆」，否则就不是例外。**
